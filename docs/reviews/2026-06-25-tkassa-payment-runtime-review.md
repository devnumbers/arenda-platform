# Ревью пользовательских сценариев оплаты и интеграции с Т‑Кассой

**Дата:** 2026-06-25  
**Коммит:** `HEAD` текущей ветки  
**Область:** `apps/backend/internal/billing`, интеграция `tkassa`, пользовательские сценарии подписки  
**Предыдущее ревью:** [`docs/reviews/2026-06-22-tkassa-integration-review.md`](./2026-06-22-tkassa-integration-review.md)

## Краткий вердикт

Большинство критических контрактных нарушений, зафиксированных в ревью от 2026‑06‑22, исправлены: базовый URL `/v2/`, `PaymentId` как строка, отсутствие `Recurrent=Y` в MIT‑списаниях, валидация `APP_BASE_URL`, проверка `TerminalKey` в webhook, исключение `Data`/`DATA`/`Receipt` из подписи.

Однако в ходе текущего ревью (code review адаптера и сервисного слоя + попытка прогона сценариев через реальный sandbox Т‑Кассы) выявлены **новые риски и недоделки**, которые могут привести к ошибкам автопродления, неправильной обработке привязки карт и затруднённой диагностике в production. Реальный sandbox Т‑Кассы в текущих условиях недоступен (HTTP 403) без whitelist IP со стороны банка, поэтому end‑to‑end проверка оплаты/привязки карты через Т‑Кассу **не выполнена**.

## Исправлено в рамках этой задачи

- **C2** — добавлен фоновый дожим pending upgrade‑платежей (`ProcessPendingUpgradePayments` + `BillingWorker`).
- **I1** — убрана некорректная обработка `AddCustomer` code `7` как дубликата; ошибки AddCustomer теперь прокидываются.
- **I2** — `RemoveCard` теперь мапит коды `107` и `231` как «карта не найдена`; убран `502`.
- **I3/I4** — `ParseWebhook` явно dispatch'ит по `NotificationType`, принимает `NotificationAddCard` и устаревший `AddCard`, отклоняет неизвестные типы.
- **I5** — перед повторным `Charge` в renewal вызывается `provider.Status(GetState)`.
- **I6** — код ошибки провайдера сохраняется в `subscription_payments.error_code` при failed renewal.
- **N1** — оставлено без изменений: согласно официальной документации, метод `Charge` не принимает поле `Amount`.
- **N2** — убраны неподдерживаемые URL из `InitAddCardRequest` и сервисного вызова.
- **N3** — проверка `IsActive` в `DeletePaymentMethod` перенесена внутрь транзакции.
- **N5** — при HTTP‑ошибках адаптер сохраняет первые байты тела ответа.
- **N6** — Bruno‑коллекция `system-e2e/10-subscription` приведена в соответствие с актуальным ответом `AddPaymentMethod` (`paymentMethod.id`, статус 200).

## Scope ревью

Проверялись пользовательские сценарии, связанные с **Оплатой подписки / Subscription Payment**:

1. Первичная оплата тарифа (оформление подписки).
2. Автопродление подписки.
3. Неудачное автосписание и поведение системы (grace → blocked / базовый тариф).
4. Добавление / удаление / активация способа оплаты (привязка карты).
5. Апгрейд / даунгрейд тарифа.
6. Отмена и восстановление подписки.
7. Обработка уведомлений от Т‑Кассы (webhooks).
8. Возврат средств / refund (ограниченно: в коде нет прямого вызова `Cancel`/`Refund` для подписок).

Операции по объектам (арендные платежи, ЖКУ) в scope не входили.

## Методология

- **Code review** адаптера `apps/backend/internal/billing/adapters/payment/tkassa/tkassa.go` и сервиса `apps/backend/internal/billing/application/service.go` на соответствие официальной документации Т‑Кассы API v2 (`https://developer.tbank.ru/eacq/api`).
- **Runtime‑проверка** через реальный sandbox Т‑Кассы с терминалом `1782144767344DEMO` и endpoint `https://rest-api-test.tinkoff.ru/v2/`.
- **Проверка Bruno/e2e** в двух конфигурациях:
  - `PAYMENT_PROVIDER=tkassa` — ручные запросы и коллекции.
  - `PAYMENT_PROVIDER=fake` — системная e2e коллекция `system-e2e/10-subscription`.

## Найденные риски и несоответствия

### 🔴 Критические

#### C1. Sandbox Т‑Кассы возвращает 403 Forbidden — невозможно пройти реальные платежи

- **Проявление:** любой вызов `Init`, `AddCustomer` к `https://rest-api-test.tinkoff.ru/v2/` возвращает `403 Forbidden`.
- **Причина:** для доступа к тестовой среде Т‑Банк требует whitelist IP, с которого идут запросы.
- **Влияние:** end‑to‑end проверка первичной оплаты, автопродления и привязки карты через Т‑Кассу невозможна до получения доступа. Все findings ниже получены из code review и частично из тестов на `fake`‑провайдере.
- **Рекомендация:** написать в поддержку Т‑Кассы (`acqhelp@tbank.ru`) с запросом на добавление IP в whitelist для `rest-api-test.tinkoff.ru` либо получить доступ к терминалу/URL без ограничения.

#### C2. Нет фонового дожима pending‑платежей за апгрейд

- **Файлы:** `apps/backend/internal/billing/application/service.go` (`changeTariffUpgrade`, `HandleWebhook`).
- **Проблема:** при апгрейде тарифа создаётся pending‑платёж, вызывается `Init`, и система ждёт webhook от Т‑Кассы. Если webhook потерян (недоступен `NotificationURL`, сетевая ошибка, local‑разработка), платёж остаётся pending, а подписка никогда не перейдёт на новый тариф.
- **В отличие от автопродления:** для renewal есть `recoverRenewalFailure` с вызовом `GetState`; для upgrade — нет worker/фонового дожима.
- **Рекомендация:** добавить периодическую задачу (worker), которая для pending upgrade‑платежей старше N минут запрашивает `GetState` и финализирует платёж, аналогично `recoverRenewalFailure`.

### 🟡 Важные

#### I1. `AddCustomer` обрабатывает неверный код ошибки как «дубликат»

- **Файл:** `apps/backend/internal/billing/adapters/payment/tkassa/tkassa.go:594–602`.
- **Проблема:** `isDuplicateCustomerError` считает `ErrorCode == "7"` признаком дублирующего покупателя. Согласно официальной таблице кодов ошибок (`https://developer.tbank.ru/eacq/intro/errors/error-codes`), код `7` — **«Неверный статус покупателя»**, а не «уже существует».
- **Влияние:** реальные проблемы со статусом покупателя будут проигнорированы, и система попытается вызвать `AddCard` на невалидного покупателя.
- **Рекомендация:** проверить в sandbox, какой код реально возвращает `AddCustomer` при существующем `CustomerKey`. Если `Success=true` (идемпотентность), убрать спецобработку. Если есть отдельный код дубликата — использовать его.

#### I2. `RemoveCard` не мапит код `107` «карта не найдена»

- **Файл:** `apps/backend/internal/billing/adapters/payment/tkassa/tkassa.go:604–614`.
- **Проблема:** `isCardNotFoundError` мапит коды `502` и `231`. Документация:
  - `231` = «Не найден идентификатор карты» ✅
  - `502` = «Карта по RequestKey не найдена» — относится к `AddCard`/`GetAddCardState`, а не `RemoveCard`.
  - `107` = «Неверно введен CardId. Проверьте, что такая карта была ранее привязана» — именно этот код вероятен для `RemoveCard`, но он **не обработан**.
- **Влияние:** попытка удалить уже удалённую у провайдера карту не будет считаться «not found», и локальная запись не удалится.
- **Рекомендация:** добавить код `107`, убрать `502` из `RemoveCard` (оставить только для `AddCard`, если используется).

#### I3. Непонятно, совпадает ли `NotificationType` для AddCard с реальным webhook

- **Файлы:** `tkassa.go:36`, `tkassa.go:331`; `service.go:640`.
- **Проблема:** код ожидает `NotificationType == "AddCard"`. В официальной документации уведомление называется **NotificationAddCard**, а в примере проверки токена перечислены поля, но не указано точное значение `NotificationType`. Если реальный webhook присылает `"NotificationAddCard"`, привязка карты сломается.
- **Влияние:** пользователь привяжет карту на форме Т‑Кассы, webhook придёт, но система не создаст способ оплаты.
- **Рекомендация:** после получения доступа к sandbox протестировать привязку карты и зафиксировать реальное значение. Возможно, стоит принимать оба варианта.

#### I4. Неизвестные типы уведомлений обрабатываются как платежи

- **Файл:** `tkassa.go:331–367`.
- **Проблема:** если Т‑Касса пришлёт `NotificationFiscalization`, `NotificationQr` или новый тип уведомления на тот же URL, код попытается распарсить его как платёж (`OrderId`, `PaymentId`, `Status`).
- **Влияние:** некорректная обработка/запись несуществующих платежей, ложные ошибки в логах.
- **Рекомендация:** явно dispatch'ить по `NotificationType`: поддерживать `NotificationPayment`/`AddCard` (или пустое значение), остальные — отклонять с ошибкой.

#### I5. Renewal‑воркер может повторно вызывать `Charge` для pending‑платежа

- **Файл:** `service.go:1087–1356`.
- **Проблема:** если `Charge` вернул `Pending` и webhook не дошёл, следующий запуск воркера найдёт тот же pending‑платёж и снова вызовет `Charge` с тем же `PaymentId`/`RebillId`. Т‑Касса не гарантирует идемпотентность повторных `Charge`.
- **Влияние:** риск двойного списания или ошибки провайдера.
- **Рекомендация:** перед повторным `Charge` вызывать `provider.Status(GetState)`. Если платёж уже финализован — применить результат; если pending — оставить в ожидании webhook.

#### I6. Код ошибки провайдера не сохраняется при failed renewal

- **Файлы:** `service.go:1323`, `markRenewalFailedAndGrace`.
- **Проблема:** при неудачном автопродлении в `subscription_payments.error_code` пишется `nil`, хотя `ProviderError.ErrorCode` известен.
- **Влияние:** невозможно понять причину неудачи (недостаточно средств, блокировка карты и т.д.) без логов.
- **Рекомендация:** передавать распарсенный `ErrorCode` в `MarkFailed` при recovery/renewal failure.

### 🟢 Замечания

#### N1. `Charge` не передаёт `Amount`

- **Файл:** `tkassa.go:196–201`.
- **Проблема:** в теле `Charge` нет поля `Amount`. Согласно документации, `Amount` для `Charge` не является обязательным (сумма берётся из родительского платежа), но явная передача защищает от несоответствий.
- **Рекомендация:** уточнить у Т‑Кассы/в sandbox, рекомендуется ли передавать `Amount`; при необходимости добавить.

#### N2. Для `AddCard` передаются URL, которые API не принимает

- **Файлы:** `service.go:448–461`, `tkassa.go:241–284`.
- **Проблема:** `AddPaymentMethod` строит `SuccessURL`/`FailURL`/`NotificationURL` и передаёт их в `InitAddCard`. Официальная схема `/v2/AddCard` не содержит этих полей — они настраиваются в терминале.
- **Влияние:** код работает (поля просто не отправляются в теле, так как адаптер их отбрасывает), но логика в сервисе вводит в заблуждение. Локально webhook AddCard не придёт на `localhost` без tunnel/whitelist.
- **Рекомендация:** убрать URL из `InitAddCardRequest` и явно задокументировать, что AddCard URL настраиваются в личном кабинете Т‑Кассы.

#### N3. `DeletePaymentMethod` проверяет `IsActive` вне транзакции

- **Файл:** `service.go:498–539`.
- **Проблема:** метод загружается, проверяется `IsActive`, затем открывается транзакция. Между проверкой и транзакцией другой запрос может активировать карту.
- **Рекомендация:** перенести проверку `IsActive` внутрь транзакции (`SELECT FOR UPDATE`).

#### N4. Webhook успешной оплаты и AddCard всегда активирует новую карту

- **Файлы:** `service.go:695–668`, `applyPaymentResult`.
- **Проблема:** после каждого успешного платежа или привязки карта становится активной по умолчанию. Пользователь не может сохранить старую карту по умолчанию, оплатив однократно другой.
- **Рекомендация:** задокументировать поведение или дать пользователю возможность не менять активный способ оплаты.

#### N5. Адаптер теряет тело ответа при HTTP‑ошибках

- **Файл:** `tkassa.go:391–394`.
- **Проблема:** при HTTP 4xx/5xx тело ответа читается и сбрасывается; в ошибке только статус.
- **Рекомендация:** включать первые N байт тела в ошибку (без секретов) для упрощения диагностики.

#### N6. Bruno/e2e коллекции рассчитаны на `fake`‑провайдер

- **Результат прогона `system-e2e/10-subscription` с `PAYMENT_PROVIDER=fake`:** 11/16 запросов passed, 5 failed.
- **Причины failures:**
  - `activate second payment method` — 400 вместо 204 (в коллекции ожидается, что добавлено два метода оплаты, но сценарий setup не привёл к этому).
  - Несколько negative‑тестов ожидают статусы, которые не совпадают с текущим состоянием.
- **Рекомендация:** привести e2e‑коллекцию в соответствие с актуальным состоянием backend или добавить документацию, что коллекция требует свежего состояния и `PAYMENT_PROVIDER=fake`.

## Вывод

Интеграция с Т‑Кассой архитектурно сделана качественно и основные контрактные нарушения устранены. До production необходимо:

- получить рабочий доступ к sandbox для end‑to‑end валидации,
- исправить оставшиеся несоответствия в обработке ошибок и webhook,
- закрыть race‑условия и добавить фоновый дожим pending‑платежей.
