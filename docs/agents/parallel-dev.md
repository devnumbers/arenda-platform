# Параллельная разработка в ворктри: процесс, слоты портов, `.env`, compose-проекты

Изоляция локальных dev-окружений для параллельных агентских сессий в git-ворктри: правила и процесс (когда и как создавать ворктри, интеграция, разборка, troubleshooting) и технический контракт слотов.

Процесс и правило браузерных работ проверены живыми параллельными сессиями; история решений — в issue-трекере (карты #485–#490 и #512–#517).

## Правила

- **Ворктри — только по явной команде пользователя.** Агент не создаёт и не переключается в ворктри по собственной инициативе (правило репозитория в корневом `AGENTS.md`); скилл `/using-git-worktrees` — исполнитель, а не инициатор.
- **Основной чекаут свободен от фич**: живёт на свежем `dev`, из него создаются ворктри, в нём — быстрые правки, ревью и мелкие задачи; фичевые сессии работают в ворктри.
- **e2e изолирован по построению**: у каждого слота свой e2e-compose-проект и свои порты; раннер e2e одного ворктри не задевает стеки и процессы другого.

## Браузерные работы параллельных сессий

Правило «каждая сессия — свой видимый браузер»: любые репозиторные браузерные работы — живая приёмка `/ui-walkthrough`, headed-прогоны спеков, интерактивная отладка фронта в браузере — идут через per-session `playwright` MCP. Правило одинаково для одиночной и параллельной сессии: сессии не знают друг о друге, ветвления «параллелен ли я» у агента нет.

- **Механизм**: сервер объявлен в workspace-конфиге `.zcode/config.json` — файл коммитится в репо и ZCode автоподключает его в каждом чате и в каждом ворктри (механизм ZCode-only; Kimi Code берёт playwright из своего user-конфига). stdio-сервер живёт в процессе своей сессии и поднимает свой видимый браузер — установленный Google Chrome (канал `chrome`, не бандл-Chromium): headed по умолчанию, профиль в памяти (`--isolated`). Автоматические артефакты (снапшоты, консольные логи) пишутся в `.playwright-mcp/artifacts/` (gitignored) — относительный путь резолвится от cwd сессии, то есть своего ворктри; именованный скриншот `browser_take_screenshot` при голом имени пишется в cwd сессии, а не в artifacts — имя файла передавайте полным путём `.playwright-mcp/artifacts/<имя>.png`. `timeoutMs` 180000 — страховочный потолок: нормальный handshake ~0.3–3 c. Сервер запускается глобальным бинарем `playwright-mcp` (пакет `@playwright/mcp`, версия в `.zcode/config.json` не пинится — машина ставит её сама: `npm i -g @playwright/mcp@<версия>`; на dev-Маке бинарь дополнительно симлинкнут в `/opt/homebrew/bin`, чтобы GUI-контекст ZCode его видел). Ранее запуск шел через `npx -y @playwright/mcp@…` — при одновременном старте нескольких сессий параллельные npx-спавны контендируют кэш/реестр npm и иногда не укладывались в 60 с: сервер помечался упавшим на всю сессию, `mcp__playwright__*` пропадали до рестарта (эпизоды 02–08.09.2026 в логах ZCode) — поэтому npx с критического пути убран. При смене версии пакета: `npm i -g @playwright/mcp@<версия>` + симлинк не трогаетcя (указывает на bin глобальной установки).
- **`--isolated` обязателен**: без него профиль персистентный и захеширован по cwd — два чата, открытые в одном чекауте (типичный случай: два чата в корне основного), дерутся за один профиль, и второй падает по SingletonLock; персистентный профиль вдобавок протаскивает auth-состояние между приёмками. In-memory профиль снимает обе проблемы: состояние браузера живёт только до закрытия, каждая приёмка логинится заново (сид-логин — код из backend-лога; для повторных сессий — `--storage-state`, см. ниже).
- **Переопределения на сессию** (`--storage-state` для сид-логина, `--headless` при превышении лимита) — через user-конфиг ZCode (`~/.zcode/cli/config.json`, `mcp.servers.playwright`): одноимённая user-запись перекрывает workspace-запись **целиком** — скопируйте рабочие флаги (`--isolated`, `--output-dir`) и добавьте свои. Если в user-конфиге уже болтается старая запись `playwright`, workspace-конфиг молча не действует — удалить или обновить её обязан владелец машины. User-конфиг в git не попадает; коммитный workspace-конфиг остаётся нейтральным.
- **Browser Use (встроенная панель ZCode) в репозиторных задачах не используется**: все вкладки всех чатов делят одно cookie-хранилище — auth-сессии стендов на `127.0.0.1` пересекаются (наблюдавшийся «обрыв сессии»), а видимых панелей — одна на окно. Остаточная роль Browser Use — обычный веб-сёрфинг агента вне приёмки.
- **Ресурсный лимит** (замеры живых приёмок): видимое окно приёмки — это установленный Google Chrome, дерево процессов ~0,8–1 ГБ RSS (замер: 0,78 и 0,99 ГБ на живом кабинете при двух одновременных приёмках, суммарно ≈1,8 ГБ; свободная память машины не опускалась ниже 30%). На машине разработки (macOS, 18 ГБ) — не больше 2–3 одновременных видимых браузеров сверх обычной сессионной нагрузки. Если параллельных сессий больше — видимый браузер только у активной приёмки, остальные переходят в headless (`--headless` через user-конфиг, см. «Переопределения на сессию») или работают по очереди.

## Когда создавать ворктри и как запускать сессии

Ворктри нужен каждой фичевой сессии, которая идёт параллельно с другой работой (вторая фича, долгий прогон, живой walkthrough). Одиночная последовательная задача обходится основным чекаутом.

1. Основной чекаут — на свежий `dev` (`git switch dev && git pull`): ветка ворктри создаётся от его текущего HEAD.
2. `make worktree-new WT=<slug>` — создаёт `.worktrees/<slug>` и ветку `<slug>`, выделяет слот (реестр `.env` + префлайт занятости портов, см. «Реестр слотов») и генерирует `.env` ворктри; печатает факты подключения.
3. В ворктри поставить зависимости (`npm install` фронта, `go mod download`; админка — когда нужна) и прогнать бейзлайн — сторона скилла `/using-git-worktrees`; затем `make local-infra-up && make migrate-up` — свой dev-стек на портах слота.
4. Агентская сессия открывается в каталоге ворктри: свой `.env`, свои порты, свои compose-проекты — make-команды внутри ворктри действуют только на его слот. `gh` и lefthook-хуки (pre-commit, pre-push с полным `make test`) работают из ворктри без настроек.

## Интеграция

- Ветка фич создаётся от `dev` и вливается в `dev`. Push в `dev` деплоит stage (`deploy-stage.yml`), push в `main` — prod (`deploy-prod.yml`); CI гоняет полный suite только на PR — прямые push в `dev` CI не проверяет. Зелёность `dev` держит pre-push хук с полным `make test`; обход через `--no-verify` — осознанное исключение, тогда прогон делают руками до push.
- Порядок при нескольких параллельных ворктри: завершил — влей в `dev`; каждый следующий перед влитием подтягивает свежий `dev` (`git fetch origin && git rebase origin/dev` в своей ветке), повторяет быстрый прогон и вливает. Слияния — по очереди, не скопом.
- `main` — только через PR из `dev`, вручную владельцем.

## Разборка ворктри

Стеки гасят **до** `git worktree remove`: удаление каталога вместе с `.env` освобождает слот (реестр — сами `.env`), но процессы стека, осиротевшие с ppid 1 (next-server, arenda-api), переживают каталог и продолжают держать порты слота (случай: чужой хелпер держал порт слота больше часа после своей сессии).

Из корня ворктри:

1. dev-стек: `make local-infra-down` (`down -v` compose-проекта своего слота).
2. live-e2e-стек, если поднимался: `make frontend-e2e-live-down`; обычный `make frontend-e2e` убирает себя сам.
3. Сироты — слушатели портов слота, оставшиеся после шагов 1–2 (compose-порты к этому моменту уже свободны). Свой стек узнаётся по имени процесса: `next-server` (фронт), `arenda-api` (e2e-бинарник бэка), временный бинарник `go run` (`…/exe/api`, dev-бэк). Погасить по портам из `.env`:

   ```bash
   slot=$(grep -E '^AREND_SLOT=' .env | tail -1 | cut -d= -f2)
   for port in $((5440+slot)) $((8090+slot)) $((3020+slot)) $((5445+slot)) $((8095+slot)) $((3025+slot)); do
     lsof -nP -iTCP:"$port" -sTCP:LISTEN || continue   # кто держит: команда, pid
     for pid in $(lsof -ti tcp:"$port" -sTCP:LISTEN); do
       case "$(ps -o command= -p "$pid")" in
         *next-server*|*arenda-api*|*/exe/api*|*standalone/server.js*) kill "$pid" ;;
         *) echo "посторонний pid $pid на порту $port — не трогаем" ;;
       esac
     done
   done
   ```

   Посторонний слушатель на слотовом порту не гасится (случай: dadata-stub.mjs из чужой сессии) — гасить его не ваша забота; `worktree-new` при выдаче такой слот всё равно пропустил бы (префлайт).

4. Из основного чекаута: `git worktree remove .worktrees/<имя>`, затем `git branch -d <имя>`. Если каталог удалён, а стек остался — порты слота N восстанавливаются формулой (см. «Слоты и формула портов» ниже).

## Troubleshooting

- `WARNING: slot N skipped — port X (pid P) already listening` — префлайт `worktree-new` нашёл слушателя на портах кандидата: слот пропущен, выдан следующий. Вернуть слот в оборот — погасить держащие процессы (см. «Разборка», шаг 3).
- `lsof is not available — the port preflight was skipped` — префлайт не выполнился; перед e2e проверить порты слота вручную.
- `every free slot 1..9 has listening ports` — все свободные слоты держат слушатели: разобрать стеки («Разборка») и повторить.
- GIT_DIR-утечка из pre-push ворктри (ломала tools-тесты внутри `make test` и пачкала общий `.git` основного репозитория) — исправлена; pre-push из ворктри проверен зелёным.
- Отравление кэша golangci-lint между ворктри («линтер смотрит по старому проекту»): записи кэша результатов линта ключуются по содержимому пакетов, но хранят абсолютные пути дерева, которое их посчитало, а каталог кэша по умолчанию один на машину — ворктри с тем же содержимым пакета переигрывали чужие находки с чужими путями; лечилось только `golangci-lint cache clean`. Корневой Makefile пинит `GOLANGCI_LINT_CACHE` внутрь чекаута (`.golangci-lint-cache`, gitignored, сносится вместе с ворктри) — у каждого ворктри свой кэш по построению; правило действует на все make-прогоны (pre-commit и CI зовут `backend-lint` через make). Голый вызов `golangci-lint` вне make по-прежнему пишет в общий глобальный кэш — падение «на чистом коде» в таком прогоне лечится прогоном через make либо `golangci-lint cache clean`.
- Редкий флейк `npm audit` (`audit endpoint returned an error`, ETIMEDOUT) — внешний npm-сервис, не ворктри-специфика; изолированный ретрай зелёный.
- Повторная приёмка подряд: повторный запрос кода упирается в продуктовый кулдаун отправки (429; кнопка «Отправить новый код MM:SS») — дождаться таймера и запросить снова; сам логин с кодом из backend-лога у каждой сессии работает только со своим стеком.
- При первом заходе на логин на `127.0.0.1` в консоли браузера шумит `ERR_SSL_PROTOCOL_ERROR` на https-версию страницы — артефакт dev-стенда (https-апгрейд), на приёмку не влияет; одинаков в любых сессиях.
- Ресурсы: контейнер postgres слота ~65 МиБ; macOS на 18 ГБ держит 3–4 одновременные сессии — тяжёлое: prod-сборка фронта в e2e и полный `make test`. Видимый браузер приёмки (Google Chrome) — ещё ~0,8–1 ГБ RSS на сессию (замер; лимит — «Браузерные работы параллельных сессий» выше). Serena стартует по инстансу на сессию — при большом числе одновременных сессий следить за их количеством.

## Слоты и формула портов

Слот 0 — основной чекаут: исторические порты без изменений (обратная совместимость). Слоты 1–9 — ворктри; ожидаемая эксплуатация — 2–3 одновременных сессий, диапазон до 9 оставляет запас.

Формула: **порт = BASE[сервис] + OFFSET[роль] + N**, где N — номер слота; роль dev = +0, роль e2e = +5.

BASE: postgres 5440, backend 8090, frontend 3020.

| сервис        | слот 0 (main) | слот 1 | слот 2 | слот 3 |
|---------------|---------------|--------|--------|--------|
| postgres dev  | 5433          | 5441   | 5442   | 5443   |
| postgres e2e  | 5436          | 5446   | 5447   | 5448   |
| backend dev   | 8080          | 8091   | 8092   | 8093   |
| backend e2e   | 8081          | 8096   | 8097   | 8098   |
| frontend dev  | 3000          | 3021   | 3022   | 3023   |
| frontend e2e  | 3010          | 3026   | 3027   | 3028   |

- Базы тестов (postgres test, порт 5435, compose-проект `arenda-test`) и testcontainers остаются прерогативой основного чекаута: в ворктри `backend-test`/`backend-test-integration` идут через testcontainers — свой контейнер на прогон, без общих портов и имён.
- Все порты схемы < 32768 — вне эфемерных диапазонов macOS/Linux; зоны сервисов не пересекаются с существующими ручными выделениями (5433/5435/5436, 8080/8081, 3000/3010).

## Compose-проекты

Имя compose-проекта — единственный механизм изоляции контейнеров, сетей и томов: контейнеры `<project>-<service>-<index>`, named-тома `<project>_<volume>` (префикс автоматический, external-томов в схеме нет).

- dev-стек ворктри: `arenda-wt<N>`; e2e-стек ворктри: `arenda-e2e-wt<N>`.
- Make-таргеты передают имя явно флагом `-p` (высший приоритет compose), вычисляя его из `AREND_SLOT` в `.env` чекаута; слот 0 → `arenda-local` (сегодняшнее поведение основного чекаута не меняется).
- `COMPOSE_PROJECT_NAME` дублируется в per-worktree `.env`: ручные вызовы `docker compose --env-file .env -f apps/backend/docker-compose.local.yml ...` без `-p` попадают в тот же проект.
- `name: arenda-local` в `docker-compose.local.yml` остаётся — дефолт для вызовов без `.env` и `-p`.
- `local-infra-down`/`local-infra-reset` и e2e-зачистка действуют только на проект своего слота; `down -v` чужие данные не трогает.

## Per-worktree `.env`

Ворктри не наследует untracked-файлы — `.env` в нём обязан появиться заново. `worktree-new` создаёт два файла (оба игнорируются git'ом: `.gitignore` — `.env`, `.env.*`, `.worktrees/`).

1. **Корневой `.env` ворктри** — копия корневого `.env` основного чекаута (реальные ключи: DADATA, ENCRYPTION_KEY, SMTP, T-Kassa sandbox; если корневого `.env` нет — копия `.env.example` с предупреждением, что ключи-плейсхолдеры надо вписать руками) + переопределяющий блок в конце файла (последнее вхождение побеждает и в shell-сорсинге `set -a; . ./.env`, и в `--env-file` compose):

   | переменная            | значение                                                     |
   |-----------------------|--------------------------------------------------------------|
   | `AREND_SLOT`          | N                                                            |
   | `POSTGRES_PORT`       | 5440+N                                                       |
   | `DATABASE_URL`        | `postgres://arenda:arenda@localhost:5440+N/arenda?sslmode=disable` |
   | `HTTP_ADDR`           | `:8090+N`                                                    |
   | `APP_BASE_URL`        | `http://localhost:8090+N`                                    |
   | `BACKEND_URL`         | `http://localhost:8090+N`                                    |
   | `COMPOSE_PROJECT_NAME`| `arenda-wt<N>`                                               |
   | `E2E_PG_PORT`         | 5440+5+N                                                     |
   | `E2E_BACKEND_PORT`    | 8090+5+N                                                     |
   | `E2E_FRONTEND_PORT`   | 3020+5+N                                                     |
   | `E2E_COMPOSE_PROJECT` | `arenda-e2e-wt<N>`                                           |

   Всё остальное наследуется из копии без изменений (`APP_ENV`, `LOG_*`, `TRUSTED_PROXIES`, `POSTGRES_USER/PASSWORD/DB`, `MIGRATIONS_DIR`, `COOKIE_SECURE`, `EMAIL_*`, `PAYMENT_PROVIDER`, `T_KASSA_*`, `ENCRYPTION_KEY`, `OTEL_*`, `DADATA_*`, `VAPID_*`, `PHOTO_*`/S3): одинаковые имена БД, пользователя и пароля не конфликтуют — у каждого слота свой контейнер, том и порт.

2. **`apps/frontend/.env.development.local`** — `BACKEND_URL=http://localhost:8090+N`.

### Почему `BACKEND_URL` обязан быть в per-worktree env (факт репо)

`BACKEND_URL` читает только серверный код фронта — `apps/frontend/proxy.ts` и `apps/frontend/app/api/[...path]/route.ts` — из `process.env` с фолбэком `http://localhost:8080`; `NEXT_PUBLIC_` не нужен. `make frontend-dev` корневой `.env` не сорсит, а Next читает env-файлы только из каталога приложения (`apps/frontend`) — корневой `.env` репо для него невидим. Сегодня фронт работает лишь потому, что фолбэк совпадает с дефолтным портом бэка: при слотовом бэке на 8091 фронт молча остался бы на 8080. Поэтому значение передаётся файлом `apps/frontend/.env.development.local` (высший файловый приоритет в dev) и дублируется в корневом `.env` ворктри — чтобы сорсинг `.env` (make, direnv, вручную) не экспортировал устаревший `:8080` поверх файла (process env сильнее файлов). Порт dev-сервера фронтенда задаётся флагом `next dev -p` (переменную `PORT` Next из `.env`-файлов не читает — HTTP-сервер поднимается до инициализации env); `make frontend-dev` вычисляет порт из слота, слот 0 — без флага (дефолт 3000).

## Реестр слотов

Центрального файла-реестра нет — реестр это сами `.env`-файлы чекаутов (центральный файл означал бы merge-конфликты). `worktree-new` сканирует `AREND_SLOT=` в корневом `.env` и `.worktrees/*/.env`, берёт первый свободный N из 1..9, дубликаты отклоняет. Слот освобождается сам: `git worktree remove .worktrees/<имя>` удаляет каталог вместе с `.env`. Живая правда о запущенных проектах — `docker compose ls`.

Реестр знает только претензии из `.env`, но не фактическую занятость портов (случай: слот был выдан, хотя его e2e-порт бэкенда уже держал чужой процесс — раннер e2e такого ворктри убил бы его своим `free_port()`). Поэтому выдача проходит **префлайт портов**: у кандидата проверяются все шесть портов (dev+e2e, `lsof -ti tcp:<порт> -sTCP:LISTEN`); слушатели на портах — слот пропускается с предупреждением (порт и pid держателя в выводе), выдаётся следующий; заняты все свободные — отказ без создания ворктри. `lsof` недоступен — префлайт пропускается с предупреждением, слот выдаётся по реестру.

## make worktree-new

`make worktree-new WT=<имя>` — `<имя>` одновременно имя ветки и каталога (валидация: slug `[a-z0-9._-]`, ветка и каталог не существуют).

Делает (минимум — решение владельца при чартинге карты):

1. `git worktree add .worktrees/<имя> -b <имя>` от текущего HEAD.
2. Выделяет слот — реестр `.env` плюс префлайт занятости портов (см. «Реестр слотов»); свободных нет — отказ.
3. Генерирует корневой `.env` ворктри и `apps/frontend/.env.development.local` (см. «Per-worktree .env»).
4. Печатает факты подключения: слот; порты postgres/backend/frontend для dev- и e2e-ролей; `DATABASE_URL`; имена dev- и e2e-compose-проектов; команды старта с путём ворктри (`make local-infra-up && make migrate-up`, `make frontend-dev`, `make frontend-e2e`).

Не делает: зависимости (`npm install`, `go mod download`), бейзлайн-тесты, старт инфраструктуры, push — это сторона скилла `using-git-worktrees`.
