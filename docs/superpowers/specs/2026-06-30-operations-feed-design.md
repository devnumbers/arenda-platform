# Operations Feed Viewing Design

## Context

The current `/finance/operations` page mixes two different concepts:

- `Operation` - a concrete money record for a property on a specific date.
- `RecurringOperation` - a template that creates concrete operations.

This makes the screen harder to understand. It also prevents the user from reliably viewing all operations because the page defaults to the current month, uses `limit: 100`, has no load-more behavior, and ignores some URL filtering such as `property_id`.

The target behavior is a bank-style operations history: a simple feed of concrete money records.

## Goals

- Make `/finance/operations` a simple operation history feed.
- Show manual, lease-generated, and recurring-generated operations as the same kind of row.
- Stop showing recurring operation templates as feed items.
- Let the user view all operations over time.
- Preserve the existing domain model: `Operation` and `RecurringOperation` remain separate.
- Keep the implementation aligned with the existing FSD frontend structure and contract-first backend.

## Non-Goals

- Do not remove recurring operations from the product.
- Do not redesign operation creation.
- Do not add custom categories, bank import, reconciliation, partial payments, debts, export, or audit log.
- Do not make the feed manage recurring operation templates.

## Product Decisions

### Operation Feed

`/finance/operations` shows only concrete `OperationResponse` items from `GET /operations`.

The feed includes:

- manual operations;
- operations generated by leases;
- operations generated by recurring operations;
- past, current, and future operations.

Operations generated by a recurring operation appear as normal operation rows. The list does not show a "series" card, "recurring" template card, pause/resume controls, or "edit series" actions.

### Default Period

The default period is all time.

Frontend must not send `from` or `to` by default. Month, quarter, and year are quick filters, not the default view.

### Regular Operation Templates

Recurring operation templates remain a separate management concern.

This change does not add a separate recurring templates list. If the product adds template management in the future, it should be a separate screen or a detail-level action, not part of the operation history feed.

If a concrete operation has `recurring_operation_id`, the detail page may show a subtle source label such as "Created automatically" and may link to series editing. This source is not shown as a primary concept in the feed.

## User Experience

### Feed Row

Each global feed row should show:

- operation date;
- operation name;
- property name;
- category;
- signed amount;
- operation status.

The row links to `/finance/operations/{id}`.

The global feed must include the property name because owners can manage multiple properties.

### Filters

Keep the high-value filters:

- operation type: all, income, expense;
- status: all, planned, overdue, completed;
- period: all time, current month, current quarter, current year.

Remove the current "kind" filter from this feed. A filter named "Regular" would imply templates, while the feed is intentionally only concrete operations.

If `property_id` is present in the URL, the feed applies it to `GET /operations`.

### Empty States

- No properties: prompt the user to add a property before creating operations.
- No operations at all: show "No operations" with "Add operation" when editing is allowed.
- No operations for filters: show "Nothing found" and a reset-filters action.

### Loading And Errors

- Initial loading can keep using the existing finance loading state.
- Initial load errors can keep using the existing finance error state.
- Loading more must not clear already loaded rows.
- The "Show more" button has its own loading and error handling.

### Readonly And Archive Behavior

Readonly subscription state hides creation and mutation actions, but the history remains visible.

Archived properties do not remove old operations from the feed. Archived-property operations remain viewable, while mutation restrictions stay on detail/edit flows.

## Frontend Design

### Main Changes

In `widgets/operations/ui/OperationsPage.tsx`:

- remove `useRecurringOperations`;
- remove recurring template merging from `filteredItems`;
- use only `operationsData.items`;
- read `property_id` from `searchParams`;
- default `from` and `to` to `undefined`;
- use paginated loading for the feed;
- pass property names into rows or map operation property ids to display names.

In `widgets/operations/ui/OperationFilters.tsx`:

- remove `OperationKind`;
- remove "All / One-time / Recurring" chips;
- add an all-time period option;
- make reset return to all time, all statuses, and no type-specific filters.

In `widgets/operations/ui/OperationsList.tsx`:

- simplify the item type to concrete operations only;
- remove `RecurringOperationListItem` from feed rendering.

`RecurringOperationListItem` can remain for a future template-management surface, but it should not be used by `/finance/operations`.

### Component Boundaries

Keep the existing FSD direction:

- `app/` owns routes only.
- `widgets/operations` owns page assembly and feed composition.
- `features/operations/api` owns operation queries and mutations.
- `features/recurring-operations/api` remains for template management outside the feed.
- `entities/operation` owns labels, categories, dates, and money formatting.

## Backend And API Design

`GET /operations` is the correct feed source. It already returns concrete operations and supports filters including `property_id`, `from`, `to`, `limit`, and `offset`.

To make "all operations" robust, upgrade `OperationsResponse` with pagination metadata:

```yaml
OperationsResponse:
  type: object
  required: [items, limit, offset, has_more]
  properties:
    items:
      type: array
      items:
        $ref: '#/components/schemas/OperationResponse'
    limit:
      type: integer
    offset:
      type: integer
    has_more:
      type: boolean
    next_offset:
      type: integer
      nullable: true
```

Handler behavior:

- default `limit` stays conservative;
- maximum `limit` is bounded, recommended `100`;
- `offset` is non-negative;
- repository fetches `limit + 1` rows;
- response returns at most `limit` rows;
- `has_more` is true when an extra row exists;
- `next_offset = offset + len(items)` when `has_more` is true.

This avoids a costly count query and gives the frontend an explicit load-more signal.

## PostgreSQL Design

The current SQL already orders by:

```sql
ORDER BY operation_date DESC, id DESC
```

For the improved feed, add a partial index matching the owner feed sort:

```sql
CREATE INDEX IF NOT EXISTS idx_operations_owner_operation_date_id_not_deleted
  ON operations(owner_id, operation_date DESC, id DESC)
  WHERE deleted_at IS NULL;
```

This supports the global owner feed and keeps deleted operations out of the index.

Offset pagination is acceptable for MVP. If operation volume grows substantially, switch to keyset pagination using `(operation_date, id)` as the cursor.

## Documentation Impact

No glossary change is required. The existing glossary already distinguishes:

- operation as a concrete money record;
- recurring operation as a template.

Implementation should update `CHANGELOG.md` under the current date because this changes user-visible operation browsing.

No ADR is required. This is a reversible UI/API refinement and follows existing domain and architecture decisions.

## Testing

Frontend checks:

- `/finance/operations` does not call `/recurring-operations`.
- operations with `recurring_operation_id` render as ordinary feed rows.
- default feed request omits `from` and `to`.
- `property_id` in the URL is passed to the operations query.
- "Show more" appends rows and does not clear the current list.
- empty states distinguish no properties, no operations, and no filtered results.

Backend checks:

- `GET /operations` returns pagination metadata.
- `has_more` is true when more rows exist and false otherwise.
- `limit` is bounded and `offset` is normalized or rejected consistently.
- property filtering still works.
- generated operation code and frontend API types are regenerated from OpenAPI.

Verification commands for implementation:

```bash
make backend-lint
cd apps/backend && go test ./...
cd apps/backend && go vet ./...
cd apps/frontend && npm run lint
cd apps/frontend && npm run build
```

## Open Questions

None for the feed design. The user confirmed Variant A:

`/finance/operations` is only a concrete operations feed. Recurring operation templates are not shown in the feed, while operations generated by those templates are shown as normal operations.
