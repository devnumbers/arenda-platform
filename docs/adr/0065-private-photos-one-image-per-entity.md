# ADR 0065: Приватные фото — одна картинка на сущность, стриминг и загрузка через бэкенд

Фото объекта, контакта и профиля — максимум одна картинка на сущность, хранится в приватном бакете Рег.ру Object Storage; ни выдача, ни загрузка не идут мимо бэкенда: браузер отдаёт файл multipart-запросом бэкенду и получает его обратно стримом с того же бэкенда под cookie-сессией. Публичные перманентные URL (ADR 0005, canned-ACL `public-read`) уходят: бакет остаётся закрытым по умолчанию, а приватность личных фото (квартира, лицо, телефонная книга) не совместима с «угадай URL».

## Status

Accepted. Частично заменяет ADR 0005: порт хранилища и Рег.ру S3 как провайдер остаются, публичная часть (перманентные публичные URL) — нет. Аменд 2026-10-20: версионная выдача (`?v=`), disk-backed file-провайдер дева, ретрай загрузки на клиенте (см. Decision). Аменд 2026-10-23: SW-кеш публичной статики как слой выдачи — иконки пустых состояний (#1593, см. Decision). Аменд 2026-10-23: серверный кеш и CDN для фото рассмотрены ресерчем #1589 — не делаем, триггер возврата к LRU — тикет #1606 (#1596, см. Decision). Аменд 2026-10-26: blur-кадр — второй производный артефакт фото, колонка рядом с `photo_key`, доставка base64 в DTO (#1594, #1603, см. Decision).

## Context

Старый фото-пайплайн объекта (ADR 0005) построен вокруг публичной выдачи: S3-адаптер ставил `ObjectCannedACLPublicRead`, `PhotoStorage.Upload` возвращал перманентный URL, и до 10 фото объекта жили в таблице `property_photos`. Фича так и не дошла до UI: на stage/prod всегда стоял `PHOTO_STORAGE_PROVIDER=fake`, фронтовые хуки загрузки остались без консюмеров, карточки рисуют глифы-плейсхолдеры (карта #1217, тикет #1226). Контракт сгнил сам по себе: Рег.ру не документирует canned-ACL (снятие решения — research #1218), а «публичное фото» противоречит требованиям карты — фото недвижимости с GPS-меткой съёмки и аватар профиля не должны быть доступны без авторизации.

Карта #1217 добавляет фото контактов (ADR 0054) и профиля; решения по развилкам приняты владельцем на grilling #1220 по рекомендациям research #1218/#1219.

## Decision

**Одна картинка на сущность.** У объекта, контакта и профиля максимум одно фото. Схема: колонки `photo_key TEXT NULL` + `photo_content_type TEXT NULL` на `properties` / `contacts` / `users` — S3-ключ и фактический content-type, определённый по магическим байтам. Таблица `property_photos` и весь старый контракт (эндпоинты `uploadPropertyPhoto`/`deletePropertyPhoto`, схема `PropertyPhoto`, массив `photos[]` в DTO) сносятся: строк в таблице нет, данных не переносится (прецедент ADR 0046/0054).

**Порт хранилища — стриминговый.** `PhotoStorage` переходит на `Put(ctx, key, reader, contentType, size)` / `Open(ctx, key) → (ReadCloser, size, contentType)` / `Delete(ctx, key)` — ни один метод не возвращает URL. S3-адаптер ходит в `https://s3.regru.cloud` path-style (`BaseEndpoint` + `UsePathStyle=true`) без canned-ACL; ключи плоские, `photos/<uuid>.<ext>` — UUID без PII, ключ живёт в колонке сущности. Fake-адаптер (память) — dev и тесты, MinIO в докер-композе по-прежнему нет (ADR 0005 в этой части действует).

**Выдача — стриминг через бэкенд.** `GET /api/properties/{id}/photo`, `GET /api/contacts/{id}/photo`, `GET /api/me/photo` — cookie-auth, бэкенд стримит объект из S3 с `Cache-Control: private, max-age=300` и `ETag` = хеш ключа: замена фото = новый UUID-ключ = новый ETag, 304 отдаётся без похода в S3. Presigned GET отклонены: с ними браузер минует авторизацию бэкенда, а срок жизни ссылки либо мешает кэшу, либо оставляет окно утечки. *(Кэш-политика пересмотрена амендом 2026-10-20 — immutable по версионному URL, см. «Контракт DTO».)*

**Загрузка — multipart через бэкенд.** `POST .../photo` (поле `file`) + `DELETE .../photo` на те же три сущности. Валидация до записи в S3: размер ≤ 5 MiB; белый список `image/jpeg|png|webp` по магическим байтам (`http.DetectContentType`, заголовку клиента не верим; SVG попадает в отказ самим списком); лимит мегапикселей через `image.DecodeConfig` до полного декодирования (pixel-bomb); EXIF/GPS срезаны до сохранения — jpeg/png ре-энкодом (заодно ломает встроенные payload'ы, OWASP), webp — выкидыванием `EXIF`/`XMP` RIFF-чанков без декодирования. Замена = новый ключ + best-effort удаление старого объекта; сироты логируются.

**Доступ.** Фото объекта — матрица ADR 0028 (просмотр — CanView, загрузка/удаление — CanEdit, редактирование объекта); фото контакта — правила ADR 0054 (свой без объекта — всегда, привязанный — по роли на связанном объекте, privacy-404); фото профиля — сам пользователь и, с амендом 2026-10-09 (#1286, «показ участникам» — то самое отложенное решение), каждый, с кем пользователя связывает хотя бы один объект, читаемый обеими сторонами (ADR 0028 derived read, симметрично: владелец↔участник и со-участники). Нет связи и нет фото — один и тот же 404: существование фото не раскрывается; сбой проверки связи — fail-closed 500. Отзыв доступа закрывает стрим (404), клиент откатывается на заглушку. Выдача чужого фото — `GET /api/users/{userId}/photo`, тот же контракт заголовков (private max-age, ETag=key hash), и путь `/api/users/{id}/photo` в производных payload'ах (участники, списки членов объекта, актёры уведомлений/истории).

**Контракт DTO.** Наружу — `photoUrl`: относительный same-origin путь `/api/.../photo` (null, когда фото нет); CSP фронтенда не меняется (`img-src 'self' data:` достаточно). Аменд 2026-10-09 (инцидент stage: фото 404 после выката): изначально путь писался `/api/v1/...` и работал только через BFF-прокси фронта в dev — Caddy на stage/prod снимает с `/api/*` только префикс `/api`. По решению владельца v1-форма не поддерживается: `photoUrl` отдаётся как `/api` + путь спеки OpenAPI — та же форма, которой клиент зовёт остальные эндпоинты; BFF-срезание `v1` снесено.

**Аменд 2026-10-21 (миниатюры; усиление «холодная перезагрузка = секунды глифа на мобильной сети»):** аватары рисуются в кругах ≤96 CSS px, а хранился и стримился полный кадр (3024×4032, ~1.4 МБ) — каждый холодный вход тянет мегабайты ×2 (шапка + hero). Теперь `Process` строит **thumb ≤320px по длинной стороне** (покрывает 96px на retina ×3), всегда непрозрачный jpeg (пиксели компонируются на белый — фон кругов), area-даунскейл собственным кодом без новых зависимостей (принцип «image-библиотек в проекте нет»); thumb живёт производным ключом `<uuid>_t.<ext>` рядом с основным — одна судьба на замену/удаление/самолечение. Стрим принимает `?size=thumb`: ETag миниатюры выводится из ключа storage-free (байты детерминированы основным объектом — 304 не лжёт), загрузки без thumb (старые объекты, в пределах 320px, webp — декодера в тулчейне нет) честно отдают полный объект, причём первый же такой запрос **лениво материализует** thumb и сохраняет его. Клиентский `CirclePhoto` (единственный рендер фото — круги) запрашивает `?size=thumb` всегда для производных URL выдачи (аменд 2026-10-23, #1607: непроизводные URL — data:/blob: превью летящей загрузки — суффикса не получают, байты уже на руках, а `data:…?size=thumb` — невалидный `src`, net::ERR_INVALID_URL); крупный просмотр, если появится, ходит без параметра. Честный fallback (webp, ≤320px, старые объекты) отдаёт полный объект под ETag основного ключа — для этих клиентов storage-free 304 по thumb-ETag недостижим, их ревалидация ходит в бэкенд обычным путём; осознанная цена за то, что 304 никогда не лжёт о байтах.

**Аменд 2026-10-26 (blur-кадр — второй производный артефакт фото; решение #1594, тикет #1603):** thumb закрыл байты аватара, но первый кадр всё ещё ждёт сеть — круг рисуется заглушкой, пока thumb-стрим не доедет. Теперь `Process` строит рядом с thumb **blur-кадр: jpeg длинной стороной 16px, q≈50** (та же area-даунскейл-математика, тот же композит на белый, непрозрачный; ~0.5–1 КБ), и доставляет его **готовым base64 в DTO** — клиент красит кадр поверх заглушки мгновенно, к первому кадру. Развилки:

- **Хранение — колонка, не storage-объект:** `photo_blur TEXT NULL` рядом с `photo_key` на `properties`/`contacts`/`users` (миграция 000164). Списки и `/me` читают байты из уже выбранной строки — ноль походов в S3 на сериализацию; производный объект в storage отвергнут (лишний `GetObject` на каждую сборку DTO).
- **Отдельный `?size=blur`-запрос отвергнут:** лишний раунд-трип на каждый круг, при полном охвате домножается на списки; blur нужен мгновенно к первому кадру.
- **Генерация — аплоад + ленивая материализация.** Аплоад несёт кадр из тех же уже-декодированных пикселей, что и thumb (`Processed.Blur`); сбой кадра не валит аплоад (канон «the thumbnail rides with the upload»). Существующие фото материализуют кадр лениво **на выдаче фото/thumb**: ветки `ServeOrMaterializeThumb` и полная выдача за тот же декод считают кадр и best-effort пишут колонку («next request retries» по образцу thumb; `/me` на горячем пути — только чтение колонки, писать её на путях DTO не нужно). NULL в колонке — штатное состояние: webp не декодируется (честная деградация), кадр в пределах 16px сам себе blur, до материализации колонка пуста. Условная запись `...BlurIfKey` ключуется по всё ещё объявленному `photo_key` — конкурентная замена фото побеждает, свежее фото несёт свой кадр. Ветке попадания в уже сохранённый thumb кадр не «бесплатен»: пока колонка NULL, выдача читает и декодирует главный объект ради кадра — однократная цена на фото когорты до-blur. Сама условная запись бампит `updated_at` строки (общий триггер): однократное всплытие ряда в `updated_at`-сортировках после первого показа фото — осознанная цена, точечный обход триггера отвергнут как инвазия в общий механизм 000001.
- **Доставка — base64-поле во всех продуктовых DTO с фото-путями** (`photoBlur`/`photo_blur`/`owner_photo_blur`/`actor_photo_blur` по именованию схемы): MeResponse, PropertyResponse (вкл. `owner_photo_blur` в PropertyAccessContext), ContactResponse, PaymentObjectItem, PropertyAccessMemberResponse, ParticipantResponse, ParticipantPropertyResponse, HistoryItem (`actor_photo_blur`), HistoryParticipant, HistoryObject; кадры уведомлений несут `photo_blur` в карточках (`EntityRef`). SQL-пейлоады (history, notifications, participants, payments_global) читают колонку из уже выбранной строки. NULL-колонка → null-поле: контракт nullable, как у `photoUrl`.
- **Приватность не меняется:** blur едет в тех же authed DTO, что и `photoUrl` (кадр — те же пиксели, что и thumb, по той же проверке доступа).

**Аменд 2026-10-23 (SW-кеш публичной статики как слой выдачи; иконки пустых состояний, #1593):** иллюстрации пустых состояний (`public/images/**` — полноэкранные `EmptyState`, секционные пустые объекта, хаб и каталог платежей, иконки категорий уведомлений; также `public/icons/**`) — публичная статика, одинаковая для любого аккаунта. HTTP-кеш уже иммутабелен на год (`next.config.ts`, канон «новая версия ассета — новое имя файла»), но браузерный кеш не закрывает три сценария: первый заход на устройство, вытеснение (Safari ITP чистит хранилища через ~7 дней неактивности, дисковое давление Chrome), офлайн в установленном PWA. Решение: `sw.js` (тот же сервис-воркер ADR 0032) получает ветку **runtime cache-first** для этой статики — по фактическим URL, без precache-списка: иконки рендерятся через `next/image`, выбор `w`-варианта зависит от DPR/зума устройства, кешировать заранее нечего. Матчинг консервативный: прямые `/images/*` и `/icons/*` плюс ответы `/_next/image`, чей параметр `url` начинается с `/images/` или `/icons/` — `remotePatterns` пуст, внешних картинок через оптимизатор нет, но явное правило самодокументируется и не заденет будущую динамику. Хранилище — отдельный кеш `static-assets-v1`, вне будущего приватного фото-кеша; без квот и eviction (сет конечен, реально используемых вариантов на устройстве десятки — сотни КБ). **При логауте статический кеш не чистится** — при логауте чистится только приватный фото-кеш (направление cache-first для thumb одобрено владельцем 23.10; детали — открытые подвопросы #1593: состав thumb/all, детект логаута, версии/квоты, приватный режим Safari). Инвариант свежести общий с HTTP-заголовками: новая версия ассета — новое имя файла; смена стратегии оптимизатора — бамп версии SW-кеша (ADR 0032).

**Аменд 2026-10-23 (серверный кеш и CDN — рассмотрены ресерчем #1589, решено не делать; #1596):** холодный показ thumb (Go-хендлер → строка Postgres → `GetObject` из Рег.ру → стрим; повторные показы закрыты immutable-кешем браузера и SW-кешем) — осознанная цена и дальше. **CDN поверх cookie-authed origin отклонён трижды:** деньгами (пакет 800 ГБ Selectel ≈ 27 млн холодных thumb-показов/мес — на порядки выше масштаба продукта), латентностью (хост и аудитория в одном регионе РФ — edge-узлы выигрыша RTT не дают; нативного CDN у Рег.ру Object Storage нет) и приватностью (российские CDN — Selectel/Яндекс/VK — умеют только bearer-подписи: семейство слабее уже отклонённых пресайнов, cookie к краю не пробрасывается; Cloudflare троттлится в РФ с 06.2025). **In-memory LRU thumb-кеш в Go — не сейчас, по измеримому триггеру** (тикет #1606): p95 фактической thumb-выдачи > 200 мс на 7-дневном окне в Uptrace (порог 200 — решение владельца из диапазона ресерча 200–300; атрибут `photo.size` на спан стрима) → декоратор над `PhotoStorage.Open` — кеш байт thumb по производному ключу строго после проверки доступа, count-лимит ~10 тыс. записей ≈ 300 МБ; кешировать дескриптор = кешировать решение авторизации — не делать никогда (параметры — #1589). Протокол чист без действий: `Set-Cookie` только на login/logout, `Vary` не ставится, jpeg Caddy не сжимает, Early Hints до SPA-`<img>` не доходит, keep-alive к Рег.ру реюзается AWS SDK по умолчанию.

**Аменд 2026-10-20 (версионная выдача; симптом «перезагрузишь страницу несколько раз — заглушка, хотя фото есть»):**

- **`photoUrl` несёт версию ключа: `/api/.../photo?v=<sha256(ключа)[:16]>`.** Версию печёт бэкенд в каждом DTO — `/me`, объект, контакт и все производные payload'ы (участники, члены объекта, актёры истории/уведомлений/глобальных платежей; SQL собирает её тем же `sha256`, тесты пинуют совпадение с Go). Замена/удаление фото = новый UUID-ключ = новый URL, поэтому выдача отвечает `Cache-Control: private, max-age=31536000, immutable` (`httpsupport.PhotoCacheControl`): браузер держит приватную копию вечно и не ходит в бэк за байтами, а новое фото — просто другой URL. ETag/304 остаются как валидатор. До аменда кэш жил 300 секунд, а клиентский бастер `?v=N` был сессионным (сбрасывался перезагрузкой страницы, шапка его не применяла) — после замены фото и перезагрузки браузер до 5 минут показывал прежние байты.
- **`PHOTO_STORAGE_PROVIDER=file` — disk-backed дев-хранилище** (`PHOTO_STORAGE_FILE_DIR`, по умолчанию `.photo-storage/`). In-memory fake терял все объекты с каждым рестартом бэкенда, пока ключи в БД продолжали обещать фото: стрим 404 → самолечение стирало ключ → заглушки во всём UI после каждого локального рестарта/пересборки (воспроизведено 20.10: рестарт 19:55 → 404+хил 19:59 → перезаливка 20:01). File-провайдер переживает рестарт и убирает сам класс висячих ключей в деве; fake остаётся для тестов; в строгих окружениях по-прежнему s3 (WARN при не-s3 сохраняется).
- **Клиентский ретрай загрузки.** `CirclePhoto` на первую ошибку `<img>` перезапрашивает байты с нонсом (`&r=N`): транзиентный сбой (обрыв сети, 429, оборванный стрим) больше не прячет живое фото навсегда; ошибка после ретрая — честный глиф-фолбэк (#1275). Сессионный бастер `?v=N` и его реестр в react-query снесены — URL строит только бэкенд.

## Consequences

- (+) Бакет остаётся закрытым по умолчанию: доступ к каждому байту проходит авторизацию бэкенда, отозвать доступ = отозвать сессию.
- (+) EXIF/GPS не доходят до хранилища вовсе — утечка геолокации исключена на входе, а не фильтрацией на выдаче.
- (+) Снос `property_photos` упрощает модель: производные аватары (лента истории, платёжные списки) читают `photo_key` прямо со строки объекта.
- (−) Каждый показ фото — поход в бэкенд и S3: трафик и нагрузка на бэкенд растут против CDN-сценария; при текущих объёмах (одна картинка на сущность, private max-age=300) это осознанная цена.
- (−) Холодный показ (Go → Postgres → GET из Рег.ру → стрим) остаётся ценой и при immutable-выдаче: серверный LRU thumb-кеш и CDN рассмотрены ресерчем #1589 и решены «не делаем» (#1596); триггер возврата к LRU — p95 фактической thumb-выдачи > 200 мс на 7-дневном окне в Uptrace (тикет #1606).
- (−) Ре-энкод jpeg/png — лёгкая генерационная потеря качества; webp проходит без перекодирования.
- (~) Задача бакета и ключей Рег.ру — тикет #1222 (владелец); локальная разработка и приёмка экранов — на fake-хранилище, stage-проверка приватной выдачи — после #1222.
- (+) SW-кеш статики: иллюстрации пустых состояний отрисованы офлайн и после вытеснения HTTP-кеша; повторные показы не ходят в сеть даже в холодных сценариях (первый заход, вытеснение, ITP).
- (~) Запрос под SW-хендлером минует memory-cache браузера: в рамках сессии повторные показы статики обслуживает Cache Storage — выигрыш не в тёплых онлайн-заходах (их закрывал и immutable HTTP-кеш), а в холодных и офлайн.
- (~) SW-кеш не убирает видимый remount-цикл экранов (скелетон → контент → иконка): вспышку повторного показа гасит render-слой (предекод-реестр статических иллюстраций, отдельный тикет), скелетон при возврате назад — data-слой react-query (отдельный тикет); оба слоя в сеть не лезут.
