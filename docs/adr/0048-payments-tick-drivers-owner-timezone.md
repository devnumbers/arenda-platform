# ADR 0048: тик платежей — драйверы и часовой пояс собственника

## Status

Accepted

## Context

Тик материализации — идемпотентный прогон «правила + паузы + "сегодня" → операции». Решение №1 карты wayfinder #443 (чартинг-сессия 2026-08-25, ревизия гриллингом того же дня) фиксирует драйверы: ежечасный фоновый воркер `platform/scheduler` плюс прогон внутри каждой мутации контекста; чистые GET не пишут, страховка от молчащего воркера — алертинг, а не компенсация при чтении. Решение №2 добавляет: «сегодня» — в часовом поясе владельца данных, дефолт Europe/Moscow. Этот ADR фиксирует детали часового пояса (тикет #445): источник TZ, вычисление даты, обход зон воркером, семантика смены пояса.

Хранение TZ в платформе уже есть: `users.timezone TEXT NOT NULL DEFAULT 'Europe/Moscow'` (миграция 000088), IANA-валидация через `time.LoadLocation` (`identity/domain/timezone.go`), редактирование в профиле (`PATCH /me`).

Контраст с ADR 0040 (ежедневный UTC-якорь прежнего overdue-скана): там кандидатство просрочки было датой по серверным UTC-часам, и пояс влиял лишь на стенное время доставки напоминаний — единый UTC-якорь был достаточен. Здесь «сегодня» — сама доменная граница: просрочка, долг и автоплатёж наступают по дате собственника, поэтому дата считается в его поясе и UTC-якорь не подходит в принципе.

## Decision

1. **Источник TZ — существующая `users.timezone` собственника объекта** (`properties.owner_id → users`). Ни снапшота пояса на платеже (устареет при смене), ни новых колонок. Колонка NOT NULL с дефолтом: «не выставил» неотличим от «выбрал Москву» — авто-детекция пояса по браузеру, если появится, потребует отдельного решения и сюда не входит.
2. **«Сегодня» вычисляется в Go**: `clock.Now().In(time.LoadLocation(tz))` → дата `YYYY-MM-DD`, в SQL уходит параметром; `AT TIME ZONE` в Postgres не используется. Вся арифметика дат (генерация вхождений, прижатие 31-го) остаётся date-строчной в домене, как в прототипе.
3. **Воркер обходит зоны без состояния**: каждый час выбираются различающиеся пояса собственников с активными платежами, для каждого пояса вычисляется свой `today`, материализуются все владельцы зоны. Идемпотентность делает прогоны между полуночами no-op (вставки конфликтуются по дедуп-ключу). Алерт «тик не прогонялся» — heartbeat успешного прогона воркера; порог — операционная настройка наблюдения.
4. **Мутации считают «сегодня» по поясу собственника объекта** в момент мутации, а не по поясу действующего пользователя: граница суток едина для всего аккаунта — участник с Full Access из другого пояса работает в сутках собственника.
5. **Смена пояса собственником не переписывает историю и ничего не перепланирует** — сдвигаются только будущие границы суток. Переезд на запад может локально откатить «сегодня» на день назад: материализация просто ничего нового не создаёт, сходимость сохраняется. Переезд на восток — первый прогон материализует на день больше, что и требовалось. `paid`-операции тик не трогает никогда.

## Considered Options

- **Вычисление даты в Postgres (`(now() AT TIME ZONE tz)::date`)** — отклонено: логика в домене при тонком SQL (конвенция репо), даты тестируются без БД, один источник даты для домена и запросов.
- **Per-owner состояние тика** (таблица `owner_id → last_date`, работа только для «перевернувшихся» суток) — отклонено на старте: новая таблица и запись в каждом прогоне ради экономии на no-op-прогонах; идемпотентность позволяет добавить такое состояние позже без ломки.
- **Полуночный fan-out** (тип по расписанию локальной полуночи каждой зоны) — отклонено картой #443 в пользу ежечасного прогона: десяток расписаний вместо одного, а ежечасный прогон даёт автоматический догон после пропущенного часа.
- **Единый UTC-якорь по образцу ADR 0040** — отклонено: годится для времени доставки напоминаний, но не для доменной границы «сегодня».

## Consequences

- Словарь: `payments/CONTEXT.md` (Тик — «сегодня» по поясу собственника), `identity/CONTEXT.md` (Часовой пояс перепривязан от удалённого Rental-контекста к Payments; смена пояса больше ничего не перепланирует).
- Мутации контекста payments всегда разрешают собственника объекта (`property → owner`) до прогона тика, даже когда действует участник с Full Access.
- Пропущенный час воркера покрывается следующим прогоном и тиком внутри мутаций; наблюдение — heartbeat воркера в Uptrace.
- Реализация драйверов (порт воркера, регистрация в `platform/scheduler`, метрика heartbeat) — спека-фаза усилия.
