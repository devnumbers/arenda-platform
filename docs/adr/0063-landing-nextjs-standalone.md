# ADR 0063: Лендинг — отдельное Next.js-приложение в apps/landing

Старый лендинг — Figma Make-экспорт (Vite SPA, раздаётся nginx-контейнером) — перестраивается с нуля: публичная SEO-страница по макетам Figma 1:1, с серверным рендерингом и tariff-aware точками рендера — хедер отражает только факт входа («Войти»/«Профиль»), тариф показывает секция «Тарифы» кнопкой «Ваш тариф»; оба читают `/me` через React `cache`. Решили: `apps/landing` остаётся **отдельным приложением** и переписывается на Next.js (версия синхронна кабинету — 16.3.7), сохраняя деплой-идентичность — образ `landing`, порты 13002/23002, сервис в compose и Caddy-исключение на публичном домене. Авторизация/тариф — серверный fetch `GET /me` с прокинутой сессионной cookie по внутренней сети compose (`BACKEND_URL: http://backend:8080`), дырка хедера под `<Suspense>`, HTML рендерится на каждый запрос.

## Considered Options

- **Влить лендинг в кабинет** (маршрут `/` во `apps/frontend`): отклонено. Service worker кабинета живёт со scope `/` и **изолирует `/`** — в standalone-режиме установленного PWA корень принудительно ведёт на `/properties` (канон PWA, ADR 0032); CSP и security-заголовки `/:path*` кабинета навешивались бы на лендинг; любой выкат маркетинговой страницы стал бы выкатом всего кабинета (пересборка, инвалидация, SW-цикл у пользователей). SEO-страница оказалась бы в одном рантайме с авторизационным приложением.
- **Отдельное Next.js-приложение (выбрано)**: нулевые изменения кабинетного PWA/proxy/CSP, независимый деплой-цикл маркетинговой поверхности, чистый SSG/SSR-контракт для поисковиков. Цена — обновление деплой-контракта лендинга (см. Consequences) и собственный, компактный инстанс Next.

## Consequences

- Caddy-матчер `@landing` (`deploy/caddy/rentlee.caddy`) переходит с Vite-путей (`/assets/*`, `/landing-fonts/*`) на Next-пути (`/fonts/*`, `/icon.png` и точные метадата-маршруты `/opengraph-image`, `/apple-icon.png`, `/favicon.ico`); smoke-проверки `_deploy.yml` обновлены под маркер `id="landing-root"`, immutable `/_next/static/*` и 200 на og:image. Первоначальная редакция включала в матчер и весь `/_next/*` — на stage это сломало кабинет (30.09): кабинет — тоже Next.js, и его бандлы, уходя в лендинг-контейнер, отдавали 404 при зелёном смоуке (смоук не проверял кабинетные чанки). Исправлено по контракту карты #649 («`/_next/*` — фронту catch-all'ом»): кабинет снова владеет `/_next/*`, а лендинг собран с `assetPrefix /landing` (env `LANDING_ASSET_PREFIX` в Dockerfile, снимает Caddy через `uri strip_prefix`) — его ассеты публикуются как `/landing/_next/*` (image-оптимизатор префикса не получает — серверный рендер Next всегда пишет `/_next/image` — и разводится по параметру `url`); оба `/_next/*` разведены по пути. Смоук дополнен проверкой кабинетного чанка.
- Dockerfile лендинга — node standalone runtime (как у фронта) вместо nginx; healthcheck `/healthz` — route handler; `PORT=8080`.
- Сервису landing в compose (stage+prod) добавлен `environment: BACKEND_URL: http://backend:8080` — compose-уровень, дрейф-чек ENV_FILE не задевается.
- HTML лендинга с авторизованным хедером рендерится на каждый запрос (динамическая дырка хедера) — CDN-кэш HTML не шарится; осознанно: трафик лендинга мал, остальная страница и ассеты кэшируются как обычно.
- `robots.txt` и `sitemap.xml` остаются статикой `public/` лендинга (контент не меняется); при изменении кабинетных роутов синхронизируется вручную, как и раньше.
