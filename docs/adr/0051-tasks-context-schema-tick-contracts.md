# ADR 0051: контекст «Tasks» — схема БД, тик и контракты первого среза

## Status

Accepted (аменде 2026-10-01: «Удалить все выполненные» чистит и живые правила через пер-правильный горизонт истории, миграция `000146_task_rules_history_horizon` — §3, §2)

## Context

Доменная модель задач согласована словарём (#494) и контрактом схемы и тика (#496): правило порождает вхождения-задачи по образцу Payments (ADR 0047–0049) без пауз, без денег и без долга; просрочка и «без срока» вычисляемые; удаление правила жёсткое, журнал выполнений остаётся. Экранная карта #497 добавила операцию «Удалить все выполненные» и отказалась от UI-удаления активных задач. Этот ADR фиксирует последний слой решений перед реализацией (#498): как модель ложится на PostgreSQL и OpenAPI по правилам репозитория (ADR 0003 sqlc/pgx, ADR 0019 UUIDv7 app-side, ADR 0028 actor/scope, ADR 0033 UoW).

## Decision

### 1. Схема (миграция `000118_tasks_context`)

Две таблицы; канонический DDL — резолюция #496, миграция повторяет его дословно плюс конвенционные триггеры `set_updated_at` (обновление `updated_at` на записи, как у всех таблиц контекстов):

- `task_rules` — правило: `title`, `comment`, `due_date` (якорь, опционален), `due_time TIME` (HH:MM, требует дату), `repeat TEXT` — enum `once/daily/weekly/monthly/yearly` (параметров повтора в v1 нет — JSONB-прецедент Payments отклонён). CHECK'и: `task_rules_time_requires_date` (время требует дату), `task_rules_repeat_needs_anchor` (повтор ≠ once требует якорь — недатированным бывает только разовое правило). Аменд 2026-10-01 добавляет `history_before DATE` (миграция `000146`) — пер-правильный горизонт истории, см. §3.
- `tasks` — задача = вхождение: снимок `title`/`comment`/`due_date`/`due_time` правила на момент материализации, `rule_id REFERENCES task_rules ON DELETE SET NULL` (журнал выполнений переживает удаление правила), `completed_date DATE` — NULL = активная, дата = факт выполнения. Статус-колонки и статус-надгробий нет: просрочка и «без срока» вычисляемые, дедупликацию материализации держат сами строки задач.
- Дедуп-индексы: частично уникальный `(rule_id, due_date)` для датированных задач (выполненная задача тоже держит ключ — тик не перематериализует дату) и `(rule_id)` по недатированным; плюс индексы под списки объекта и owner-скоуп (ADR 0028).

Просрочка на чтении: для задачи со временем граница — момент срока с точностью до минут, включительно (15:13 → просрочена в 15:13); для даты без времени — конец суток (следующая полночь); вычисляется сервером в поясе собственника (ADR 0048), секунды усекаются.

### 2. Домен и тик

- `domain` — чистые функции: перечисление вхождений повтора (daily +1 день; weekly +7 дней того же дня недели; monthly — день якоря каждого месяца с прижатием к последнему дню: 31-е → 28/29; yearly — с прижатием 29.02 → 28.02; каждый месяц/год перестраивается от якоря без дрейфа), время суток `HH:MM` как минуты от полуночи, план тика. Никаких часов и I/O; «сегодня» и текущий момент приходят параметрами (CODING_STANDARDS: `clock.Clock`, даты — UTC-полночь).
- План тика: материализовать все наступившие (дата ≤ сегодня) без задачи — от max(якоря, горизонта истории правила, аменд 2026-10-01); держать ровно одно будущее (первое вхождение после сегодня без задачи — вставить, с невыполненной — стоит; выполненная вперёд срока пропускается, как в Payments; подавленные горизонтом вхождения без строки пропускаются, стоящая строка на подавленной дате остаётся — горизонт подавляет создание, не существующие строки); недатированное правило материализует свою единственную задачу при создании, поднятый горизонт держит его в спячке (amenд 2026-10-01).
- `application` — прогон тика per-owner внутри `UoW` (ADR 0033): блокировка, снапшот правил и дедуп-ключей, применение планов. Сериализация — `SELECT … FOR UPDATE` строки property (прецедент ADR 0025 §5, ADR 0049 §3): каждая мутация и каждый прогон тика; дедуп-индексы страхуют независимо от блокировки.
- **Драйверы**: свой ежечасный воркер в `platform/scheduler` со своим advisory-lock-пространством (`0xB114`; payments — `0xB113`), обход зон по ADR 0048 (DISTINCT TZ собственников с правилами на активных/в maintenance объектах), per-owner UoW, heartbeat `tasks.tick.last_success`. Тот же прогон — внутри каждой мутации контекста в своей транзакции (создание/правка/удаление правила, выполнение/отмена выполнения); чистые чтения не тикают. Интервал — доменное решение (час), не конфигурируется окружением — как у payments.
- **Задним числом нельзя**: срок при создании и правке — сегодня или позже пояса собственника, иначе 400. Пропущенная обязанность записывается задачей на сегодня. Правка правила не трогает уже созданные задачи: снимки заморожены; инвалидация правки сносит невыполненные «ещё не наступившие» (недатированную и строго будущие), тик ставит единственное будущее заново со свежим снимком.

### 3. Удаление правила и «Удалить все выполненные»

- Удаление правила — жёсткое, без параметров (аналога `keep_overdue` нет): все его невыполненные задачи сносятся физически, строка правила удаляется, выполненные остаются в журнале с `rule_id = NULL` и живыми снимками. Надгробие не нужно: правило исчезло — тику нечего материализовать. Аудит: `task_rule.deleted` (ADR 0020, in-tx fail-safe).
- **«Удалить все выполненные» (#497, аменд 2026-10-01)**: операция сносит **все** выполненные задачи объекта навсегда — и журнал удалённых правил (`rule_id IS NULL`), и выполненные задачи живых правил; правила и невыполненные задачи не трогаются. Дедуп-долю снесённых строк перенимает **пер-правильный горизонт истории** (миграция `000146_task_rules_history_horizon`, колонка `task_rules.history_before DATE`, NULL = не поднимался): операция до удаления поднимает каждой живой правил-потеряшке горизонт до `max(дата срока снесённых) + 1`; тик не материализует вхождения раньше горизонта — ни долгом, ни будущим — а стоящие строки не трогает (горизонт подавляет создание, не существующие строки). Недатированному правилу дата бессмысленна: любое значение — маркер спячки «задача снесена, не воссоздавать»; правка правила маркер сбрасывает — пользователь, тронувший правило, снова его включил (правка датированного правила горизонт бережёт: снесённая история не воскресает). Первоначальное решение (операция только по журналу удалённых правил, вопрос вынесен владельцу) заменено решением владельца 2026-10-01 — расхождение с буквой шита #497 стало багом «не удаляются завершенные задачи». Аудит: `task.completed_cleared` с `count` в контексте.
- Выполнение (`task.completed`) — `completed_date := сегодня` пояса собственника; повторное — 409. «Отменить выполнение» (`task.uncompleted`) — `completed_date := NULL`, только пока правило живо: журнал удалённого правила — только чтение (409).

### 4. Контракты первого среза (OpenAPI)

Пути вложены под объект (прецедент payments):

- `POST /properties/{propertyId}/tasks/rules` — создание правила = создание задачи; первая материализация — в той же транзакции.
- `GET|PATCH|DELETE /properties/{propertyId}/tasks/rules/{ruleId}` — чтение (экран редактирования), частичная правка (`comment`/`dueDate`/`dueTime` — tri-state), жёсткое удаление (UI v1 не покрыт, контракт готов — решение #497).
- `GET /properties/{propertyId}/tasks?completed=&limit=&offset=` — постраничный список задач объекта с фильтром-«вкладкой» (`completed=false` — активные, `true` — журнал); `status` элемента — серверно-вычисляемый бакет `active | overdue | undated | completed`; ответ несёт `total` того же фильтра (счётчик «Выполненные N») и `today` собственника — границу секций «Сегодня»/«Завтра»; клиент пояса не знает.
- `POST /properties/{propertyId}/tasks/{taskId}/complete` и `…/uncomplete` — выполнение и отмена.
- `DELETE /properties/{propertyId}/tasks/completed` — «Удалить все выполненные» (см. §3).

Спека — единый файл `api/openapi/openapi.yaml` (прецедент ADR 0049 §4); фронтовый клиент регенерируется `npm run generate:api`. Права — матрица ADR 0028 через policy-порт: Viewer — чтение; Full Access и Owner — все мутации контекста (решение #496: удаление правила — не Owner-only). Аудит: `task_rule.created|updated|deleted`, `task.completed|uncompleted|completed_cleared`; bulk-тик не пишется пооперационно (расширенный гэп ADR 0020).

## Considered Options

- **JSONB-повтор (прецедент Payments)** — отклонён резолюцией #496: параметров повтора в v1 нет, TEXT-enum достаточно.
- **Мягкое удаление правила (`deleted_at`)** — отклонено: журнал переживает удаление через снимки, «живые мёртвые строки» без пользы.
- **Буквальное «удалить ВСЕ выполненные» (включая живые правила) без механизма** — отклонено: следующий тик воссоздаёт прошлую историю правила как активные просроченные задачи (дедуп-ключи исчезают вместе со строками) — data-corrupting поведение, противоречащее тику. Амендом 2026-10-01 та же цель достигнута с механизмом — пер-правильным горизонтом истории (`000146`): удаление осталось буквальным, а «воскрешение» подавлено границей на правиле.
- **Статус-надгробия задач (per-instance, EXDATE-стиль) для «Удалить все выполненные»** — отклонено: против решения #496 «статус-надгробий нет»; выбран грубый per-rule горизонт — достаточно для массовой операции, не требует пометки каждого вхождения.
- **Один тик-воркер на payments+tasks** — отклонено: резолюция #496 требует собственную петлю с собственным advisory-lock-пространством; контексты независимы, падение одного тика не должно останавливать другой.
- **Просрочка по границе суток у задач со временем** — отклонена research #495: граница — момент срока с точностью до минут.

## Consequences

- (+) Все дюральные инварианты — в БД: дедуп материализации (две частичные уникальности), время-требует-дату, повтор-требует-якорь; остальное — идемпотентный тик.
- (+) Единая точка сериализации (property row lock) — та же дисциплина, что в payments; гонки update-vs-tick, archive-vs-tick, delete-vs-tick закрыты.
- (+) Журнал выполнений переживает удаление правила с целостными снимками; чтение не требует join'а на правило.
- (−) «Удалить все выполненные» безвозвратно стирает журнал живых правил: горизонт истории подавляет их воссоздание, но сам факт выполнения и его дата теряются — осознанная цена решения владельца 2026-10-01 (аменд §3; до него строки живых правил береглись как дедуп-ключи).
- (~) Горизонт истории (`history_before`, `000146`) — ещё одно правило-носитель состояния: правка датированного правила обязана его сохранять (иначе снесённая история воскресает), правка недатированного — сбрасывать маркер; инвариант держат интеграционные тесты журнала.
- (−) Просрочка со временем зависит от текущего момента: каждый листинг резолвит TZ собственника и усекает минуты (один запрос `users.timezone` на чтение).
- (~) Приложение обязано поддерживать `owner_id` = `properties.owner_id` при каждой вставке (денормализация ADR 0028); расхождение исключено транзакционным созданием через резолв property.
- Миграция проходит `make migrations-lint`; интеграционные тесты репозиториев, тика и use cases — testcontainers PostgreSQL 18 (швы: повторы, материализация, удаление/журнал, права).
