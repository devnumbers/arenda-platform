# ADR 0068: bfcache не возвращаем — pageshow-гард остаётся последним рубежом

Гард #1098 (`BfcacheGuard`, `shared/lib/bfcache/bfcache-reload.ts`) перезагружает документ при любом `pageshow` с `event.persisted`: после логаута bfcache-возврат показывал бы кабинет из in-memory снимка (JS-heap с RSC-кэшем Next и react-query) без единого сетевого запроса, а сессия httpOnly — клиент cookie не видит. Цена гарда: «Назад/Вперёд» = полная перезагрузка. Решение-тикет #1595 (HITL): возвращать ли bfcache мягким механизмом. **Решено: не возвращаем** — гард остаётся обязательным; мягкий паттерн «pageshow → fetch /me → 401 → /login, иначе снимок» отвергнут как регресс безопасности для финансового кабинета. База — ресерч #1097 и #1590 (резолюция с источниками 2025–2026).

## Considered Options

1. **Гард `pageshow persisted → location.reload()` (выбран, статус-кво #1098).** Единственный механизм, работающий во всех браузерах: неаутентифицированный документ не отдаётся вовсе — proxy.ts проверяет сессию на сервере уже при загрузке документа. Safari/iOS закрывается только им: Page Cache не контролируется заголовками, `Clear-Site-Data: "cache"` не поддерживается, эвикции по изменению cookie нет, NotRestoredReasons нет. В Chrome с 2025 (CCNS) bfcache для no-store-HTTPS-страниц из приложения не отключается в принципе.
2. *Мягкий возврат: pageshow → fetch /me → 401 → /login, иначе снимок.* Отвергнут: (а) вспышка замороженного DOM кабинета (суммы, имена) до ответа сервера — субсекундная экспозиция чувствительных данных, которой при reload нет; (б) неустранимый TOCTOU — логаут во второй вкладке/на другом устройстве после ответа /me; (в) офлайн или недоступный сервер требует ветки, которая либо показывает снимок с неизвестным состоянием сессии, либо вырождается в тот же reload; (г) деньги остаются замороженными: при bfcache-восстановлении ремоунта нет, `refetchOnWindowFocus: false`, без отдельного `queryClient.invalidateQueries()` на pageshow данные не перечитываются никогда. web.dev канонизирует паттерн для logout, но с проверкой cookie — с httpOnly-сессией остаётся только сетевой fetch, что и делает его регрессом.
3. *Управление bfcache заголовками (`Clear-Site-Data`, `Cache-Control: no-store`).* Отвергнуто: снимок заголовком не контролируется (#1097). `no-store` на документе есть, но Chrome с 2025 игнорирует его для bfcache (CCNS); Firefox по-прежнему не кэширует no-store (там «Назад» — полный переход и так); Safari кэширует no-store всегда. `Clear-Site-Data: "cache"` на логауте уже пробовали и убрали (#1098, диагноз 2026-10-06): Chrome подвешивает доставку 204 на 11–14 с, Firefox от `"cache"` bfcache не эвиктит, Safari не поддерживает.
4. *Ускорение возврата вместо гарда (SW-кеш фото, серверный префетч).* Не альтернатива гарду, а смягчение его цены: серверный префетч #887 уже гидратит данные до первого рендера; SW-кеш фото — решение карты #1587, принимается отдельно. Даже без bfcache «Назад» после перезагрузки станет быстрым.

## Consequences

- **Код не меняется:** трио рубежей #1098 сохраняется — `hardReplace` на границе авторизации, `BfcacheGuard` в корневом layout, proxy-гейт /me. Юнит-тесты гарда и e2e `auth.spec.ts` остаются каноничной проверкой.
- **Цена известна и принята:** во всех браузерах, где bfcache живёт (Chrome CCNS, Safari), «Назад» из кабинета = полная перезагрузка документа. Внутренние SPA-навигации гарда не касаются.
- **Взаимодействие с SW:** SW-контролируемые страницы остаются bfcache-eligible; каждая активация новой версии SW выселяет лежащие в bfcache записи (безопасно, лишь режет hit-rate). Будущий SW-кеш фото (#1587) на решение не влияет: фото — версионные URL, снимок внутренне консистентен.
- **Триггер пересмотра (решение #1595, 2026-10-23):** пересмотреть, если после лендинга SW-кеша фото #1587 «Назад» в кабинете всё ещё будет ощущаться медленным на мобилке. Без телеметрии и без заранее созданного тикета — эта строка.
