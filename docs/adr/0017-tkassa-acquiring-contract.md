# ADR 0017: Контракт T-Kassa Acquiring (CC/COF)

## Status

Accepted

## Context

Подписка оплачивается через T-Kassa по сценарию CC/COF (платежи по сохранённым реквизитам): первый платёж привязывает реквизиты, продления списываются без участия пользователя. Несколько production/stage-багов возникли из непроверенных предположений о контракте провайдера: неверный `OperationInitiatorType` на родительском платеже (`"2"` вместо `"1"`), `Recurrent=Y` на дочернем платеже, ожидание статуса `"SUCCESS"` в add-card webhook (такого статуса не существует) и маршрутизация add-card webhook без `NotificationType` в платёжную ветку парсера.

Источники истины по контракту T-Kassa:

- официальная документация: https://developer.tbank.ru/eacq;
- вендоренная OpenAPI-спецификация: `apps/backend/internal/billing/adapters/payment/tkassa/spec/openapi.yaml` (см. ADR 0016).

Любое изменение платёжной интеграции обязано сверяться с этими двумя источниками до реализации.

## Decision

### Платёжные сценарии

- **Родительский платёж** (первый платёж, получает `RebillId`): `Init` с `Amount`, `PayType="O"`, `Recurrent="Y"`, `DATA.OperationInitiatorType="1"` (CIT CC), `CustomerKey`, `NotificationURL`/`SuccessURL`/`FailURL`, `Description` ≤ 140 символов. `RebillId` приходит в `AUTHORIZED` webhook-уведомлении после родительского CC-платежа (не в ответе `Init`) и также доступен в ответе `GetState`; он сохраняется на способе оплаты.
- **Дочерний платёж** (продление, MIT): `Init` с `Amount` и `DATA.OperationInitiatorType="R"`, поле `Recurrent` **не передаётся**; затем `Charge` с `PaymentId` + `RebillId`. `Charge` вызывается без `Amount` — сумма берётся из исходного `Init`.
- **Обычный разовый платёж** без сохранения реквизитов: `OperationInitiatorType="0"`.

Матрица `OperationInitiatorType` из официальной документации:

| Значение | Тип операции |
|---|---|
| `0` | CIT без сохранения реквизитов (обычный платёж) |
| `1` | CIT CC — родительский платёж по введённым карточным данным |
| `2` | CIT COF — дочерний платёж по сохранённым реквизитам, инициированный покупателем |
| `R` | MIT COF Recurring — рекуррентное списание мерчантом |
| `I` | MIT COF Installment — рассрочка |
| `D` | MIT COF Delayed — отложенное списание |
| `N` | MIT COF No-Show — неявка |

Дочерние типы (`2`, `R`, `I`, `D`, `N`) используются **только** для платежей по сохранённым реквизитам; `Recurrent=Y` передаётся **только** в родительском платеже. Несовместимые комбинации `Recurrent`/`RebillId`/`OperationInitiatorType` отклоняются ошибкой `1126`.

### Жизненный цикл платежа

Статусы платежа по официальной документации:

- `NEW` — `Init` принят, выданы `PaymentId` и `PaymentURL`.
- `FORM_SHOWED` — покупателю показана платёжная форма.
- `AUTHORIZING` — выполняется авторизация (списание) средств.
- `PAY_CHECKING` — результат авторизации неизвестен после попытки списания.
- `AUTHORIZED` — средства захолдированы на карте.
- `CONFIRMING` — выполняется подтверждение списания.
- `CONFIRM_CHECKING` — результат подтверждения неизвестен.
- `CONFIRMED` — средства списаны (финальный успешный статус).
- `REVERSING` / `PARTIAL_REVERSED` / `REVERSED` — отмена холда до подтверждения.
- `REFUNDING` / `PARTIAL_REFUNDED` / `REFUNDED` — возврат после подтверждения.
- `CANCELED` — платёж отменён из статуса `NEW`.
- `DEADLINE_EXPIRED` — истёк срок жизни ссылки на платёжную форму.
- `REJECTED` — банк отклонил операцию.
- `AUTH_FAIL` — ошибка проведения платежа или сбой 3DS; после 3 неудачных попыток платёж переходит в `REJECTED`.

При одностадийной оплате (`PayType="O"`): `Init` → редирект на `PaymentURL` → `CONFIRMED` при успехе либо `AUTH_FAIL`/`REJECTED` при отказе. Ограничения: минимальная сумма платежа — 1 RUB; по правилу НСПК холд живёт максимум 7 дней, включая день авторизации.

### Cancel / Refund

Один метод `Cancel` покрывает отмену холда и возврат; результат зависит от текущего статуса платежа:

| Текущий статус | Результат `Cancel` |
|---|---|
| `NEW` | `CANCELED` (поле `Amount` игнорируется) |
| `AUTHORIZED` | `REVERSED` / `PARTIAL_REVERSED` |
| `CONFIRMED` | `REFUNDED` / `PARTIAL_REFUNDED` |

- Частичный возврат при включённой онлайн-кассе требует `Receipt` с позициями; для полного возврата `Receipt` не нужен — чек формирует банк.
- Идемпотентность возврата обеспечивает поле `ExternalRequestId`.

### Привязка карты (AddCard)

`AddCustomer` (один раз на пользователя) → `AddCard` с `CheckType="3DSHOLD"` → пользователь проходит 3DS на странице по `PaymentURL` из ответа → T-Kassa присылает add-card webhook.

Выбор `CheckType` определяет проверку карты и выдачу `RebillId`:

| CheckType | Поведение |
|---|---|
| `NO` | сохранение без проверок; `RebillId` не выдаётся |
| `HOLD` | холд на 0 RUB; `RebillId` для терминалов без 3DS |
| `3DS` | проверка 3DS + платёж на 0 RUB; `RebillId` только для карт с 3DS |
| `3DSHOLD` | проверка 3DS; карты без 3DS проходят холд на 0 RUB; `RebillId` выдаётся |

Мы используем `3DSHOLD`: `RebillId` выдаётся и для карт с 3DS, и для карт без 3DS. Ссылка на форму привязки живёт 2 дня.

- Add-card webhook может **не содержать** `NotificationType`: в payload есть `RequestKey` + `CustomerKey` и нет `OrderId`. Парсер webhook дискриминирует тип по `RequestKey`/`OrderId` (см. `Provider.ParseWebhook`).
- Успешная привязка — `Status="COMPLETED"` с `Success=true`. Enum статуса привязки в спецификации: `COMPLETED`/`REJECTED`; статуса `"SUCCESS"` не существует.
- `RedirectUrl`/`FailRedirectUrl` передаются в теле запроса, но исключаются из расчёта токена (см. ADR 0010).

### Webhook-уведомления

- При одностадийной оплате и для `Charge` T-Kassa отправляет **два** уведомления одновременно: `AUTHORIZED` и `CONFIRMED`.
- На webhook отвечаем HTTP 200 с телом `OK` (заглавными буквами, без тегов) в течение 10 секунд. Иначе T-Kassa повторяет отправку: раз в час в течение 24 часов, затем раз в сутки в течение месяца; уведомления архивируются через 90 дней.
- Платёжные уведомления могут не содержать `NotificationType` или содержать `NotificationType="NotificationPayment"`.
- Уведомления о привязке карты, фискализации и оплате по QR приходят **только** на `NotificationURL`, настроенный в параметрах терминала: per-request `NotificationURL` у `AddCard` нет.
- Проверка токена по официальному алгоритму: исключить ключ `Token` и вложенные объекты `Data`/`Receipt`, добавить `Password`, отсортировать ключи лексикографически, конкатенировать значения, взять SHA-256. Поля токена add-card уведомления: `TerminalKey`, `CustomerKey`, `RequestKey`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `CardId`, `Pan`, `ExpDate`, `RebillId`.
- IP-сети источников уведомлений (только порт 443): `91.194.226.0/23`, `91.218.132.0/24`–`91.218.135.0/24`, `212.49.24.0/24`, `212.233.80.0/24`–`212.233.83.0/24`; тестовая среда — `91.194.226.181`.

### Коды ошибок

Сверено с официальным каталогом ошибок (https://developer.tbank.ru/eacq/intro/developer/errors):

- `1125` — некорректное значение `OperationInitiatorType`.
- `1126` — несопоставимые значения `RebillId` или `Recurrent` с переданным `OperationInitiatorType`.
- `10` — метод `Charge` заблокирован для терминала: COF-операции (recurring) включаются через менеджера Т-Банка; без этого `Charge` по `RebillId` падает.
- `501` — терминал не найден (маппится в `ErrProviderTerminalNotFound`; обычно неверный terminal key или неверный base URL — test вместо prod).
- `7` — неверный статус покупателя: `GetCardList` возвращает `7`, когда у покупателя нет карт, — трактуем как пустой список (в `AddCustomer` код `7` означает «покупатель уже существует» и трактуется как успех).
- `204`/`205` — неверный токен: проверьте пару TerminalKey/SecretKey (`205` также возвращается как «указанный терминал не найден»). «Платеж не найден» — отдельный код `255`; неверное состояние транзакции — коды `4`/`8`.
- `107` — неверный `CardId`, карта не была привязана; `231` — не найден идентификатор карты. Оба маппятся в `ErrProviderCardNotFound`.
- `104` — ошибка рекуррентного платежа.
- `262` — истёк срок жизни родительского платежа.
- `223`/`235` — некорректный формат `RebillId`.
- `502` — карта по `RequestKey` не найдена.
- `504` — ошибка платежа во время привязки карты.
- `510` — карта уже привязана к `CustomerKey`.
- `511` — проверка 3DS не пройдена.
- `99` — отказ эмитента; стоит повторить позже.
- `103`/`116`/`1051` — недостаточно средств на карте.
- `119`/`120`/`123`/`125` — лимиты запросов / временные ошибки; повторить позже.
- `1238` — недостаточно средств на балансе мерчанта для возврата.
- HTTP `500`/`503` — ошибки на стороне провайдера, временные: HTTP-клиент повторяет запрос с экспоненциальным backoff и jitter.

### Эксплуатационные требования

- COF/recurring должен быть включён на терминале менеджером Т-Банка (иначе ошибка `10`).
- `SuccessAddCardURL`/`FailAddCardURL` для редиректа после `AddCard` настраиваются через поддержку acq_help@tbank.ru, а не через API.
- TLS: endpoints T-Kassa используют сертификаты HARICA / MinCA (см. intro/certificates в официальной документации).

### Тестовая среда и аттестация

- Тестовая среда: боевой терминал (без префикса `DEMO`) + base URL `https://rest-api-test.tinkoff.ru/v2`; доступ — по whitelist IP, который запрашивается через чат T-Business (ИНН, название организации, список IP). Без whitelist вызовы падают с ошибкой «терминал не найден» (`501`).
- Тестовые карты (любой `expDate`, cvv `123`):
  - `2201382000000013` — успешный платёж, 3DS frictionless;
  - `2201382000000047` — 3DS challenge (пароль ACS `1qwezxc`);
  - `2201382000000831` — недостаточно средств;
  - `2201382000000021` — ошибка платежа;
  - `2200770239097761` — успешный платёж без 3DS.
- Аттестация: `DEMO`-терминал + `https://securepay.tinkoff.ru/v2`, тест-кейсы запускаются кнопкой «Тестировать» в ЛК терминала; группы «Общие», «Автоплатежи», «Формирование чека». Известные подводные камни: в общем тест-кейсе нельзя передавать `Recurrent=Y`; ответ на webhook должен быть строго `200:OK`.

### Polling

После `Charge` статус платежа уточняется опросом `GetState` (`Provider.Status`). Маппинг статусов (`mapStatus`): `REVERSED`/`PARTIAL_REVERSED` из `GetState`/webhook для нашего подписочного платежа трактуются как failed (неясно, чей это возврат); в ответах `Cancel` (`mapCancelStatus`) те же статусы означают успешный возврат по нашей инициативе.

## Consequences

- (+) Единый проверенный контракт: решения по платёжному коду принимаются по официальной документации и вендоренной спецификации, а не по предположениям.
- (+) Контрактные тесты (`tkassa_test.go`) фиксируют тела запросов к типам спецификации и ловят регрессии (`OperationInitiatorType`, `Recurrent`, состав полей `Charge`).
- (+) Явно зафиксированы эксплуатационные зависимости, которые раньше обнаруживались только на stage/prod инцидентах.
- (-) Часть контракта живёт вне кода: включение COF на терминале, IP-whitelist тестовой среды, AddCard redirect URL — готовность stage/prod зависит от ручных действий в Т-Банке.
- (-) Документация и спецификация T-Kassa могут меняться: при обновлении версии спецификации контракт нужно перепроверять (см. ADR 0016).
