# ADR 0052: задачи без объекта

Глобальный экран «Задачи» (карта wayfinder #518, макеты Figma «Рентли. Новые экраны сервиса») требует задачу как личное дело владельца: создание с опциональным выбором объекта, лента всех задач владельца, фильтр по объекту. Действующая модель (ADR 0051) держит `property_id UUID NOT NULL ON DELETE CASCADE` в `task_rules` и `tasks` — связь с объектом обязательна, и её нельзя ослабить без решений о доступе, времени и тике. Решаем: ссылка на объект опциональна; безобъектные правила и задачи живут в книге владельца — owner-only, по поясу владельца, с собственным якорем сериализации тика; удаление объекта по-прежнему уносит его задачи каскадом. Решения приняты на grilling-сессии тикета #519 карты #518 (2026-09-04).

## Status

Accepted

## Context

Экранная карта #522 и макеты Figma вводят создание задачи с опциональным полем «Объект» и глобальную ленту задач владельца. Сегодня контекст tasks (ADR 0051) привязывает каждое правило и каждую задачу к объекту: миграция `000118_tasks_context` — `property_id UUID NOT NULL ... ON DELETE CASCADE` в обеих таблицах, пути контрактов только под `/properties/{propertyId}/tasks`, тик идёт по зонам — DISTINCT TZ собственников с правилами на активных/в maintenance объектах — и сериализуется `FOR UPDATE` строк объектов владельца. Пояс для безобъектного времени уже есть: `users.timezone` NOT NULL (ADR 0048). Прецедент необязательной связи с объектом — книга контактов (ADR 0054 contacts): nullable `property_id`, `ON DELETE SET NULL`, безобъектные записи — только владелец.

## Decision

1. **Ссылка на объект опциональна** (миграция 000121): `property_id` в `task_rules` и `tasks` становится nullable. Правило или задача, созданная явно без объекта, — «задача без объекта» (словарь: `tasks/CONTEXT.md`); денормализованный `owner_id` для безобъектных строк — сам владелец.
2. **Удаление объекта — каскад остаётся**: в обоих режимах ADR 0025 удаление объекта сносит его правила и задачи целиком, включая журнал выполнений. Безобъектными задачи становятся только когда созданы явно без объекта — удаление объекта их не порождает.
3. **Доступ**: безобъектные правила и задачи видит и правит только владелец — actor/scope ADR 0028 определён только на объекте, вне объекта участников нет. Глобальные списки участника шаринга показывают только задачи объектов, к которым у него есть доступ.
4. **Время**: «сегодня», момент просрочки и дата выполнения безобъектных правил — по `users.timezone` владельца (ADR 0048); схема не меняется.
5. **Тик**: зоны тика (`ListTaskTickZones`) дополняются владельцами с безобъектными правилами — их TZ берётся из `users.timezone`; иначе безобъектное правило никогда не материализует. Якорь сериализации безобъектного среза — `FOR UPDATE` строки владельца (`users`); механика совмещения с существующей блокировкой строк объектов — техрешение бэкенд-тикетов #520/#521. Контракт тика (идемпотентность, дедуп-индексы, план материализации) не меняется.
   - _Механика (решена в #520)_: срезы тика раздельные, чтобы не скрещивать порядки блокировок. Мутация объектного правила берёт то же упорядоченное множество строк объектов владельца, что и тик, — первым локом транзакции (владелец резолвится неблокирующим чтением), её внутри-мутационный тик планирует только объектные правила (безобъектные она изменить не может). Мутация без объекта блокирует только строку владельца и тикает только безобъектный срез. Полный тик (часовой воркер и `RunOwnerTick`) — единственная транзакция с обоими якорями: сначала строки объектов владельца (по `id`), затем строка владельца; мутации объектов никогда не берут строку владельца, поэтому циклов нет.
   - _Уточнение (2026-09-05, [#546](https://github.com/devnumbers/arenda-platform/issues/546))_: исходная механика #520 держала у объектной мутации только её собственную строку объекта, а owner-wide упорядоченный лок брала в тике в конце транзакции — две параллельные мутации на разных объектах одного владельца взаимно ждали («своя строка → всё множество» против «своя строка → всё множество») и ловили дедлок (SQLSTATE 40P01) на «Отметить все задачи». Объектная мутация теперь берёт owner-wide упорядоченное множество строк объектов первым локом транзакции: один частичный порядок для всех транзакций среза, дедлок исключён по построению; набор блокируемых строк не изменился (тик и раньше брал всё множество).

## Considered Options

- **`ON DELETE SET NULL` как у контактов** — rejected: задача — обязанность объекта (расписание работ), а не запись книги владельца; после удаления объекта владелец получил бы ворох внезапно безобъектных активных и просроченных задач, а разъединённое правило продолжало бы материализовать уже без объекта — тихое изменение его обязательств. У контактов связь справочная — разъединение ничего не обязывает; у задач — календарная.
- **Отдельный срез безобъектных задач (своя таблица)** — rejected: дублирует модель «правило → вхождения», тик, журнал и дедуп-механику; единая nullable-связь дешевле и не плодит второй словарь.
- **Advisory lock как якорь сериализации безобъектных мутаций** — уступил `FOR UPDATE` строки владельца: блокировка одной строки проще и остаётся в той же дисциплине UoW (ADR 0033); вернуться — только если механика #520 вскроет конфликт с блокировкой строк объектов.

## Consequences

- (+) Задача может быть личным делом владельца: глобальная лента, создание без объекта, фильтр по объекту — по макетам карты #518.
- (+) Семантика удаления объекта не меняется: объект уносит свои задачи в обоих режимах ADR 0025; глобальный срез безобъектных задач живёт независимо.
- (−) Каждый список, счётчик и очистка журнала получают два среза — объектный и безобъектный; запросы обязаны явно выбирать срез предикатом по `property_id`, смешение срезов в одном ответе — ошибка контракта.
- (−) Сериализация тика получает второй якорь: тик per-owner совмещает блокировку строк объектов и строки владельца (детали #520).
- (~) Глобальные пути задач вне `/properties/{propertyId}` — контракты бэкенд-тикетов #520/#521; прецедент глобальных путей — `/contacts`.
