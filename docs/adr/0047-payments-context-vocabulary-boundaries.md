# ADR 0047: контекст «Платежи» — словарь и границы

## Status

Accepted

## Context

После удаления домена аренд (ADR 0046) record-keeping словарь денег пуст: «Операция, Доход, Расход» ушли вместе с доменом, а ADR 0036 банит «платёж» и «транзакцию» в record-keeping мире. Доменная модель-замена проверена в прототипе вне репозитория (снимок 2026-08-24; указатель на референс — Notes карты wayfinder #443): словарь из 8 терминов, 17 пронумерованных решений, 70 смоук-проверок. Правила переноса (HANDOFF прототипа): термины переименовываемы с таблицей соответствия, разделение «правило / вхождение / факт оплаты» обязано пережить переименование, отступления от 17 решений — только через владельца продукта.

При возвращении словаря в платформу обнаружена коллизия: «Способ оплаты» — канонический термин Billing (привязанная карта T-Kassa, ADR 0036), а прототип вводил своё «Способ оплаты» (перевод / наличка).

## Decision

Новый bounded context Payments — пакет `internal/payments`, имя «Платежи / Payments»; канонический словарь — `apps/backend/internal/payments/GLOSSARY.md` (создан до кода). Решения grilling-сессии (тикет #444, 2026-08-25):

1. **Identity-перенос словаря прототипа**: Платёж (правило), Операция (вхождение), Автоплатёж (режим, не сущность), Просрочка (вычисляемое состояние), Долг, Пауза, Доход/Расход — с прототипными определениями. «Объект» прототипа в словарь не входит: платёж ссылается на Property из контекста properties через `property_id`, своих сущностей-объектов нет.
2. **«Платёж» возвращается в активный record-keeping язык** — ревизия запрета ADR 0036. «Транзакция» остаётся processing-словом Billing; «Оплата подписки» в Billing не переименовывается. UI-исключение ADR 0036 («Платежи» как навигационный лейбл) растворяется: секция зовётся по доменной сущности.
3. **«Способ оплаты» остаётся за Billing** (карта T-Kassa); payments-термин — **«Форма оплаты»** (перевод / наличные), поле платежа, снапшот в операцию при материализации/оплате. В коде и контрактах: `payment_form` у Payments против занятого Billing `payment_method`. **Ревизия 2026-10-01** (карта #1005, тикет #1006, решение владельца): «Форма оплаты» **удалена целиком** — поле write-only, нигде не читается пользователем, ценности не несёт; колонки снесены (миграция 000145), `paymentForm` выбыл из контрактов и домена. Термин выбыл из словаря; разграничение с Billing осталось чистым — «способ оплаты» по-прежнему не payments-слово.
4. **Категория** — единый справочник, нейтральный к направлению (доход/расход выбирает пользователь на платеже, а не в справочнике — ревизия 2026-08-25 от пользователя, тикет #447; изначально предполагался признак применимости): нередактируемый дефолтный каталог (JSON → генерация Go + TS, паттерн property attributes) + пользовательские категории уровня аккаунта. Задаётся на правиле, операция наследует снапшотом; ручная операция — напрямую.
5. **Термины механики в словаре**: Тик, Материализация, Проекция — на них ссылаются будущие ADR схемы и фронтовые спеки; «Регулярность» — нет (внутри определения Платежа).
6. **Границы**: доступ — policy-порт по матрице ADR 0028; тик — ежечасный воркер `platform/scheduler` плюс прогон внутри мутаций контекста; в Audit контекст пишет, как все; зависимостей от Notifications нет (уведомления о платежах — вне текущего усилия); новая связь с Billing не заводится. Судьба платежей при архивации/удалении объекта и БД-форма удаления платежа — ADR схемы (тикет #446).

## Considered Options

- **Переименовать «Платёж»/«Операцию» под язык платформы** — отклонено: прототип гриллил имена и отверг альтернативы (avoid-лист: шаблон, регулярный платёж); identity-перенос сохраняет трассируемость 17 решений по правилам HANDOFF.
- **Одноимённый «Способ оплаты» в двух контекстах** — отклонено: воспроизводит боль, ради прекращения которой написан ADR 0036 (learning-record 0007); `payment_method` в коде и БД Billing уже занят.
- **Раздельные каталоги категорий дохода и расхода** — отклонено: одна сущность и один генератор каталога вместо двух; категория не привязана к направлению — направление выбирается на платеже.

## Consequences

- GLOSSARY-MAP: контекст в списке, связь Properties → Payments, record-keeping словарь в shared kernel перестаёт быть пустым; корневой AGENTS.md обновлён. ADR 0036 и 0046 остаются историей без правок — актуальность обеспечивают ссылки.
- Словарь — вход для тикетов карты #443: каталог из Figma (#447 — форма каталога: единый справочник без привязки к направлению), схема БД и контракты (#448 — имена сущностей и `payment_form`), жизненный цикл в БД (#446), экраны (#449).
- Разделение «правило / вхождение / факт оплаты» пережило перенос без изменений; отступлений от 17 решений прототипа нет.
