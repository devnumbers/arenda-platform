# ADR 0065: Лог изменений платежа (payment_change_log)

## Status

Accepted (research [#1184](https://github.com/devnumbers/arenda-platform/issues/1184), карта [#1183](https://github.com/devnumbers/arenda-platform/issues/1183), тикет [#1187](https://github.com/devnumbers/arenda-platform/issues/1187), 2026-10-07; миграция, запись и чтение — тикет [#1188](https://github.com/devnumbers/arenda-platform/issues/1188))

## Context

Экран «История платежа» (макеты 3214-73216/73857, карта #1183) получает переключаемый режим «изменения»: чипы вида «Сумма изменена: 2 500 ₽», «Категория изменена: „Юридические услуги"», «Регулярность изменена: каждый месяц, 1, 10, 15 числа». Продуктовые ограничения из брифа владельца:

- «Название изменено» — только для заданных пользователем названий: авто-имя из категории чипа не порождает;
- записей о ранней/поздней оплате в истории нет — факт расхождения дат виден на странице операции;
- чипы на странице платежа не показываются — только на экране истории платежа в режиме изменений.

Research #1184 сравнил три укладки: (a) отдельная append-only таблица в контексте payments; (b) расширение `action_journal` (entity kind+id + структурный диф в `context`); (c) гибрид. Ограничения (b): лента `action_journal` живёт в grain «действие по объекту» и не имеет entity_id (id платежа — только внутри `segments.link.id` JSONB, ADR 0061 §2), её текст строк строит сервер ради сцепки «searchable = показанному тексту» (§6), читается она по объекту, а не по платежу; существующие записи задним числом не достраиваются.

## Decision

### 1. Отдельная append-only таблица в контексте payments

Grain экрана — «правка → поля → old→new» по одному платежу, обратная хронология, пагинация; отдельная таблица даёт этот grain одним keyset-индексом, без расширения общего журнала миграцией с невозможным бэкфиллом (старых значений полей нигде не хранится — правки до внедрения в истории изменений не видны, и это осознанно).

Каноническая форма DDL (миграция и точки записи — тикет #1188):

```sql
-- Лог изменений платежа (ADR 0065): одна append-only строка на правку
-- пользователя; пауза/возобновление — строки с пустым changes и своим
-- action; создание и удаление строк не пишут. Живёт и умирает с платежом.
CREATE TABLE payment_change_log (
    id UUID PRIMARY KEY,                        -- UUIDv7 из приложения (ADR 0019)
    payment_id UUID NOT NULL REFERENCES payments(id) ON DELETE CASCADE,
    owner_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,     -- денормализация скоупа (ADR 0028), как у payments/operations
    property_id UUID NOT NULL REFERENCES properties(id) ON DELETE CASCADE,
    actor_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,     -- пишут только пользователи
    action TEXT NOT NULL CHECK (action IN ('updated', 'paused', 'resumed')),
    changes JSONB NOT NULL DEFAULT '[]'::jsonb, -- [{field, old, new}] — типизированные значения (§2)
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_payment_change_log_payment
    ON payment_change_log (payment_id, created_at DESC, id DESC);

-- Маркер ручного названия (§3): взводится правкой с title, не сбрасывается
-- никогда — «название когда-либо было задано вручную».
ALTER TABLE payments ADD COLUMN title_is_manual BOOLEAN NOT NULL DEFAULT false;
```

Append-only: INSERT без updated_at, никаких UPDATE/DELETE из приложения; единственный канал удаления — каскад за платежом (тотальное удаление объекта удаляет и его). Надгробие «Платёж удалён» остаётся в ленте «История действий» (ADR 0061 `payment.deleted`).

### 2. Словарь полей и типизированные значения

Ключи словаря — словарь мутационного аудита контекста (`type`, `title`, `amount_kopecks`, `recurrence`, `category_slug`, `end_date`, `auto_pay`, `reminder_offset_days`; reminder_offset_days включён решением владельца к #1188). Значения типизированы, никогда не строки-с-форматированием:

- копейки — число (int64);
- регулярность — канонический JSON-объект, та же форма, что `payments.recurrence` и OpenAPI `Recurrence*` (`kind`, `weekdays`, `daysOfMonth`, `lastDay`, `month`, `day`) — множественная месячная форма «каждый месяц, 1, 10, 15 числа» едет структурой `{kind: "monthly", daysOfMonth: [1, 10, 15]}`;
- даты (`end_date`) — «YYYY-MM-DD» или null;
- направление и название — строки; автоплатёж — булево; напоминание — число (1/3/7) или null;
- категория (`category_slug`) — ссылка плюс снапшот лейбла на момент правки: `{"slug": "…", "label": "…"}` или `{"userCategoryId": "…", "label": "…"}` — чип читаем после переименования или удаления пользовательской категории (канон снапшота `category_label` операций, ADR 0049 §1).

Порядок строк дифа — словарный, стабильный; чипы экрана читаются в нём.

### 3. Правило «Название изменено» и маркер ручного названия

Diff-patch-семантика PATCH структурно гарантирует источник титульной строки: фронт шлёт `title` только при реальной правке пользователем (визард хранит title как undefined до касания), арендный шов названий не правит. Поэтому титульная строка в `changes` возникает только из ручной правки — она и есть чип «Название изменено». Домен выражает правило функцией `HasTitleChange`; она же — сигнал взведения маркера.

Маркер `payments.title_is_manual` — durable-состояние «название когда-либо было задано вручную»: взводится любой правкой с `title`, не сбрасывается никогда (обратного пути к авто-имени нет). Создание маркер не взводит: первый титул — не «правка», старого значения не существует. Сегодняшних читателей у маркера нет — правило чипа держится структурой PATCH; маркер закрепляет состояние для будущих авто-правок названия (например, слежения названия за категорией, пока оно не задано вручную). Правило на тот случай фиксируется сразу: авто-правка названия обязана идти мимо дифа — пока `title_is_manual = false`, титульная строка в `changes` не попадает и маркер не взводится, иначе появилось бы ложное «Название изменено».

### 4. Что пишется, а что нет (решения владельца 07.10, раунд 2 к #1188)

- Пишется: правка платежа пользователем — строка `updated` с дифом; пауза — строка `paused` с пустым `changes`; возобновление — строка `resumed` с пустым `changes`.
- Арендный конвейер: правка условий аренды (сумма, день оплаты → регулярность, автоплатёж, окончание) пишет диф в историю управляемого платежа — вторая точка записи на шве `paymentSyncFromUpdate`/`RentPaymentChange` (payment store), не только PaymentService; словарь и диф те же.
- Не пишется: создание (не правка — старых значений нет), удаление (FK CASCADE роняет журнал вместе с правилом; надгробие — в «Истории действий»), оплаты операций и раннее/позднее попадание (факт виден на странице операции), звезда избранного и порядок (шум, канон ADR 0061 §3).

### 5. Текст чипов рендерит фронт

Осознанное отклонение от канона ADR 0061 §6 («сервер — источник текста строки») для этого экрана: вся лексика уже канонически фронтовая — `recurrenceLabel` (резолюция #452, включая множественную месячную форму «Каждый месяц 1, 10 и 15 числа»), `formatMoneyKopecks`, каталог категорий; поиска на экране нет, и сцепки «searchable = показанному тексту», ради которой сервер строит segments ленты действий, здесь не существует. Сервер отдаёт структуру (§2), фронт собирает фразы. Исходная формулировка «серверный рендеринг» из тела #1187 заменена этим решением по итогам research #1184 (закреплено картой #1183).

### 6. Запись и чтение (план тикета #1188)

Запись — в транзакции мутационного конвейера (ADR 0049 §3): снимок правила до `applyUpdate`, слияние патча, диф `DiffPaymentChanges(before, after)` из домена, INSERT той же транзакцией — fail-safe канон ADR 0020/0061; слот в `mutationOutcome` рядом с Audit/History. Чтение — `GET /properties/{propertyId}/payments/{paymentId}/changes`: производный доступ (ADR 0028), чужое/невидимое — приватный 404, обратная хронология, двусторонний keyset-курсор по `(created_at, id)` (канон #597, `shared/cursor`); контракт-first OpenAPI и кодогенерация — в #1188. Миграция одна (`000152_payment_change_log`: CREATE TABLE + ALTER payments; на ветке 000151 занят `operations_paid_source` из карты #1162), down тривиален — DROP таблицы и колонки, схема без данных.

## Consequences

- (+) Grain «правка → поля → old→new» ровно под экран; чипы собираются на фронте без парсинга текста.
- (+) Чтение — один keyset-индекс по платежу; запись — один INSERT в уже открытой транзакции мутации.
- (+) Словарь полей един с мутационным аудитом контекста — второй словарь не заводится.
- (−) Ещё одна таблица контекста и ещё одна запись на каждую мутацию правила (человеческий темп — микросекунды).
- (−) История правок до внедрения пуста: бэкфилл невозможен (старых значений нигде нет) и не требуется.
- (~) `action_journal` остаётся лентой «действий по объекту» без entity_id; его каноны не тронуты.

## Rejected alternatives

- **Расширение `action_journal`** (entity_id + структурный диф в `context`): grain и канон ленты — «действие по объекту» с серверным текстом строк; потребовал бы миграцию с backfill, который невозможен; сцепка текста с поиском экрану без поиска не нужна.
- **Гибрид** (чипы из `action_journal.context`): те же проблемы бэкфилла плюс второй словарь полей.
- **Триггеры БД**: не знают актёра и продуктовых правил («авто-имя из категории — не изменение названия»).
- **Event sourcing / SCD2 / full-row снапшоты**: удвоение хранения и дифференциация на чтении; для аудита правок достаточно regular logging (Fowler, Event Sourcing).
- **Серверный рендеринг текста чипов**: отклонён (§5).
