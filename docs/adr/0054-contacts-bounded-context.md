# ADR 0054: книга контактов — отдельный контекст contacts

> Историческая нумерация: принят как «ADR 0051» в параллельной ветке contacts; номер 0051 был занят ADR tasks-context-schema-tick-contracts, коллизия снята ренумерацией в 0054.

## Status

Accepted

## Context

Фича «Контакты» (карта wayfinder #503) хочет книгу контактов владельца: карточки людей для объектов — сантехник, управляющая компания, консьерж, — с поиском по ФИО, телефону, почте, имени пользователя мессенджера и роли, живущие в книге владельца даже без привязки к объекту.

Действующая модель — ADR 0026: `property_contacts` внутри контекста `properties`; контакт принадлежит ровно одному объекту и каскадно удаляется с ним в обоих режимах (ADR 0025), страница объекта — единственная поверхность, где контакты живут. Этой модели книга противоречит: контакт без объекта в ней невозможен, а удаление объекта уничтожает его записи. Линия 0026 частично уже сгнила и сама по себе: `tenant_contacts`, в сопоставлении с которыми принималось то решение, удалены вместе с доменом аренд (ADR 0046).

Решение принято на grilling-сессии карты #503 (2026-09-02); язык и границы фиксирует тикет #504.

## Decision

1. **Новый bounded context `contacts`** (`apps/backend/internal/contacts`) — книга контактов владельца. Таблица `contacts`: `owner_id` (книга владельца) + nullable `property_id` (опциональная привязка к объекту). Канонический термин — «Контакт / Contact»; глоссарий — `contacts/CONTEXT.md`.
2. **Удаление объекта обнуляет ссылку в обоих режимах ADR 0025**: FK `contacts.property_id ON DELETE SET NULL`. Контакт выживает в книге владельца. Это осознанный разворот решения ADR 0026 (там `ON DELETE CASCADE` по образцу `property_photos`): контакт теперь самостоятельная запись владельца, а не ребёнок объекта.
3. **Доступ — как у платежей**: владелец управляет всеми своими контактами (actor/scope, ADR 0028); контакты, привязанные к объекту, видимы и редактируемы участникам шаринга по ролям на объекте (CanView/CanEdit); контакты без объекта видит только владелец.
4. **Старая `property_contacts` сносится целиком**: таблица, домен/сервис/handlers в `properties`, эндпоинты `/properties/{id}/contacts`; чтение в админке переводится на `contacts`; старый UI удаляется. **Данные не переносятся** — решение владельца (grilling 2026-09-02): записи не представляют ценности, книга начинается пустой.
5. UI фичи — только на странице объекта, без новых пунктов навигации; глобальный раздел книги владельца — туман карты #503, не эта карта.

## Rejected alternatives

- **Обобщение внутри `properties`** (продолжение линии ADR 0026: сделать привязку `property_contacts` необязательной) — rejected: книга владельца — не объектная сущность; держать её в `properties` значит тащить чужой для объекта owner-scope и доступ участникам шаринга поверх объектного контекста. Граница проводится так же, как в 0026 проводился отказ от единой книги с `tenant_contacts`, — только теперь в обратную сторону.
- **Перенос данных `property_contacts` → `contacts`** — rejected: владелец отказался от переноса («не жалко»); миграция данных только усложнила бы снос. Прецедент — снос аренд и Операций без переноса (ADR 0046).

## Consequences

- ADR 0026 помечен superseded; термин «Контакт объекта / Property Contact» уходит из активного языка (`properties/CONTEXT.md`, `CONTEXT-MAP.md`).
- `properties` теряет последние контактные поверхности (эндпоинты, домен, таблицу); контекст остаётся «только про объект»: карточка, фото, атрибуты, архив.
- Админка читает контакты из `contacts` (привязанные к объекту — по `property_id`); карточки контактов в админке без объекта не привязаны никуда.
- Down-миграция сноса восстанавливает схему без данных (прецедент ADR 0046).
