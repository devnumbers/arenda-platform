# Списание платных запланированных downgrade при применении: дизайн и верификация

Дата: 2026-07-21. Статус: реализовано, проверено локальным E2E и регрессионными тестами.

## Контекст

Запланированный downgrade применялся бесплатно (ADR 0008 §3): в момент применения списания не было, новый тариф просто начинал продлеваться на обычном цикле. Для downgrade на бесплатный basic это корректно, но для downgrade на **платный** тариф это дыра в монетизации: business → pro/year дарил пользователю бесплатный год pro до первого продления. Решение: запланированный downgrade на платный тариф списывается **в момент применения** через существующий renewal-путь; downgrade на бесплатный тариф остаётся бесплатным. Этот документ фиксирует: проблему → решение → найденный при E2E баг → проверку.

## Реализация — gate в `ProcessScheduledChanges`, списание через renewal-путь

- В `application/scheduled_change_service.go` добавлен gate: `applyScheduledChange` теперь возвращает `(bool, error)`. Если цена pending-тарифа за pending-период > 0, изменение **не применяется** — пишется info-лог «paid scheduled downgrade left for renewal charge», подписка остаётся в выборке due-записей для renewal-пути (skip не считается ни ошибкой, ни обработанной записью). Если цена == 0 (на практике — basic), применение идёт по-прежнему бесплатным путём без изменений.
- Renewal-путь уже умел всё необходимое: `resolveRenewalTariffAndAmount` (`application/renewal_service.go`, ветка pending) резолвит pending-тариф/период/цену, успешное списание применяет изменение и архивирует избыточные объекты сверх лимита, неуспешное переводит подписку в grace. `ScheduleDowngrade` выставляет `auto_renew_enabled = true`, поэтому due-записи с pending-изменением попадают в выборку продлений.
- `ProcessScheduledChanges` запускается в том же тикe биллинг-воркера перед `ProcessRenewals`: пропущенный платный downgrade тут же подхватывается renewal-списанием, а batch-цикл не крутится вхолостую на skip-записях (warn «batch made no progress» теперь пишется только когда прогресса нет из-за одних ошибок).

## Баг, найденный E2E и тут же исправленный — grace с due pending-изменением ломал CHECK

- Проблема: вход в grace при наличии due запланированного downgrade нарушал CHECK-ограничение `user_subscriptions_pending_change_at_check` (`pending_change_at IS NULL OR pending_change_at >= valid_until`): `EnterGrace` поднимает `valid_until` до `now+7d`, а `pending_change_at <= now` оказывался меньше нового `valid_until` → SQLSTATE 23514, транзакция перевода в grace откатывалась, подписка застревала в состоянии active с истёкшим `valid_until`, и воркер повторял неудачную попытку каждый тик.
- Почему не поймали юнит-тесты: fake-репозитории не воспроизводят SQL CHECK-ограничения; баг проявился только на реальном Postgres в E2E.
- Фикс: `EnterGrace` (`domain/subscription.go`) очищает `pending_*` через `ClearPendingChange` — запланированное изменение считается потреблённым неуспешным списанием, вызвавшим grace; повторное планирование после продления — это новое действие пользователя. Заодно это снимает нарушение ограничения.

## E2E-верификация (локально, `PAYMENT_PROVIDER=fake`, реальный Postgres)

Все сценарии пройдены:

- business + рабочая карта → запланирован downgrade на pro/year → применение: платёж `pro/year 440000 коп succeeded`, подписка `active pro/year` с `valid_until` +1 год, `pending_*` очищены, 3 объекта сверх лимита заархивированы, в API `currentPeriod="year"`;
- fail-карта → применение: платёж `failed` (с сохранённым `error_code`), подписка `grace/business`, `pending_*` очищены, ошибки CHECK-ограничения нет;
- downgrade на basic → применяется без какого-либо платежа, архивация сверх лимита работает.

Регрессия: `go test ./internal/billing/...` — полностью зелёные.

## Замечание о fake-провайдере (local-testing caveat)

`fake.Status` возвращает `succeeded` для неизвестных ему provider payment ID. Поэтому после перезапуска бэкенда «заставший» pending-платёж в локальных экспериментах может ложно считаться успешным — это особенность только локального тестирования с fake-провайдером, на stage/prod-провайдеров не распространяется.
