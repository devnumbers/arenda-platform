# Research #726: UA-парсинг и оффлайн GeoIP для Go

**Дата исследования:** 2026-09-16. Все версии, даты коммитов и лицензии проверены по первоисточникам в этот день (Go module proxy `proxy.golang.org`, GitHub API, официальные страницы лицензий, исходные коды библиотек скачаны и просмотрены локально).

---

## 1. Контекст

**Задача:** на каждой сессии пользователя показывать: тип устройства (смартфон/компьютер — иконка), браузер + мажорную версию («Chrome 121»), время последней активности, город по IP («Москва»). Город фиксируется при создании сессии и обновляется при смене IP. Определение — на бэкенде, оффлайн, без внешних HTTP-API в рантайме. Аудитория — Россия.

**Факты по коду (проверено 2026-09-16):**

- Клиентский IP уже извлекается и нормализуется в `RealIPMiddleware` (`apps/backend/internal/platform/httpsupport/real_ip_middleware.go`): с учётом доверенных прокси разбираются `X-Forwarded-For` / `X-Real-IP`, итог кладётся в `requestctx.WithClientIP(...)`. Аудит берёт IP именно оттуда (`internal/audit/application/recorder.go`: `entry.IP = requestctx.ClientIPFromContext(ctx)`). Это готовая точка интеграции и для UA-парсинга, и для GeoIP — второй раз «доставать» IP из запроса не нужно.
- UA нигде не парсится и не сохраняется.
- Таблица `sessions` (`db/migrations/000001_init_schema.up.sql`) сейчас содержит только `id, user_id, token_hash, expires_at, created_at` — нет ни IP, ни `last_seen_at`, ни UA/города. Всё это добавляется новой миграцией.
- Деплой: GitHub Actions → GHCR (Docker-образ, multi-stage, `debian:bookworm-slim`, non-root, миграции копируются в образ) → SSH. На сервере ничего не собирается и не правится руками (docs/deployment.md, ADR 0024/0045). Значит, естественная стратегия для базы — «печь в образ».

### 2.2. Рекомендация

**Библиотека: `github.com/LumenResearch/uasurfer`** (fallback-вариант — `medama-io/go-useragent`).

Почему uasurfer:

1. **Тип устройства — его специализация**: возвращает `DeviceType` константой (phone/tablet/computer/TV/wearable/console) — ровно то, что нужно для иконки. Конкуренты дают либо «сырой» device family (uap-go), либо покрытие уже (medama).
2. Даёт браузер (имя + major/minor/patch) — «Chrome 121» строится тривиально; мажор не страдает от Chromium UA reduction (заморожены только минор/патч).
3. Apache-2.0, активная разработка (август 2026), поддерживает client hints (`ParseWithHints`) — если позже захотим отличать iPad в режиме десктопа, можно передать `Sec-CH-UA-Form-Factors` с фронтенда. Для MVP достаточно обычного `Parse(ua)`.
4. Распознаёт Яндекс.Браузер (проверено по исходникам `browser.go`).

Порядок в бэклоге второй кандидат: **medama** (живее всех, MIT, но сам признаёт более узкое покрытие хвоста UA — а для РФ-хвоста вроде Mi Browser / Samsung Internet покрытие важнее скорости).

**Чем парсить: один раз при создании сессии, не в middleware на каждый запрос.**

- Сессия привязана к браузеру (cookie `session_id` в рамках одного браузера) — UA сессии не меняется. Парсить на лету в middleware — тратить CPU на каждый запрос ради неизменного результата.
- На запросе нужен только `last_seen_at` (+ опционально город при смене IP), UA парсится при логине: `type → device_type`, `browser → browser + browser_major`, сырая строка сохраняется рядом.
- Сохранение сырого UA-текста обязательно: если через год захотим richer-данные (ОС, модель) — перепарсим существующие сессии новым алгоритмом без ожидания пользователей.
- Замечание про скорость: известная претензия к regex-парсерам (uap-go issue #59 — «parser is very slow») неприменима к нашему режиму «1 парс на логин».

### 3.2. Рекомендация

**Основная база: MaxMind GeoLite2 City + `oschwald/geoip2-golang`.**

Аргументы:

1. **Точность уровня города для РФ**: абсолютных публичных цифр ни у кого нет; MaxMind — единственная база, у которой данные обновляются 2 раза в неделю и которая прямо показывает per-country accuracy в своём инструменте. По совокупности (свежесть + покрытие мира на случай foreign IP + аудит независимых валидаций) это самый безопасный выбор. Синдром «Sypex точнее по РФ» основан на бенчмарках 2012–2016 годов; сегодня у Sypex главное преимущество — русские названия и малый вес (21 МБ), но не подтверждаемая свежесть данных.
2. **Экосистема MMDB**: читается поддерживаемым ISC-ридером, локаль `ru` из коробки (city name «Москва» без своих справочников), свободно тестируется в unit-тестах на маленьком самодельном mmdb.
3. **Лицензия для нашего кейса допустима**: закрытый SaaS = «internal business purposes»; атрибуция MaxMind добавляется в UI (подвал/страница «Устройства» — «IP geolocation by MaxMind»); образ в приватном GHCR не является редистрибуцией третьим лицам. Единственное реальное обязательство — **регулярно обновлять базу** (EULA требует уничтожать копии старше 30 дней после релиза) — решается планировщиком CI (раздел 4).
4. **План Б (зафиксировать в тикете): DB-IP City Lite** — если по какой-то причине не хотим аккаунт MaxMind и секрет в CI: CC BY 4.0 позволяет скачивать базу в CI вообще без регистрации и ключей и свободно класть в образ (даже в git), ценой — 121 МБ mmdb и ежемесячная свежесть.

**Sypex Geo не рекомендую**, несмотря на то, что проект жив (City Free от 2026.08.31): нестандартный формат, Go-биндинги — брошенные хобби-проекты, лицензия на редистрибуцию не формализована (в образ печём — ок, но юридической определённости нет), вендор-риск. Держать в уме как вариант, если реальная точность GeoLite2 по РФ-городам окажется неудовлетворительной.

**ipinfo — отпадает** (город только платно), **IP2Location LITE — не рекомендуется**: регистрация, ограничения редистрибуции, отсутствие mmdb, слабая видимость точности по РФ.

## 4. Схема доставки базы для нашего деплоя

Рассмотренные варианты:

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **База в git-репо** | Простой `COPY` | 44–67 МБ бинарника в истории git; GeoLite2 EULA ограничивает редистрибуцию (репо приватное, но правило всё равно лишнее); обновление = мусорные коммиты | Нет |
| **База в Docker-образе (скачивание в CI при сборке)** | Иммутабельный образ (ADR 0024/0045); секрет только в GitHub Secrets; ноль внешних зависимостей в рантайме; обновление = плановая пересборка | База свежая ровно настолько, насколько часто пересобирается образ; для города по IP протухание на недели не меняет результат | **Да** |
| **Скачивание при старте контейнера** (geoipupdate в контейнере, токен на сервере) | Всегда свежая база | Внешняя зависимость на старте (недоступность MaxMind = деградация старта), секрет на сервере, лишняя логика отказа, расход лимита 30 скачиваний/сутки на каждый рестарт | Нет |
| **geoipupdate сайдкаром + volume** | Свежесть без пересборки | Состояние на сервере, оркестрация не предусмотрена деплоем (systemd + SSH), усложнение | Нет |
| **Go-библиотека со встроенной базой** | — | Для города такой не существует (база десятки МБ); любые «встроенные» либы = протухшие данные и мутные лицензии | Нет |

**Рекомендуемая схема (база в образе + еженедельная пересборка):**

1. Зарегистрировать бесплатный аккаунт MaxMind, сгенерировать License Key, положить в GitHub Secrets как `MAXMIND_LICENSE_KEY` (account id рядом: `MAXMIND_ACCOUNT_ID`).
2. В `apps/backend/Dockerfile` на стадии build: установить/скачать `geoipupdate` (Apache-2.0, есть готовые бинарники) либо просто `curl` tar.gz по подписи с ключом → `GeoLite2-City.mmdb`; на стадии runtime — `COPY --from=build ... /app/geoip/GeoLite2-City.mmdb` (образ и так ≈; +50–70 МБ несжимаемого слоя — приемлемо).
3. GitHub Actions: добавить `schedule: cron` (раз в неделю, вторник/пятница — после релизов MaxMind) на пересборку образа. Обновление подхватывается при ближайшем деплое; 30-дневное требование EULA выполняется с запасом.
4. Конфиг бэкенда: `GEOIP_DB_PATH=/app/geoip/GeoLite2-City.mmdb`, локали ридера `[]string{"ru", "en"}`. **База отсутствует/не открылась → сервис полностью работоспособен, город просто не пишется** (NULL) — деградация, а не отказ. Это же поведение используется локально у разработчиков без базы.
5. Атрибуция: строка «Данные о городах — MaxMind GeoLite2» в UI рядом со списком устройств.
6. Тесты: tiny fixture `.mmdb` (несколько диапазонов, генерируется `mmdbwriter` из тех же oschwald-пакетов) коммитится в тесты — в git попадает тестовая фикстура на килобайты, не реальная база.

## 5. Хранение, обновление, пограничные случаи

### 5.1. Схема хранения (расширение `sessions`)

Города по IP — медленно меняющиеся данные; хранить достаточно **строкой**, как и предполагает тикет, но с двумя уточнениями:

```sql
ALTER TABLE sessions
  ADD COLUMN last_seen_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  ADD COLUMN last_ip INET,
  ADD COLUMN user_agent TEXT NOT NULL DEFAULT '',
  ADD COLUMN device_type TEXT NOT NULL DEFAULT 'unknown',   -- phone | computer | tablet | tv | unknown
  ADD COLUMN browser TEXT NOT NULL DEFAULT '',              -- Chrome, YaBrowser, Safari...
  ADD COLUMN browser_major INT,
  ADD COLUMN country_code TEXT,                             -- ISO 3166-1, из GeoIP
  ADD COLUMN city TEXT;                                     -- имя города в локали ru, NULL если не определён
```

- `last_ip INET` — PostgreSQL-тип, удобно для сравнения (`inet` сравнивается оператором `<>`), и audit-писатель уже хранит IP совместимо.
- Сырой `user_agent` храним всегда — перепарсинг в будущем (обоснование в 2.2).
- «Время последней активности» = `last_seen_at`; обновлять на авторизованных запросах (лёгкий UPDATE с условием `WHERE last_seen_at < now() - interval '1 minute'`, чтобы не писать на каждый чих).

### 5.2. Порог «смены IP» — при наличии локальной базы порог не нужен, нужен порог записи

Поскольку резолв локальный (микросекунды, без платных API), предложение тикета «считать сменой новый /24» избыточно и лишь откладывает обновление города. Логика:

1. На запросе: если `last_ip <> current_ip` → ре-резолв города по `current_ip`.
2. Пишем `UPDATE sessions SET last_ip, city, country_code ...` **только если изменился результат** (`city`/`country_code`/`last_ip`). Если IP сменился, а город тот же — обновляем только `last_ip`; если город сменился — оба. Отсюда естественный анти-churn: гуляние по /24 внутри того же города не порождает апдейтов города.
3. Резолвить город можно прямо там же, где аудит берёт IP (`requestctx.ClientIPFromContext`), в хендлере, который и так обновляет `last_seen_at`.

### 5.3. Неизвестные и особые IP

| Случай | Поведение |
|---|---|
| Loopback `127.0.0.0/8`, `::1`, приватные RFC1918 (`10/8`, `172.16/12`, `192.168/16`), ULA IPv6 `fc00::/7`, CGNAT `100.64/10`, link-local `169.254/16` | Гео не резолвим: `city = NULL`, в UI «—». Существующее значение города **не затирать** («неизвестный» не означает «город пропал») |
| IP не нашёлся в базе (новые диапазоны, `0.0.0.0`) | То же: NULL, старое значение сохранить |
| Локальная разработка / healthcheck | Покрывается правилом выше |
| VPN/прокси | Определяется город **выходного узла** — это ожидаемое поведение всех оффлайн-баз; GeoLite2 не содержит флагов анонимности (это платные БД MaxMind) — лечить не пытаемся |
| Мобильные операторы (CGNAT) | Город часто резолвится в хаб оператора, а не в фактическое положение — известное ограничение данных; в UI подпись «город определён приблизительно» снимает вопросы поддержки |
| IPv6 | GeoLite2 City покрывает IPv6, `oschwald`-ридер принимает `netip.Addr` (v2) / `net.IP` (v1) — ничего специального не нужно |
| Локаль названий | Открывать ридер с `[]string{"ru","en"}`: если русского имени у geoname нет — вернётся английское (документированное поведение полей локалей) |
