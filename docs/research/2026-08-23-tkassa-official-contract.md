# Контракт Т-Кассы по официальной документации

Дата: 2026-08-23
Вход для: ревью интеграции интернет-эквайринга Т-Кассы в `apps/backend/internal/billing/adapters/payment/tkassa/` (ADR 0016/0017). Справочник фиксирует контракт провайдера строго по официальным источникам, чтобы ревьюер сверял код с первоисточником, а не с пересказами.

Источники (официальный портал разработчика Т-Банка; зеркала `developer.tbank.ru` ≡ `developer.tinkoff.ru`):

- OpenAPI-спека (артефакт портала): <https://developer.tbank.ru/schemas/eacq/openapi.yaml> — версия **1.28**, та же, что вендорена у нас (см. §10).
- Руководство разработчика: [Токен](https://developer.tbank.ru/eacq/intro/developer/token), [Уведомления об операциях](https://developer.tbank.ru/eacq/intro/developer/notification), [Тестовая среда](https://developer.tbank.ru/eacq/intro/errors/test), [Коды ошибок платежей](https://developer.tbank.ru/eacq/intro/errors/error-codes).
- Методы API: [Init](https://developer.tbank.ru/eacq/api/init), [Charge](https://developer.tbank.ru/eacq/api/charge), [GetState](https://developer.tbank.ru/eacq/api/get-state), [Confirm](https://developer.tbank.ru/eacq/api/confirm), [Cancel](https://developer.tbank.ru/eacq/api/cancel), [FinishAuthorize](https://developer.tbank.ru/eacq/api/finish-authorize), [AddCard](https://developer.tbank.ru/eacq/api/add-card), [GetAddCardState](https://developer.tbank.ru/eacq/api/get-add-card-state), [GetCardList](https://developer.tbank.ru/eacq/api/get-card-list), [RemoveCard](https://developer.tbank.ru/eacq/api/remove-card).
- Сценарии: [получение данных о платеже](https://developer.tbank.ru/eacq/scenarios/notification/), [карточные платежи](https://developer.tbank.ru/eacq/scenarios/payments/nonPCI/card/), [платежи по сохранённым реквизитам](https://developer.tbank.ru/eacq/scenarios/payments/nonPCI/autopay/).

Все факты ниже — из этих страниц/спеки, если прямо не помечено иное. Спека 1.28 скачана с upstream 2026-08-23 и разобрана построчно; свёрнутые таблицы страниц методов недоступны статическому фетчу — такие пункты помечены «не подтверждено по статической странице» с лучшей доступной ссылкой.

## Резюме

1. Протокол: POST JSON на `https://securepay.tinkoff.ru/v2/<Method>` (тест — `https://rest-api-test.tinkoff.ru/v2`), аутентификация парой TerminalKey/Password из Т-Бизнес через подпись `Token` (SHA-256, только корневые поля, `Password` в наборе, сортировка по ключу, конкатенация значений).
2. `Amount` — **int64 в копейках** на всех денежных полях; оплата только в RUB.
3. Init возвращает `PaymentId` + `PaymentURL` (ссылка на платёжную форму банка) + статус; браузер возвращается по `SuccessURL`/`FailURL`, статус asynchronously приходит webhook'ом.
4. Привязка карты: `AddCustomer` → `AddCard` (`CheckType=3DSHOLD`) → форма банка → webhook `NotificationAddCard` (`RequestKey`, `CardId`, `RebillId`) и/или поллинг `GetAddCardState` (8 статусов, терминальный — `COMPLETED`).
5. Рекурренты: родительская CC-операция (`Init` с `Recurrent=Y`+`CustomerKey`, `OperationInitiatorType=1` CIT CC) выдаёт `RebillId` в уведомлении на `AUTHORIZED`; списание — `Init`(`OperationInitiatorType=R`) + `Charge`(`PaymentId`,`RebillId`) без переадресации; `Amount` в `Charge` не предусмотрен — сумма задаётся в `Init`.
6. Webhooks: JSON POST на `NotificationURL` (per-request перекрывает терминальный), банк ждёт ответ **10 секунд**, требует **HTTP 200 с телом `OK`** (без тегов, заглавными); ретраи — раз в час 24 часа, затем раз в сутки месяц, потом архив на 90 дней. Подпись входящих проверяется тем же Token-алгоритмом.
7. Статусы: словарь из 24 значений в enum'е спеки; терминальные успех/провал для одностадийной оплаты — `CONFIRMED`/`REJECTED`; в спеке 1.28 **нет** `ASYNC_REFUNDING`, `PARTIAL_REVERSED`, `3DS_FAILED` (адаптер их обрабатывает — легаси-словарь, см. §6).
8. Проверка статуса: актуальный метод — `GetState` (по `PaymentId`); по `OrderId` — отдельный `CheckOrder`. Источник истины — webhook, `GetState` — сверка/восстановление.
9. Возвраты: единый `Cancel` — и отмена (до подтверждения), и полный/частичный возврат (`Amount` в копейках; `ExternalRequestId` — идемпотентный ключ).
10. Сверка спеки: upstream по-прежнему **1.28**, URL из `spec/README.md` (`generate.go` содержит только `//go:generate`) актуален; единственное байтовое расхождение вендоренной копии — значение `example` в поле `AcsSignedContent` (3DS-секция), на типы не влияет.

## 1. Общий протокол

Факты из вводной части спеки 1.28 (`info.description`) и страниц методов:

- **Метод вызова**: все методы — `POST`, тело JSON, заголовок `Content-Type: application/json`. «Все методы и передаваемые параметры чувствительны к регистру».
- **TLS**: «Для корректной работы с API-методами используйте TLS протокол версии 1.2 и выше».
- **Базовые URL** (из `servers` спеки и страниц методов): production — `https://securepay.tinkoff.ru/v2/…`; test — `https://rest-api-test.tinkoff.ru/v2/…`. Домен до сих пор `tinkoff.ru`, не `tbank.ru`.
- **Валюта**: «оплата проходит только в рублях. Если мерчанту нужна оплата в валюте, он самостоятельно реализует логику конвертации суммы в запросе на своей стороне» (совпадает с ADR 0036).
- **Аутентификация**: пара `TerminalKey` + `Password` терминала, выдаётся в Т-Бизнес при заведении терминала. Password «можно найти в личном кабинете интернет-эквайринга» (`business.tbank.ru/oplata/main`). Заголовочной авторизации нет — UI портала рисует «Bearer API Token» на страницах методов, но в теле реальная аутентификация — `TerminalKey` + подпись `Token`.
- **Подпись Token** («подпись запроса»; официальная страница не версионирует алгоритм — то, что сообщество зовёт «Token v2», на портале просто «Токен»). Алгоритм дословно со [страницы токена](https://developer.tbank.ru/eacq/intro/developer/token):
  1. «Соберите массив передаваемых параметров в виде пар ключ:значение» — «В массив нужно добавить только параметры корневого объекта — вложенные объекты и массивы не участвуют в формировании токена» (значит `DATA`/`Data`/`Receipt` и любые вложенные структуры исключаются; исключается и сам `Token`).
  2. «Добавьте в массив пару `{"Password": "Значение пароля"}`».
  3. «Отсортируйте массив по алфавиту по ключу».
  4. «Конкатенируйте только значения пар в одну строку» (без разделителей).
  5. «Примените к строке хеш-функцию SHA-256 (с поддержкой UTF-8)» → hex-строка.
  6. «Добавьте получившийся результат в значение параметра Token в тело запроса».
- Тот же алгоритм для **проверки входящих уведомлений**, с явным списком исключений: «кроме параметра Token и вложенных объектов (Data, Receipt)» (страница уведомлений).
- Диагностика подписи в ЛК: Операции → заказ → блок «Дополнительная информация» → `inittokenisvalid` (true/false).
- Официальных лимитов RPS/QPS и рекомендаций по таймаутам клиента на портале нет — есть только коды «повторите позже» (§9). Не подтверждено по офиц. источнику: единый публичный SLA API.

## 2. Init (`/v2/Init`)

Назначение ([страница](https://developer.tbank.ru/eacq/api/init) + спека): «Метод инициирует платеж» — создаёт платёж и возвращает ссылку на платёжную форму банка.

Обязательные параметры:

| Параметр | Тип/лимит | Описание (дословно) |
|---|---|---|
| `TerminalKey` | string ≤64 | «Идентификатор терминала. Выдается мерчанту в Т‑Бизнес при заведении терминала.» |
| `Amount` | integer int64 | «Сумма в копейках. Например, 3 руб. 12коп. — это число 312.» Должен равняться сумме `Amount` позиций `Items` чека. |
| `OrderId` | string ≤50 | «Идентификатор заказа в системе мерчанта. Должен быть уникальным для каждой операции.» |
| `Token` | string | «Подпись запроса.» |

Ключевые необязательные:

- `Description` — string ≤140 («Значение параметра будет отображено на платежной форме»); для карт допускается 250, для СБП и платежей по сохранённым реквизитам — 140.
- `CustomerKey` — string ≤255; «Нужен для сохранения карт на платежной форме»; **обязателен, если передан `Recurrent=Y` и автоплатеж проводится по карте**; если передан — в уведомлении будут `CustomerKey` и `CardId`.
- `Recurrent` — enum `[Y]`; «Признак родительского CC-платежа. Обязателен для проведения операции с сохранением реквизитов карты покупателя. Если передается и установлен в `Y`, при платеже будут сохранены реквизиты карты покупателя. В этом случае после оплаты в уведомлении на `AUTHORIZED` будет передан параметр `RebillId`».
- `PayType` — enum `[O, T]`: «O — одностадийная оплата; T — двухстадийная оплата»; если не передан — берётся из настроек терминала.
- `NotificationURL` / `SuccessURL` / `FailURL` — uri; URL для POST-уведомлений о статусе и возврата покупателя при успехе/неудаче; «Если параметр передан, используется его значение, если нет — значение из настроек терминала».
- `RedirectDueDate` — date-time, «Срок жизни ссылки или динамического QR-кода СБП»; минимум 1 минута, максимум 90 дней от текущей даты; формат `YYYY-MM-DDTHH24:MI:SS+GMT`; при отсутствии — настройка терминала REDIRECT_TIMEOUT (по умолчанию 1440 минут).
- `DATA` — объект oneOf `Common`/`TPay`/`LongPay`; «Максимальная длина ключа — 20 знаков, значения — 100 знаков», до 20 пар, спецсимволы — urlencode. В `Common.DATA.OperationInitiatorType` (string) — признак инициатора операции: «Параметр обязательный при создании родительского CC-платежа при оплате картой»; значения `0` (обычный), `1` (CIT CC), `2` (CIT COF), `R` (MIT COF Recurring), `I` (MIT COF Installment), `D` (MIT COF Delayed-Charge), `N` (MIT COF No-Show); несочетаемость с `RebillId`/`Recurrent` → ошибка **1126**.
- `Receipt` — объект чека, «Обязателен, если подключена онлайн-касса» (ФФД 1.05/1.2).
- `Language` (`ru` по умолчанию / `en`).

Ответ (`InitResponse` спеки; required: TerminalKey, Amount, OrderId, Success, PaymentId, ErrorCode, Status):

- `PaymentId` — string ≤20, «Идентификатор платежа в системе Т‑Бизнес» (числовая строка).
- `PaymentURL` — uri ≤100, «Ссылка на платежную форму. Параметр возвращается только для мерчантов, которые используют платежную форму Т‑Банка».
- `Status` — enum `SessionStatusEnum`: `NEW` (платеж создан), `AUTHORIZED` (авторизован), `CONFIRMED` (подтверждён), `REVERSED` (отменён), `REFUNDED` (возврат выполнен), `PARTIAL_REFUNDED` (частичный возврат), `REJECTED` (отклонён), `DEADLINE_EXPIRED` (срок жизни истёк), `3DS_CHECKING`, `3DS_CHECKED`, `FORM_SHOWED` (форма показана).
- `Success` (bool), `ErrorCode` (string, `0` = нет ошибки), `Message`, `Details`, `Amount`, `OrderId`, `TerminalKey`.

Семантика ответа: `Success=true` означает успех **вызова API**, не платежа; исход платежа определяется `Status` (и webhook'ами). HTTP-коды: 200 — OK, 500 — «Внутренняя ошибка сервера».

## 3. Привязка карты

Контракт «покупатель + карты» (спека, тег «Привязка карты»; сценарий [nonPCI/card](https://developer.tbank.ru/eacq/scenarios/payments/nonPCI/card/); «Обработка и хранение данных по картам покупателей происходит на стороне Т‑Банка»):

- **AddCustomer** (`/v2/AddCustomer`): `TerminalKey`, `CustomerKey` (≤255), `Token`. Создание покупателя. Повторное создание существующего — код **7** «Неверный статус покупателя» (страница [кодов ошибок](https://developer.tbank.ru/eacq/intro/errors/error-codes)).
- **AddCard** (`/v2/AddCard`, «Метод инициирует привязку карты к покупателю»). Запрос по офиц. схеме: `TerminalKey` (≤64), `CustomerKey` (≤255), `Token` — обязательные; `CheckType` — enum `NO`/`HOLD`/`3DS`/`3DSHOLD`, «Если CheckType не передается, автоматически проставляется значение NO»:
  - `NO` — «сохранить карту без проверок. RebillID для рекуррентных платежей не возвращается»;
  - `HOLD` — «при сохранении сделать списание на 0 руб. RebillID возвращается для терминалов без поддержки 3DS»;
  - `3DS` — проверка 3DS + списание 0 руб.; «RebillID будет возвращаться только для карт с поддержкой 3DS. Карты, которые не поддерживают 3DS, привязаны не будут»;
  - `3DSHOLD` — «при привязке карты выполнить проверку, поддерживает карта 3DS или нет. Если карта не поддерживает 3DS, выполняется списание на 0 руб.» (RebillId выдаётся всегда — потому и выбран у нас, ADR 0017).
  - Плюс `IP` и `ResidentState` (bool; true — карта РФ, false — не РФ, null — универсальная).
  - **URL-полей в официальной схеме AddCard нет** — ни `NotificationURL`, ни `SuccessAddCardURL`/`FailAddCardURL`, ни легаси `RedirectUrl`/`FailRedirectUrl`. Подтверждено и схемой 1.28, и страницей метода. Страница уведомлений при этом говорит: «Чтобы изменить значение этого параметра [NotificationURL] для метода Инициировать привязку карты, обратитесь к персональному менеджеру или в поддержку банка» — то есть URL привязки настраивается на уровне терминала, per-request передача недокументирована.
- **Ответ AddCard** (`AddCardResponse`; required: PaymentId, TerminalKey, CustomerKey, RequestKey, Success, ErrorCode, PaymentURL): `RequestKey` — «Идентификатор запроса на привязку карты» (uuid-строка в примере), `PaymentURL` — ссылка на форму привязки. Форму банк ждёт, «уведомление отправляется на ваш сайт на адрес NotificationURL и ждет ответа в течение 10 секунд».
- **Webhook add-card** (`NotificationAddCard`, страница уведомлений): поля — `TerminalKey`, `CustomerKey`, `RequestKey`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `CardId`, `Pan`, `ExpDate`, `NotificationType`, `RebillId` — «параметр передается, если был присвоен во время привязки». Точное wire-значение `NotificationType` — **не подтверждено по статической странице** (таблица параметров свёрнута в JS; в легаси-доке Тинькофф значение было `ADD_CARD`; раздел на портале называется NotificationAddCard). Успешная привязка — `Status=COMPLETED` + `Success=true` (семантика из словаря `GetAddCardState`, ниже).
- **GetAddCardState** (`/v2/GetAddCardState`, «Метод возвращает статус привязки карты»): запрос `TerminalKey`, `RequestKey`, `Token` (все обязательные). Ответ содержит `Status` (8 значений с дословными описаниями): `NEW` — создана; `FORM_SHOWED` — форма показана; `3DS_CHECKING` — идёт проверка 3DS; `3DS_CHECKED` — «покупатель успешно прошел проверку 3DS»; `AUTHORIZING` — «отправка платежа на 0 руб.»; `AUTHORIZED` — «платеж на 0 руб. прошел успешно»; `COMPLETED` — «карта успешно привязана»; `REJECTED` — «привязать карту не удалось». Плюс `CardId`, `RebillId`, `CustomerKey`, `RequestKey`, `Success`, `ErrorCode`, 3DS-поля (`ACSUrl`, `MD`, `PaReq`…).
- **Срок жизни сессии привязки (RequestKey)** — **не подтверждено по офиц. источнику**: ни на странице AddCard, ни на GetAddCardState, ни в спеке 1.28 TTL сессии не указан. Лучшая ссылка — [get-add-card-state](https://developer.tbank.ru/eacq/api/get-add-card-state).
- **GetCardList** (`/v2/GetCardList`, «Метод возвращает список всех привязанных к терминалу карт покупателя, включая удаленные»): запрос `TerminalKey`, `CustomerKey`, `Token` (обязательные), `SavedCard` (bool), `IP`. Ответ — массив карточек `CardId` / `Pan` / `ExpDate` / `RebillId` / `Status`. Значения `Status` карты: в примерах спеки встречаются `A` и `D`; устоявшийся словарь A=активна / I=временно неактивна / D=удалена — **не подтверждён по статической странице** (таблица ответа свёрнута; A/D подтверждаются примерами спеки, семантика I — легаси-дока). Метод требует фильтрации удалённых/неактивных на стороне мерчанта, раз «включая удаленные».
- **RemoveCard** (`/v2/RemoveCard`, «Метод удаляет привязанную карту покупателя»): запрос `TerminalKey`, `CustomerKey` (≤36), `CardId` (≤40), `Token` (обязательные), `IP`. Ответ: `CardId`, `CustomerKey`, `TerminalKey`, `Success`, `ErrorCode` (+`Message`).
- Коды ошибок блока привязки: 6 (не получилось привязать), 7 (неверный статус покупателя), 500 (добавление карты запрещено для терминала), 501 (терминал не найден), 502 (карта по RequestKey не найдена), 503 (CustomerKey не найден), 504/505 (внутренние ошибки платежа/привязки), 506/600 (карта в чёрном списке), 507/106/108 (карта без 3DS / только 3DS-карты), 510 (карта уже привязана к CustomerKey), 511/512/513 (3DS не пройден/ошибки), 381/382 (резидентность).

## 4. Рекуррентные платежи (COF/RebillId)

По [сценарию автоплатежей](https://developer.tbank.ru/eacq/scenarios/payments/nonPCI/autopay/) и спеке:

- **Модель**: родительская **CC-операция** (Credential Capture) сохраняет реквизиты; дочерние **COF-операции** (Credential On File) списывают по ним; «несколько дочерних платежей на один родительский — в зависимости от их типа». Родителем может быть CC-покупка (обычная оплата с `Recurrent=Y`) или CC-привязка (`AddCard`). Для CC-авторизации покупатель «должен обязательно пройти аутентификацию (с поддержкой 3D Secure) или ввести CVV».
- **Получение RebillId**: «После авторизации мерчант получает RebillId в уведомнении» — для CC-покупки это уведомление на `AUTHORIZED` (Init: «в уведомлении на AUTHORIZED будет передан параметр RebillId»), для привязки — add-card уведомление/`GetAddCardState`. `RebillId` — «Уникальный идентификатор сохраненных платежных реквизитов покупателя». В нашей терминологии это charge token.
- **Списание (операция называется «Провести платеж по сохраненным реквизитам», метод Charge)**: последовательность по сценарию — (1) вызвать `Init` с нужным `Amount`; (2) «Без переадресации на PaymentURL» вызвать `Charge`, передав `PaymentId` (от Init) и `RebillId` (от родительской CC-операции). «Выполняет безакцептное списание средств со счета покупателя на основании сохраненных реквизитов и параметра RebillId». **Поля `Amount` в схеме ChargeRequest нет** — сумма берётся из Init (обязательные параметры Charge: `TerminalKey`, `PaymentId` (≤20), `RebillId`, `Token`; необязательные: `IP`, `SendEmail`/`InfoEmail`).
- **CIT/MIT-семантика** (`OperationInitiatorType`): родительская CC-покупка — `1` (CIT CC) + `Recurrent=Y` + `CustomerKey`; рекуррентное списание — Init с `R` (MIT COF Recurring); разовые списания по сохранённой карте покупателем — `2` (CIT COF); `I`/`D`/`N` — рассрочка/отложенные списания/no-show. «Если передавать значения параметров, которые не соответствуют таблице, MAPI вернет ошибку 1126 — несопоставимые значения rebillId или Recurrent с переданным значением OperationInitiatorType» (её же текст в [кодах ошибок](https://developer.tbank.ru/eacq/intro/errors/error-codes)).
- **Ограничения**: `D` (Delayed-Charge) и `N` (No-Show) требуют родительской CC-**покупки**, подтверждённой `Confirm`; «использовать операцию привязки карты в качестве CC-операции нельзя». Одно-/двухстадийность COF определяется `PayType`/настройками терминала (умолчание COF меняется через acq_help@tbank.ru). Функциональность по умолчанию выключена: включение через acq_help@tbank.ru (DEMO) или персонального менеджера (prod).
- **Уведомления Charge**: «Для метода Провести платеж по сохраненным реквизитам логика такая же [как для одностадийной оплаты]» — одновременно приходят **две нотификации, AUTHORIZED и CONFIRMED**, ответ ждётся 10 секунд.
- **Отказ карты при рекурренте**: специальной доктринальной страницы нет. Контракт отказа выражается статусом `REJECTED` в ответе/уведомлении + кодами ошибок: **104** «Ошибка выполнения рекуррента», 103/116 «Недостаточно средств», 119 «Превышено допустимое количество запросов авторизации операции», 106/108/507 «Карта не поддерживает 3DS» / «Оплата разрешена только по 3DS картам», 252/1033 «Срок действия карты истек», 262 «Истек срок действия родительского платежа», 1005–1034 — отказы банка-эмитента. Автоматическая инвалидация RebillId после N отказов **не подтверждена по офиц. источнику** (лучшие ссылки — [autopay](https://developer.tbank.ru/eacq/scenarios/payments/nonPCI/autopay/) и [коды ошибок](https://developer.tbank.ru/eacq/intro/errors/error-codes)).
- **Срок жизни RebillId** — **не подтверждено по офиц. источнику**: на портале TTL сохранённых реквизитов не указан; практика платежных систем (МИР/Visa/MC COF) — до истечения срока карты или отзыва, но это не документ Т-Банка. Отметить как риск: при ошибке 252/1033/104 токен следует считать мёртвым и требовать перепривязку.

## 5. Уведомления (webhooks)

По [странице уведомлений](https://developer.tbank.ru/eacq/intro/developer/notification):

- **Типы**: `NotificationPayment` (платёж), `NotificationAddCard` (привязка), `NotificationFiscalization` (фискализация; не отправляется для «Маркетплейс»), `NotificationQr` (привязка счёта по QR; только статусы ACTIVE/INACTIVE); отдельно описаны уведомления СБП (платёж/возврат). Разделы названы именно так; `NotificationType` — имя поля в теле.
- **Транспорт**: HTTP(S) POST JSON на `NotificationURL`. URL задаётся в настройках терминала (ЛК Т-Бизнес: Магазины → Терминалы → Настроить; варианты: почта, HTTP(S) или оба) или per-request в `Init`; «Если параметр передан, используется его значение, если нет — значение из настроек терминала». Для AddCard per-request смена недоступна — через менеджера/поддержку. «Если в NotificationURL используются порты, можно использовать порт 443 (HTTPS)».
- **Когда приходят**: `Init` — по сменам статусов; `Confirm`/`Cancel` — POST об операции; `FinishAuthorize` — при двухстадийной; при одностадийной (и для `Charge`) — «отправляется на ваш сайт на адрес NotificationURL и **ждет ответа в течение 10 секунд**. Сервис одновременно отправляет две нотификации — AUTHORIZED и CONFIRMED»; AddCard/AttachCard — тоже с ожиданием 10 секунд.
- **Формат NotificationPayment** (из токен-примера страницы — это официальный список полей): `TerminalKey`, `OrderId`, `Success` (bool), `Status`, `PaymentId`, `ErrorCode`, `Amount`, `CardId`, `Pan`, `ExpDate`, `RebillId`, `Token`. Для родительского CC-платежа `RebillId` приходит в нотификации `AUTHORIZED`. Дополнительные поля из `DATA` возвращаются в `Data` («учитывайте регистр»); значения null в формирование нотификации не попадают.
- **Формат NotificationAddCard**: `TerminalKey`, `CustomerKey`, `RequestKey`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `CardId`, `Pan`, `ExpDate`, `NotificationType`, `RebillId` (если присвоен).
- **Проверка подписи входящих**: тот же Token-алгоритм — собрать все поля «кроме параметра Token и вложенных объектов (Data, Receipt)», добавить `Password`, отсортировать по ключу, конкатенировать значения, SHA-256, сравнить с присланым `Token`.
- **Ожидаемый ответ**: «При успешной обработке уведомления вам нужно вернуть ответ HTTP CODE = 200 с телом сообщения OK — без тегов, заглавными английскими буквами».
- **Гарантии доставки/ретраи**: «Если ответ OK не получен, уведомление считается неуспешным. Сервис будет повторно отправлять его **раз в час в течение 24 часов, а затем раз в сутки в течение месяца**. Если за это время оно так и не будет доставлено, уведомление будет перемещено в архив. Уведомления хранятся в архиве **90 дней**. В течение этого времени вы можете запросить их повторную отправку».
- Полнотабличные описания каждого поля и JSON-примеры лежат в свёрнутых блоках страницы («Параметры в теле уведомления о платеже», «Пример уведомления о платеже») — статическому фетчу недоступны, приведённый выше список полей из официального токен-примера той же страницы.

## 6. Статусы платежей

Словарь из спеки 1.28 (два места):

- `SessionStatusEnum` (ответ `Init`, с дословными описаниями): `NEW` — платеж создан; `AUTHORIZED` — платеж авторизован; `CONFIRMED` — платеж подтверждён; `REVERSED` — платеж отменён; `REFUNDED` — возврат выполнен; `PARTIAL_REFUNDED` — частичный возврат; `REJECTED` — платеж отклонён; `DEADLINE_EXPIRED` — срок жизни платежа истёк; `3DS_CHECKING` — идёт проверка 3DS; `3DS_CHECKED` — проверка 3DS завершена; `FORM_SHOWED` — форма показана.
- Полный enum статуса транзакции (в `ConfirmResponse`; 24 значения): `NEW`, `AUTHORIZING`, `AUTHORIZED`, `AUTH_FAIL`, `CANCELED`, `CHECKING`, `CHECKED`, `COMPLETING`, `COMPLETED`, `CONFIRMING`, `CONFIRMED`, `DEADLINE_EXPIRED`, `FORM_SHOWED`, `PARTIAL_REFUNDED`, `PREAUTHORIZING`, `PROCESSING`, `3DS_CHECKING`, `3DS_CHECKED`, `REVERSING`, `REVERSED`, `REFUNDING`, `REFUNDED`, `REJECTED`, `UNKNOWN`. Короткая сводка из `FinishAuthorizeResponse.Status`: «Возвращается один из четырех статусов платежа: CONFIRMED — при одностадийной оплате; AUTHORIZED — при двухстадийной; 3DS_CHECKING — когда нужно пройти проверку 3D Secure; REJECTED — при неуспешном прохождении платежа».
- **В спеке 1.28 отсутствуют** `ASYNC_REFUNDING`, `PARTIAL_REVERSED`, `3DS_FAILED` (проверено грепом по upstream-файлу). Адаптер (`status.go`) их обрабатывает — это легаси-словарь старой доки Тинькофф; текущий официальный enum их не содержит. Семантика сохранившихся «процессных» статусов (`CHECKING`/`CHECKED`/`COMPLETING`/`COMPLETED`/`PREAUTHORIZING`/`PROCESSING`) в спеке 1.28 не описана поштучно — только факт присутствия в enum.
- Статусы привязки карты — см. §3 (8 значений `GetAddCardState`).

## 7. Проверка статуса: GetState

- Актуальный метод — **`GetState`** (`/v2/GetState`, summary «Получить статус платежа»): «Метод возвращает статус платежа» по `PaymentId`. Запрос: `TerminalKey`, `PaymentId` (≤20), `Token` (обязательные), `IP`, `GetPhone` (необязательные). Поиска по `OrderId` в GetState нет — для этого отдельный метод «Получить статус заказа» (`CheckOrder`, тег «Статус платежа или заказа»). Метода `GetPayment`/`CheckStatus` с такой семантикой в актуальной доке нет (ближайший сосед — `getConfirmOperation`, справка по операции для кассы).
- Ответ: `Success`, `TerminalKey`, `Status`, `PaymentId`, `OrderId`, `Amount`, `ErrorCode`, `Message`, `Details` + `RebillId` («Уникальный идентификатор сохраненных платежных реквизитов покупателя» — присутствует в схеме ответа GetState) и `Params` (Route/Source/…). Для СБП: «Ориентируйтесь на статус платежа», а не на ErrorCode.
- Когда вызывать: [сценарная страница](https://developer.tbank.ru/eacq/scenarios/notification/) перечисляет GetState как способ «получения данных по конкретному платежу» рядом с уведомлениями; уведомления — оперативный канал, GetState — сверка при пропуске/подозрении на дубль и подтверждение терминального статуса. Официальной иерархии «источник истины» страница не формулирует.

## 8. Finish/Confirm и возвраты

- **Two-step (PayType=T)**: Init → платёж доходит до `AUTHORIZED` (деньги заблокированы) → **`Confirm`** (`/v2/Confirm`, «Метод подтверждает списание денег со счета покупателя… Применим только к платежам в статусе AUTHORIZED. Сумма списания может быть меньше или равна сумме авторизации»). Запрос: `TerminalKey`, `PaymentId`, `Token` (обязательные), `Amount` (int64, копейки; «Если не передан, используется Amount, который был передан в методе Инициировать платеж»), `Receipt`, `IP`, `ClientInfo`. Ответ — `ConfirmResponse` (TerminalKey, OrderId, Success, Status, PaymentId, ErrorCode, Message).
- **`FinishAuthorize`** (`/v2/FinishAuthorize`) — «Для мерчантов c собственной платежной формой»: при одностадийной сразу списывает, при двухстадийной блокирует. Ключевое поле — `CardData` (PAN/ExpDate/CVV…, шифрование X509 RSA-2048, Base64). Наша интеграция через платёжную форму банка — метод не используется.
- **Отмена и возврат — один метод `Cancel`** (`/v2/Cancel`, «Метод отменяет платеж»):
  - до подтверждения (статус `NEW`): «поле Amount игнорируется, даже если оно заполнено. Отмена проводится на полную сумму» → результат `REVERSED`;
  - после `CONFIRMED` — возврат: полный (`Amount` не передан или равен платежу) или частичный (`Amount` = сумма возврата в копейках; при подключённой онлайн-кассе обязателен `Receipt` с позициями частичного возврата);
  - `ExternalRequestId` — «Ключ идемпотентности и идентификатор операции на стороне мерчанта»: «Если такой запрос уже есть, в ответе вернется текущее состояние платежной операции, если нет — платеж будет отменен» (пустой/отсутствующий — обработка без проверки предыдущих возвратов);
  - Ответ `CancelResponse`: `OriginalAmount` («Сумма в копейках до операции отмены»), `NewAmount` («Сумма в копейках после операции отмены»), `Status` (пример `REVERSED`), `PaymentId`, `OrderId`, `Success`, `ErrorCode`.
  - Типовые коды Cancel: 100 («Платеж не получится отменить, потому что деньги покупателя не были зарезервированы», «Платеж уже отменен», «Не получилось отменить платеж. Укажите сумму не больше, чем зарезревировано» и др.), 323/326/330 («Amount не совпадают», «Неверный Amount», «Сумма в запросе больше, чем в оригинальной транзакции»).

## 10. Сверка vendored-спеки с upstream

- `spec/generate.go` содержит только директиву `//go:generate` (oapi-codegen v2.7.1, `-generate types`, вход `openapi.patched.yaml`); **источник спецификации зафиксирован в `spec/README.md`**: `https://developer.tbank.ru/schemas/eacq/openapi.yaml`, вендоренная версия 1.28.
- Проверка 2026-08-23: upstream отдаёт `version: '1.28'` — **совпадает**, регенерация не требуется.
- Побайтовое сравнение `openapi.yaml` с upstream: **одно расхождение**, строка 5438 — значение `example` поля `AcsSignedContent` (JWS-пример из 3DS ARes в `ThreeDSMethodResponse`-секции): в вендоренной копии base64-строка содержит внутренние пробелы (артефакт сохранения/переноса), upstream — без пробелов. Это чистая косметика примера: ни схемы, ни типов, ни генерации не касается. При следующем re-vendor сравнение `diff -q` «IDENTICAL» не пройдёт — стоит знать, что это не дрейф контракта.
- `openapi.patched.yaml` отличается от `openapi.yaml` ровно одним патчем `patch.sh`: `Common.additionalProperties` поднят с «свойства» на уровень схемы (баг upstream, из-за которого oapi-codegen генерил фиктивное поле `AdditionalProperties *string` вместо свободной map для `DATA`). Патч актуален и для 1.28 — pattern в upstream по-прежнему присутствует (проверено выполнением patch.sh-логики на свежем upstream: блок `Common: properties: additionalProperties:` на месте).
- `servers` спеки: `https://securepay.tinkoff.ru` (production), `https://rest-api-test.tinkoff.ru` (test) — те же, что на страницах методов.

## Критичные для нашего кода точки проверки

Что ревьюер обязан сверить в `apps/backend/internal/billing/adapters/payment/tkassa/` против этого справочника:

1. **sign() (`sign.go`)**: исключение `Token`, `DATA`, `Data`, `Receipt` и любых вложенных объектов/массивов; добавление `Password`; сортировка ключей; конкатенация только значений без разделителей; SHA-256 UTF-8; hex-lowercase. Пропуск пустых строк в подписи — интерпретация нашей стороны (офиц. правило не оговаривает пустые значения; фактически в подписываемом наборе их не бывает — важно только чтобы serialization не добавляла пустые поля).
2. **Amount как int64-копейки во всех денежных полях** — Init/Confirm/Cancel по спеке integer int64 (upstream починил number→integer в 1.27, патч у нас снят); парсинг `Amount` из webhook'ов — числовой (json.Number), в примерах доков значения как строки.
3. **Init**: `OrderId` ≤ 50 (наш UUIDv7 — 36, ок); `Description` ≤ 140 с обрезкой; `CustomerKey` обязателен при `Recurrent=Y`; `OperationInitiatorType` в `DATA`: `1` для родительского CIT CC (наш `InitiatorCustomer`), `R` для MIT COF Recurring (наш `InitiatorMerchant`) — пустой инициатор обязан отвергаться (иначе 1126); per-request `NotificationURL`/`SuccessURL`/`FailURL` перекрывают терминальные.
4. **Charge**: обязателен вызов Init перед Charge (сумма задаётся в Init) и `Amount` в ChargeRequest не отправляется — сверить, что приложение ставит сумму в Init для MIT-сценария, а адаптер не шлёт Amount в Charge.
5. **AddCard**: официальная схема не содержит URL-полей; токен считается только по схемным полям, URL-надбавки (`SuccessAddCardURL`/`FailAddCardURL`/`NotificationURL` + легаси-имена) добавляются в тело после подписи — поведение подтверждено только прод-опытом (ошибки 9 и 204), не документацией; ревьюить на регрессию при каждом re-vendor спеки.
6. **Webhook-хендлер**: ответ HTTP 200 с телом `OK` (без тегов, заглавными) на любой валидный нотиф; окно обработки 10 секунд (успеть до таймаута банка); обработка дублей (две нотификации AUTHORIZED+CONFIRMED на одностадийный платёж/Charge; ретраи час/24ч + сутки/месяц); сверка `TerminalKey`; дискриминация типа нотификации — payment-поля против add-card (`RequestKey`); `RebillId` забирается из AUTHORIZED-нотификации родителя и из add-card нотификации.
7. **Статусная модель (`status.go`)**: терминальный успех — `CONFIRMED` (одностадийная); провал — `REJECTED`/`AUTH_FAIL`/`CANCELED`/`DEADLINE_EXPIRED`; `UNKNOWN` и «процессные» статусы — pending; `ASYNC_REFUNDING`/`PARTIAL_REVERSED`/`3DS_FAILED` в enum 1.28 отсутствуют — оставить обработку (легаси-совместимость), но не считать их официальным словарём; дефолт-ветка — pending, не провал.
8. **GetState** — единственный метод сверки статуса (по `PaymentId`); ответ несёт `RebillId` (используется как запасной канал получения charge token); ErrorCode при Success=true для СБП не показатель — «ориентируйтесь на статус».
9. **Cancel**: `Amount` в копейках задаёт частичность; при `NEW` Amount игнорируется (полная отмена); `ExternalRequestId` — идемпотентность возвратов (дубли по сети должен разряжать провайдер); refunded-сумму считать из `OriginalAmount`−`NewAmount`.
10. **GetCardList**: возвращает и удалённые карты — фильтр по карточному `Status` (A) обязателен; удаление — `RemoveCard` по `CardId`.
11. **Retry-транспорт (`retry_transport.go`)**: безопасность ретраев по методам (идемпотентность GetState/GetCardList — да; Init/Charge/Cancel — только по сетевым ошибкам до получения ответа; код 119 и «повторите позже» — разные политики); полный джиттер против thundering herd.
12. **Спека**: upstream 1.28 == вендоренная; следующая проверка — `curl -fsSL https://developer.tbank.ru/schemas/eacq/openapi.yaml | diff - openapi.yaml` (известный допустимый дельта — example в `AcsSignedContent`); любое новое поле/метод — через re-vendor процедуру README, не правкой `spec.gen.go`.
