# Time travel жизненного цикла подписки (стенды)

Механизм приёмки полного жизненного цикла подписки без ожидания реального
времени (карта #611, тикет #665; решения владельца в гриллинге #648 от
14.09.2026). Работает на непродовых стендах: `local`, `dev`, `stage`.

## Рейлгейты

- Механизм включается только переменной `BILLING_TIME_TRAVEL=true`; по
  умолчанию выключен. `APP_ENV=production` с включённым флагом **падает на
  старте** конфиг-валидатором — тот же паттерн, что у fake-провайдера.
- Эндпоинты монтируются только при включённом флаге: в выключенной сборке их
  не существует вовсе. Доступ — только роль `admin` (`AdminOnlyMiddleware`).
- Один сдвиг ограничен ±90 дней (`MaxTimeShift`); каждая операция пишет
  переход `time_shifted` в лог переходов и запись аудита
  `subscription.time_shifted` с актором-админом.
- Письма на стендах отправляет fake-отправитель — напоминание наблюдаемо в
  логе mailer'а.

## Что делает сдвиг

Админ-операция переписывает временные границы подписки **когерентно** одним
подписанным дельта-сдвигом (часы):

- `user_subscriptions.valid_until` (конец оплаченного периода / конец grace) и
  `pending_change_at` — вместе, чтобы CHECK `pending_change_at >= valid_until`
  не нарушился;
- анкер ретраев долга — `created_at` последних переходов `grace_entered`
  (фаза ретраев читает именно их); переносится delete-и-reinsert тех же строк,
  потому что лог переходов append-only по триггеру (ADR 0037);
- `created_at` платежей подписки — предикат ретрая считает платежи «от
  анкера», поэтому они едут вместе с ним (порядок относительно анкера
  сохраняется).

Фазы воркера не меняются ни строчкой: следующий тик догоняет сдвинутое по
`clock.Now`. Флаг «напоминание отправлено» сбрасывается — сдвинутое окно
свежее для напоминания (как при ExtendGrace).

## Эндпоинты

| Эндпоинт | Тело | Эффект |
|---|---|---|
| `POST /admin/users/{id}/subscription/time-shift` | `{"shiftHours": -25}` или `{"preset": "…"}` | когерентный сдвиг, 204 |
| `POST /admin/billing/tick` | — | один проход фаз воркера сейчас, 204 |

Пресеты (сервер считает дельту от живого состояния — граница придвигается к
«сейчас», а не часы вперёд):

| Пресет | Цель | Сценарий приёмки |
|---|---|---|
| `period_expired` | `valid_until := now − 1ч` | «войти в grace» из active (тик: продление → отказ → grace); «истечь из grace» из grace (тик: падение на basic) |
| `retry_24h_due` | анкер `:= now − 25ч` | окно первого ретрая +24ч |
| `retry_72h_due` | анкер `:= now − 73ч` | окно второго ретрая +72ч |
| `reminder_window` | `valid_until := now + 24ч` | окно напоминания `[grace_end − 48ч, grace_end)` |

Гарды пресетов отвечают 409, если цель уже пройдена (граница не позади цели,
подписка не в grace) — шаг приёмки выполняется не по порядку. Лимит одного
сдвига ±90 дней: годовая подписка (valid_until до 12 месяцев вперёд) не
дотягивается одним `period_expired` — прогоните два сдвига подряд (например,
`HOURS=-2160` дважды).

Make-обёртка (нужны `ADMIN_COOKIE` и `USER_ID`):

```sh
make billing-time-shift USER_ID=<uuid> PRESET=retry_24h_due   # пресет
make billing-time-shift USER_ID=<uuid> HOURS=-25              # сырой сдвиг
make billing-tick                                             # прогнать фазы
```

## Как войти админом

Сессия админа — обычная: код по SMS/почте (на стенде — в логе бэка или
fake-mailer).

```sh
BASE_URL=http://localhost:8080
ADMIN_PHONE="+79000000001"   # телефон админ-пользователя стенда

curl -sS -X POST "$BASE_URL/auth/send" -H 'Content-Type: application/json' \
  -d "{\"phone\":\"$ADMIN_PHONE\"}"
# взять код из лога бэка (письмо «Рентли: NNNNNN» / SMS-лог)

curl -sS -c /tmp/admin-cookie.txt -X POST "$BASE_URL/auth/verify" \
  -H 'Content-Type: application/json' \
  -d "{\"phone\":\"$ADMIN_PHONE\",\"code\":\"NNNNNN\"}"
ADMIN_COOKIE="$(grep session_id /tmp/admin-cookie.txt | awk '{print $6"="$7}')"
```

## Прогон приёмки (полный цикл, решение #648)

Пользователь на Pro с картой (fake-провайдер), известен `USER_ID`. После
каждого шага — `make billing-tick` и наблюдение в UI кабинета и/или логах.

1. **Войти в grace.** `PRESET=period_expired` → тик: фаза продления
   списывает (fake-отказ: sentinel-сумма `…01` или режим `FAKE_AUTOCONFIRM=off`
   с fail-эндпоинтом) → статус `grace`, лишние объекты архивируются
   (grace-лимит 1), событие `GraceEntered`.
2. **Напоминание за 48ч.** `PRESET=reminder_window` → тик: письмо
   `GraceExpiring` в логе mailer'а, ровно один раз на окно.
3. **Ретрай +24.** `PRESET=retry_24h_due` → тик: фаза долга списывает снова
   (fake-отказ) — новый `failed`-платёж, подписка остаётся в grace.
4. **Ретрай +72.** `PRESET=retry_72h_due` → тик: второй ретрай, снова отказ.
5. **Истечение grace.** `PRESET=period_expired` → тик: падение на basic,
   грейс-архив остаётся в архиве.
6. **Восстановление оплатой (grace-архив).** Поднять подписку заново
   (`AssignServiceSubscription` админом или оплата тарифа в UI), войти в
   grace шагом 1, затем оплатить тариф в UI (fake-подтверждение) —
   заархивированные снимком объекты возвращаются в той же транзакции
   (ADR 0055).

История каждого шага: `GET /admin/users/{id}/subscription/transitions`
(переходы `grace_entered`, `expired`, `payment_applied`, `time_shifted`) и
`GET /admin/users/{id}/audit-logs` (`subscription.time_shifted`).
