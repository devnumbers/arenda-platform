# История

Продуктовая лента «История действий» по объектам: записи о ручных действиях пользователей, человекочитаемые строки, поиск и фильтры. Читают владелец и участники объекта (включая «Просмотр»); suspended-доступ в ленту не пускается. См. ADR 0061 (docs/adr/0061-action-history.md).

## Language

**История действий / Action History**:
Продуктовая лента действий по объектам для владельца и участников. Пишутся только ручные действия пользователя, в транзакции действия, безусловно для всех объектов. Переживает отзыв/выход участника; при удалении объекта удаляется вместе с ним (записей об удалении объекта не существует — они каскадятся вместе со всеми). Не путать с «Журналом действий» — это аудит для админки (контекст Audit, ADR 0020).
_Avoid_: журнал действий (это аудит), аудит, лог, event log

**Запись истории / History Entry**:
Одна строка ленты, append-only: вид действия, конкретное действие, основное действие, актёр (со снапшотом имени), сегменты текста, снапшот названия сущности, время. Запись неизменяема и не перечитывает сущность: снапшоты фиксируются при действии и живут вечно, у удалённой сущности остаётся строка без перехода. Каждая строка привязана к объекту (FK CASCADE): мутации без объектной привязки — карточка контакта «без объекта», задачи-правила книги «без объекта» (ADR 0052) — строк не пишут, как и системные действия; исключение — строки пары переноса и одноногие привязка/отвязка контакта (#856): строку пишет объект, который карточка покинула или к которому присоединилась (якорь — привязка карточки на момент действия), а «не пишут» остаётся про карточки вовсе без привязки (ADR 0061 §4).

**Основное действие / Base Action**:
Одна из четырёх групп фильтра ленты, каждой — своя иконка и цвет: **Добавление** (зелёный), **Изменение** (жёлтый), **Выполнение** (синий), **Удаление** (красный). Маппинг редких действий: архив/анархив объекта, пауза/снятие паузы платежа, возврат задачи в работу, продление аренды, привязка/отвязка/перенос контакта между объектами (ADR 0061 §4) — «Изменение»; вход объекта в ремонт — «Изменение» (property.maintenance_started), выход — «Выполнение» (property.maintenance_finished; аменда ADR 0061 §3, карта #1324, D2); удаление операции («Отменённая операция») — «Удаление».

**Вид действия / Action Kind**:
Семь групп словаря журнала, группы чекбоксов фильтра: Объект, Аренда, Платежи, Операции, Контакты, Задачи, Участники.

**Сегменты строки / Row Segments**:
Текст записи, собранный сервером при записи: упорядоченные фрагменты, часть — со ссылкой на сущность (синие переходы на существующие страницы сущностей, тикет #713). Ссылка ведёт на страницу сущности; у вхождений задач страница одна — правка правила, поэтому завершение/возврат задачи ссылаются на правило (правило удалено — строка без ссылки). Сервер — единственный источник текста строки; поиск ищет по конкатенации сегментов. Актёр в тексте не живёт — он поле записи, фронт группирует им.
_Avoid_: шаблоны на фронте

**Строка изменения / Change Row** (решение владельца 12.10, карта #1324; аменда D1):
Любая правка одной сущности — одна строка уровня сущности: «<Сущность> изменён(а): [значение-ссылка]» (снапшот нового значения), полевых заголовков нет («Название объекта изменено» — _avoid_). Пояснение пишется на каждое изменившееся поле: «Метка: «стар» → «нов»». У объекта единая строка поглощает и правки полей, и фото («Фото: добавлено / удалено»).

**Пояснения строки / Details** (карта #1324, протокол D1, решение #1317 §2):
Серые строки-пояснения нового шаблона («Название: «Моя квартира» → «Квартира №124»»): готовые тексты, собираемые билдерами при записи (jsonb-массив строк, 000159), фронт рендерит дословно — читающий путь без каталога форматирования. Ссылок в пояснениях нет — ссылка одна, в заголовке. Значения в пояснениях — реальные и полные: телефоны, почты, суммы («Сумма: «5 000 ₽» → «6 000 ₽»»), длинные тексты (описание, заметка) без резки (аменда ADR 0061 §5, слово владельца 12.10 — «пояснения существуют, чтобы показать, что изменилось»; запреты остались только на заголовках). NULL у строк, записанных до шаблона, и у действий без диффов: такие строки рендерятся одним заголовком (осознанное решение владельца). В поиск пояснения входят: searchable новых строк = заголовок + пояснения + актёр; легаси не пересобирается — «что видишь, то и ищешь» для обеих эпох. Метка каталога (AttributeChange.Label, RU-подпись поля) едет в context вместе со значениями — метаданные деталей, не вторая копия значений.
_Avoid_: {label, old, new} на проводе (каталог форматирования на чтении), пересборка searchable легаси, резка пояснений с «…»

**Снапшот названия / Label Snapshot**:
Человекочитаемое название сущности (объекта, платежа, операции, контакта, задачи, участника) на момент действия. Пишутся имена и названия, почты участников (видны всем участникам, решение 2026-09-20), значения характеристик, роли; периоды — структурно, в context (аудит #876). Аменда 12.10 (карта #1324): телефоны контактов и суммы пишутся в пояснениях полными значениями (ADR 0061 §5); суммы копейками едут и в context.

**Актёр / Actor**:
Пользователь, совершивший действие: владелец или участник объекта (роль — owner/full_access/viewer, паттерн аудита ADR 0020). Системных записей в MVP нет: слотовые приостановки/восстановления доступа и активация приглашения при регистрации не пишутся (решение владельца 2026-09-22); авто-оплаты и авто-задачи не пишутся по уставу карты.

**Чтение / Read** (тикеты #708/#842):
`GET /history` — двусторонний keyset по (created_at, id) DESC: `before_cursor` ведёт в прошлое, `after_cursor` — prepend свежих записей; фильтры периода/основных действий/видов/актёров/объектов; поиск q — всегда-OR предикат «как в Telegram» (ресерч #839): префикс слова и морфология через prefix-FTS (`plainto_tsquery || ':*'`), фрагменты и почты через ILIKE-trgm, обе ноги на одном вводе — маршрутизация trgm/fts/both (#705) снесена как предсказание интента. Область чтения — SQL-функция `actor_can_read_property` (000142, до #884 — `actor_can_read_history` 000137): владелец при любом статусе объекта, участник — только неархивных; suspended и чужие объекты строк не отдают, а чужой/неизвестный id в property_ids — privacy-404 всего запроса (канон ленты задач #547). `GET /history/filters` — опции шита; область «Участников» двух родов (изоляция D14, #1305): без property_ids (глобальная лента) — участники только МОИХ объектов читателя (свои архивные включены), получателю shared-доступа владелец и соучастники чужого объекта не раскрыты; с property_ids (история одного объекта) — собственник и текущие ∪ все актёры журнала суженной области (отозванные остаются фильтруемыми; обезличенные записи актёром-фильтром не становятся). Участник несёт `first_name` (имя без фамилии для строки «(Вы)»; '' — имени нет, name — «Пользователь», канон отображения #1105, аменд #1123), `is_owner` (владеет хотя бы одним объектом области чтения — иконка владельца-замка, единственная иконка строки участника шита фильтров, #711, решение владельца 12.10.2026 #1360; приглашённый без своих объектов флага не получает) и `role` (#840): максимальный доступ в области, живое членство сильнее снимка журнала отозванного; owner совпадает с is_owner по построению. Период-фильтр from/to сервер матчит UTC-сутками (канон админ-аудита), тогда как группировка дней ленты на фронте — локальный календарный день смотрящего: расхождение ограничено краевыми часами суток и принято (ADR 0061 §7).
**Живые ноги актёра** (карта #1324, D5, паттерн ADR 0065): имя/фамилия актёра строки (`actor_first_name`/`actor_last_name`) читаются JOIN'ом users при выдаче — карточка актёра показывает сегодняшний профиль; снимки actor_name/actor_email остаются строкой журнала и обязательны на проводе. Сборку отображаемого имени («Имя Фамилия» / «(Вы)» / «Пользователь») и фолбэк на снимок по actor_id = null делает фронт (хелпер D4) — сервер отдаёт части, снимок в «имя без фамилии» не подмешивает.
**Статус участника «Текущие/Удалённые»** (карта #1324, D6, решение #1317 §5): `status` опции фильтра (`current`/`removed`) вычисляется на лету, без новой таблицы: `bool_or(is_live)` по ногам CTE области — владелец и членство живы (приостановленное членство — живо: suspend не стирает строку, 000095; ревок/выход стирает), журнал-only актёр — нет. Повторное добавление живит участника автоматически; мульти-скоуп — жив хотя бы в одном объекте области; сужение property_ids до одного объекта сужает и семантику (живущий только в другом объекте честно «Удалённый» здесь).
