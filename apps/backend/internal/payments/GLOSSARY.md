# Payments

Bounded context платежей и операций: учёт по объекту (Property из контекста properties) — что объект должен платить/получать и что фактически произошло. Платёж-правило порождает операции-вхождения, просрочка вычисляется, долг копится, автоплатёж закрывает наступившее автоматически. Словарь перенесён из прототипа доходности объекта identity-маппингом (таблица соответствия — ADR 0047); «Объект» не переопределяется — см. properties/GLOSSARY.md.

## Language

**Платёж / Payment**:
Правило: что, сколько, когда и как часто должно происходить по объекту — доход или расход. Действует с момента заведения: вхождений до этой даты не создаёт — прошлое не его задача. Сам по себе не бывает оплачен, просрочен или отменён — это состояния его операций. Удаление — правом редактирования: полный доступ сносит правило в чужом объекте без эскалации к собственнику (D9 #1309; жизненный цикл самого объекта — владельческий).
_Avoid_: шаблон, регулярный платёж, автоплатёж (когда имеется в виду любое правило); разовый платёж (разовый факт — только операция)

**Операция / Operation**:
Конкретное вхождение платежа в конкретную дату либо разовый факт дохода/расхода, внесённый вручную. Единица, которую оплачивают; закрытие — только оплатой. Просроченной бывает только она. У операции две даты (решение владельца о переводе операционных лент, #933/#992; histories переведены следом — дополнение #994, отмена «учёт, не кассы» #466): плановая — дата вхождения по графику правила, планировочный атрибут (планирование вхождений, просрочка, проекция, график); фактическая — дата оплаты, платёжный факт, есть только у оплаченных. Операционные ленты — сортировка, период-фильтры и сводки — и платёжная история (история операций платежа и аренды: сорт, группировка, даты строк) читаются по фактической; планировочные поверхности остаются на плановой. Внутри одного дня факты идут в порядке оплат (решение владельца, #1195): момент оплаты — updated_at оплаченной строки (после оплаты строка не меняется, так что это именно момент факта, не создания строки); «История платежа» ставит по нему операции в ленту вперемешку со строками журнала правок. UI-copy exception (решение владельца 02.10, тикет #1073; сужено макетом 3214:76417, тикет #1194, 07.10): на странице платежа просроченные вхождения правила названы «платеж» — секция «Просроченные платежи» с подэкраном; секция ближайшего вернулась к доменному «Ближайшая операция», история зовётся «История платежа» (стрелка ведёт на подэкран «История операций»). Доменный термин не меняется — вхождения остаются Операциями. Представление на странице операции (решение владельца — поправка 08.10 к #1190, тикет #1196): страница показывает снимок операции — название, категорию и иконку, с которыми операция материализовалась (ручная — как ввели); живое правило представлено только плашкой «Платеж» в «Данных операции» — её название и картинку фронт берёт из живой детали платежа, а не из операции. Деталь операции отдаёт снимки наравне со списками; «История платежа» — тоже на снимках: строки показывают, как операция называлась.
_Avoid_: транзакция, платёж (когда имеется в виду вхождение), одна «дата операции» (их две — плановая и фактическая)

**Отменённая операция / Cancelled operation**:
Статус-надгробие удалённой операции (решение владельца об удалении вхождений): платёжный факт и долг исчезают, строка остаётся с ключом (платёж, дата), чтобы тик не материализовал отменённое вхождение заново. Отменяются только оплаченные и просроченные операции; ближайшая будущая плановая и проекции не удаляются — расписание правится на уровне правила. Для всех чтений отменённая операция не существует: из долга, истории и прямого GET она исчезает; след — в audit_log (`operation.deleted`) и в «Истории действий» («Отменённая операция», `operation.deleted`). Удалять могут Full Access и выше; отмена необратима (повторное удаление — тот же «не найден»).
_Avoid_: пропуск, «удалённая операция» (физическая строка остаётся)

**Лента операций / Operations feed**:
Глобальное чтение контекста (тикет #540): оплаченные операции всех объектов, видимых читателю, — своей книги плюс объекты с активным членством (ADR 0028); архивные объекты из ленты и сводки исключены, отменённые операции не существуют. Actor-scoped cross-property read (правило глобальных задач, тикет #521): единого скоупа нет, видимость решается в SQL самого чтения, а не через policy-порт; фильтр «Объект» проводит каждый id через view gate — чужой объект даёт приватный 404. Только чтение: оплата, удаление и детали операции остаются на объектных эндпоинтах, чистое чтение тик не запускает. Порции листаются keyset-курсором по порядку чтения (дата, id): строка, сдвинувшаяся между догрузками (создание, удаление, переименование объекта), не дублируется и не теряется (#597). Ответ несёт total — число платёжных фактов всего скоупа под теми же фильтрами («найдено N», #599): предикат списка без курсорного ключа, одинаково на каждой порции; объектные списки, делящие схему ответа, поле не ставят. Сводка ленты — карточки «Доходы/Расходы» и разбивка категорий, обе агрегируют в SQL тот же скоуп, что список: объекты, период, поиск и категорийный фильтр сужают и тоталы, и разбивку — карточка зеркалит отфильтрованный список (решение владельца 01.10, прежнее «категория сужает только разбивку» #540 отменено); фильтр направления сужает только разбивку — тоталы всегда отдают оба направления, карточка направления берёт свой сегмент.
_Avoid_: глобальные операции, все операции платформы, лента платежей, offset-окна ленты

**Избранное / Favorite**:
Личная пометка правила на глобальном экране «Платежи» (личный cutover #1308, D12): звезда (флаг #461) и — с карты #573 — ручной порядок карточек в разделе избранного — связь конкретного читателя с правилом, его рабочий набор. Состояние живёт строкой `user_payment_favorites` («строка есть = состояние»): звезда — INSERT, снятие — DELETE (позиция уходит вместе со строкой), повторное добавление после снятия — снова в конец; повторная звезда не меняет строку (позиция не сдвигается). Позиция (`favorite_order`) — целое, `NULL` = правило ещё не стояло в сохранённом порядке: новое избранное сортируется в конец («новое избранное — в конец»). Право звезды и порядка — просмотр (D12: зритель ведёт своё избранное наравне с владельцем и полным доступом). Сохранение порядка — `PUT /payments/favorites/order`: плотные позиции 1..N по присланному списку id в одной транзакции, полная замена в пределах личного набора актёра — избранное вне списка теряет позицию и уходит в конец (дубли позиций после сохранения невозможны; пустой список сбрасывает весь видимый личный порядок; избранное архивного объекта позицию сохраняет — D16, возврат из архива возвращает порядок). В lock-pass — только свои starred-строки на видимых неархивных правилах: вырожденный id (чужой, невидимый, архивный, не мой starred) — приватный 404; дубль — 400. Чужая звезда и чужой порядок мой экран не меняют; в журнале действий избранное не пишется, realtime-фреймы не публикуются (D17, D18). Чтение — `isFavorite`/`favoriteOrder` актёра в строке ленты и объектного списка: секция избранного сортируется по позиции с `NULL` в конец, порядок самого фида не меняется.
_Avoid_: избранное операции (звёздочка только у правил), «избранный — правило целиком» (отменено #1308), глобальная звезда/порядок на правиле, сортировка фида по избранному

**Лента платежей / Payments feed**:
Глобальное чтение правил (карта #573, тикет #575): каждое правило видимых неархивных объектов — своей книги плюс объектов с активным членством; тот же actor-scoped cross-property read, что у ленты операций. Строка несёт «Ближайший» (частный случай «Следующей даты оплаты»: ближайшая плановая операция или проекция — просто порядок графика, без статуса; у правила в открытой паузе и у вычисляемо-завершённого его нет), отображаемый флаг завершённости isCompleted (#1341 — вычисляемая завершённость с разрешённым на сервере исключением открытой паузы: сырой флаг за вырезанным курсором паузы отвечает «завершён», а строка пауз не несёт, — им карточка хаба показывает «Полностью оплачен» и приглашает к «Завершить» (#1377); детальное чтение несёт сырой флаг), просрочку правила (счётчик просроченных операций и возраст старейшей — «N дней») и личные `isFavorite`/`favoriteOrder` читателя (см. «Избранное», #1308); все вычисления графика идут по today владельца объекта (ADR 0048), он же едет в строке — лента смешивает владельцев. Порядок чтения — (created_at, id), название объекта в нём не участвует: переименование объекта не двигает строки, и поиск листается keyset-курсором по этому же порядку без дублей и пропусков между догрузками (#597). Ответ поиска несёт total — число совпадений всего скоупа под запросом и фильтром чипа («найдено N», #599): предикат списка без курсорного ключа, одинаково на каждой порции. Счётчики главного экрана («Все избранные», «Все просроченные», «На оплату» — #1346) описывают весь скоуп и поиском не сужаются; «Все избранные» — личный счётчик читателя (#1308); сам список секции «На оплату» — отдельное чтение (см. «На оплату»), ленту оно не трогает. Напоминания в строке фида не ездят — их поверхность секция «На оплату». Только чтение: правка правила остаётся на объектных экранах.
_Avoid_: лента операций (это другой фид — факты, не правила), «isCompleted строки — сырой флаг» (строка фида несёт отображаемый флаг, пауза разрешена сервером), «счётчик „На оплату“ сужается поиском» (счётчики хаба описывают скоуп)

**На оплату / Due** (тикет #1346):
Глобальная секция главного экрана «Платежи»: правила с включённым напоминанием (`reminder_offset_days` 1/3/7) и БЕЗ автоплатежа, у которых есть неоплаченная planned-операция с датой D в окне **D−N ≤ today ≤ D** (today — владельца объекта, ADR 0048; решение владельца 12.10, ревизия прежнего «вне среза» — напоминание у автоплатёжных стреляет, но секция их не содержит). Просроченные (D < today) в секцию не попадают — им «Все просроченные»; в день D строка ещё в группе «Сегодня», назавтра уходит в просрочку. Derivation на чтении (решение research #1343, вариант C): ни окна, ни бакета в БД нет — вторая машина правды на этом масштабе не окупается, а окно структурно совпадает с промежутком между уже стреляющими reminder-джобой (день D−N) и due-джобой (день D); истина — таблицы `operations`/`payments`, джобы — только доставка. Пауза отдельного гейта не требует: вхождения в паузе не генерируются, будущие planned сняты тиком — правилу в окне нечего показывать (смена пояса владельца derivation подхватывает бесплатно, ADR 0048 п.5). Чтения: счётчик хаба (`dueOperationsCount` + `dueNearestDays` — ближайший остаток дней для метки «Сегодня/Завтра/Через N дней»; едут в ответе фида, поиском не сужаются) и списковое `GET /payments/due` — всё окно одним чтением без пагинации (секция мала: материализация держит в окне максимум «сегодня» и одно будущее на правило), строки — пары (правило, операция) с `daysLeft` (0..7), порядок — реальные дни по возрастанию (решение владельца 13.10, ревизия прежних бакетов 2..3/4..7 из research #1343: каждая дата — своя группа, «Сегодня», «Завтра», «Через N дней» для N ≥ 2), внутри дня — id операции тай-брейк; группы по дням — клиентские, заголовки клиентские (сервер текстов не строит), чип страницы разворачивает порядок групп целиком, не трогая порядок внутри дня. Сегмент read-only: оплата — на объектных эндпоинтах; realtime-фреймов нет (D18) — перечитывание. Арендные управляемые платежи отдельного гейта не имеют: критерий секции — напоминание и не-автоплатёж.
_Avoid_: «секция напоминаний» (напоминание — критерий отбора, не содержимое), серверные заголовки групп дней, склейка дат под одним заголовком (бакеты 2..3/4..7 — отменены владельцем 13.10), материализация окна (отклонено research #1343), просроченные в секции, «дни считаются в зоне читателя» (today владельца объекта)

**Следующая дата оплаты / Next payment date** (тикет #991):
Единое серверное определение даты следующего платежа правила: ближайшая хранённая плановая операция от today владельца объекта (ADR 0048), иначе — проекция правила; у правила в открытой паузе и у вычисляемо-завершённого её нет — null. Не хранится, вычисляется на каждом чтении. Оплаченное вхождение — в том числе будущая предоплата — «следующей» не считается: дата ищется после него. Объектный список платежей несёт её на каждом правиле (`nearestDate`); «Ближайший» из «Ленты платежей» — частный случай той же даты.
_Avoid_: клиентский пересчёт графика на фронте, «ближайшая операция» (у ближайшего нет статуса), отдельная колонка в БД

**Объекты и платежи / Payment objects**:
Объектный срез глобального чтения (тикет #575): видимые неархивные объекты со стопками ключей — правила объекта группой автоплатежей и группой остальных, на каждом ключе признак просрочки (красная точка). Поиск фильтрует объекты по названию/адресу, стопки остаются полными. Объект без правил даёт пустые группы.
_Avoid_: глобальное скрепление объектов (это тикет #577, не это чтение)

**Доход / Расход / Income / Expense**:
Тип платежа и операции: деньги в объект / деньги из объекта.
_Avoid_: пополнение, списание, приход/уход

**Автоплатёж / Auto Pay**:
Режим платежа: операция оплачивается автоматически в день её наступления — тик гасит planned-вхождение с датой сегодняшнего дня. Просроченное автоматика не трогает никогда: ретроспективных автогашений нет, закрытие просрочки — только вручную (ADR 0049). Не отдельная сущность.
_Avoid_: тип платежа, отдельная сущность, автодогон (задним числом не гасит)

**Напоминание / Reminder** (карта #822, #824):
Предупреждение «за N дней» о вхождении правила: оффсет 1/3/7, NULL — напоминаний нет (выбор опционален). Колонка `payments.reminder_offset_days` с CHECK (1,3,7). Живёт независимо от auto_pay — автоплатёжное правило с напоминанием всё равно предупреждает (решение владельца, #823); аренда ставит напоминание вместе с автоплатежом (дефолт экрана аренды — «Не напоминать», #1198). Исключение — создание: у автоплатёжного правила присланное напоминание форсится в NULL (решение владельца по гриллингу #1186, макет 3214-72739 — автоплатёжная форма reminder-пикер не показывает); правка и арендный конвейер не режутся. Издатель напоминаний — notifications (день напоминания = дата операции − N, стенное 10:00 зоны; словарь — notifications/GLOSSARY.md).
_Avoid_: пер-платёжный override канала (email/push — настройки категории), отдельная сущность напоминания

**Уведомление об автоплатеже / Auto-paid notification** (тикет #1189):
Пер-платёжный флаг `payments.notify_auto_paid` — гейт события «Автоплатёж исполнен» (notifications, издатель #1169): false — исполнение правила молчит во всех трёх ногах издателя (скан, букинг, разрешение в момент доставки). Дефолт новых правил — false («Не уведомлять», макет 3214-72739); существующим автоплатежам флаг проставлен true миграцией 000153 — без поведенческого регресса (решение владельца по гриллингу #1186). После создания флаг самостоятелен: переключение auto_pay его не переписывает; аренда создаёт Платёж с флагом true безусловно (#1198, по подписи макета 1428 — без отдельного контрола) — автоплатёж, включённый позже правкой условий, тоже уведомляет.
_Avoid_: пер-платёжный override канала (email/push — настройки категории), «флаг дублирует auto_pay» (гейтится событие, не режим), флаг на операции (живёт на правиле)

**Просрочка / Overdue**:
Вычисляемое состояние операции: запланирована, но дата оплаты уже прошла. Не хранится как статус.
_Avoid_: статус «просрочен» у платежа

**Завершённый платёж / Completed** (ревизия #1377 — завершение удаляет правило; отмена хранимого штампа #1340):
Хранимого состояния «завершённый платёж» не существует — есть вычисляемая готовность и удаляющая мутация. Вычисляемая завершённость (isCompleted ответа API — read-side вид, как просрочка): у правила не осталось неоплаченных вхождений — нет ни planned-операций (просрочка включена), ни вхождений за последней материализованной датой любого статуса; оплата последнего вхождения завершает правило в тот же день, не дожидаясь endDate; бессрочное правило не завершается никогда; исключение — открытая пауза: паузные вхождения из перечисления вырезаны, и вычисление отвечает «завершён» за курсором вхождений — решение о действиях принимается по endDate правила. По вычисляемому флагу фронт показывает «Полностью оплачен» и кнопку «Завершить» — приглашение к мутации. Мутация complete гейтится доменным CanBeCompleted (вычисляемая завершённость при действительно закончившемся расписании — endDate наступила, «в тот же день» канон; открытой паузы нет) и удаляет правило из БД: страница по прямой ссылке — приватный 404, из лент, списков, поиска и счётчиков правило скрыто фактом удаления, повторное завершение — приватный 404. Хвост правила: оплаченные операции остаются в истории объекта (payment_id NULL по FK `ON DELETE SET NULL`, origin 'payment') — тот же исход, что при завершении аренды (#1161) и удалении (#446); звезда читателя падает вместе с правилом (каскад); журнал правок каскадит — строки о завершении в него не пишут, «История действий» несёт «Платёж завершён: …» (audit `payment.completed`). Завершение аренды — тот же конвейер без этой мутации (см. «Управляемый платёж»).
_Avoid_: «закрытый платёж», «архивный платёж», штамп `completed_at` (хранимого завершения не существует), read-only страница завершённого, un-complete

**Управляемый платёж / Rental-managed payment** (тикет #818, ревизия #1161):
Платёж, на который ссылается аренда (связь 1:1): создаётся, правится и удаляется только конвейером аренды — pause/resume/update/delete/complete через PaymentService отвечают 409 ErrRentManagedPayment (обратный гейт, ADR 0053 §3, ревизия 2026-09-23; complete — #1340), пока ссылка жива. Завершение аренды — тот же конвейер: правило **удаляется** (семантика keep_overdue — плановые с «сегодня» собственника сносятся, просрочка остаётся долгом объекта с обнулённым payment_id и origin 'payment', оплаченные операции остаются «платёж удалён»; rentals/GLOSSARY.md «Завершение», ревизия ADR 0053 2026-10-06), ссылка снимается, и отдельного «завершённого платежа» больше не бывает: правила завершённой аренды просто нет. Чтение несёт вычисляемый isRentalManaged. Платёжные факты (оплата) и звезда избранного гейту не подчиняются — не условия аренды; собственный конвейер аренды пишет мимо гейта по построению.
_Avoid_: «платёж аренды» как отдельная сущность, гейт на чтение, «Завершённый платёж» (отменён удалением правила при Завершении, #1161)

**История изменений платежа / Payment change log** (карта #1183, ADR 0065):
Append-only лог правок правила: одна строка на правку пользователя с массивом структурного дифа `changes` (словарь полей — как у мутационного аудита контекста; значения типизированы: копейки числом, регулярность каноническим JSON-объектом, даты «YYYY-MM-DD» или null; категория — ссылкой со снапшотом лейбла). Чипы экрана «История платежа» (режим изменений) собирает фронт из значений — сервер текста не строит: лексика повторяемости, денег и категорий канонически фронтовая (`recurrenceLabel` резолюции #452, `formatMoneyKopecks`), поиска на экране нет. Пауза и возобновление пишут строки с пустым `changes` и своими action; завершение строк не пишет — правило удалено, журнал каскадит вместе с ним (#1377); системные паузу/снятие архивного моста пишет тот же журнал с отметкой происхождения `origin` (тикет #1342: `auto_archive` — архивация/возврат объекта, null — ручное действие; все строки до тикета — null); создание и удаление строк не пишут — создание не правка, удаление каскадит журнал (надгробие «Платёж удалён» остаётся в «Истории действий»). Арендный конвейер пишет диф правки условий в историю управляемого платежа — тот же словарь и тот же доменный диф. Чип «Название изменено» возникает только из ручной правки названия (diff-patch PATCH: `title` едет только при касании пользователем); маркер `payments.title_is_manual` держит состояние «название когда-либо задано вручную». Чтение — по одному платежу, обратная хронология, двусторонний keyset; бэкфилла нет — правки до внедрения в истории не видны.
_Avoid_: «история действий» (это другая лента — action_journal, ADR 0061), серверные тексты чипов, записи о ранней/поздней оплате, строка о создании платежа, бэкфилл

**Долг / Debt**:
Накопленные незакрытые просроченные операции объекта. Существует, пока не закрыт оплатой или не отменён (удаление операции), — в том числе после удаления платежа; исчезает только с отменой всех его операций или с удалением всего объекта (объект сносится вместе со всеми данными).
_Avoid_: задолженность, непогашенный остаток, «зависшая» просрочка

**Пауза / Pause**:
Состояние платежа: вхождения в интервале паузы не генерируются вовсе — ни операций, ни долга, ни догона автоплатежом. Бессрочная, с сегодняшнего дня, снимается вручную; долг, накопленный до паузы, остаётся. У бессрочного правила в открытой паузе вычисление завершённости отвечает «завершён» — решение о действиях принимается по endDate правила (см. «Завершённый платёж»); открытая пауза запрещает и само завершение — complete отвечает 409, пока пауза не снята (#1340). У интервала есть происхождение `origin` (тикет #1342): `manual` — поставил пользователь (все паузы до тикета), `auto_archive` — системная автопауза архивации объекта: архивация ставит её всем живым правилам объекта (включая управляемые арендой — реакция на объект, не правка условий аренды, ADR 0053 §3) в транзакции архивации, возврат объекта из архива снимает ТОЛЬКО auto_archive-паузы, ручные остаются. Пока объект в архиве, пауза/возобновление правила отвечают 409, строка действий на странице платежа не рендерится вовсе (правка владельца 13.10: ни кнопок, ни пояснения — состояние несут бейдж карточки и подзаголовок списка).
_Avoid_: заморозка долга, отключение автоплатежа (это переключение режима), автопауза (без указания архивного происхождения)

**Категория / Category**:
Классификация платежа и операции, нейтральная к направлению (доход/расход выбирает пользователь на платеже, а не в справочнике). Единый нередактируемый дефолтный каталог (41 категория, включая «Другое» — замыкающую строку пикера; источник — Figma, генерация Go+TS из `tools/payment-categories/catalog.json`, БД ссылается слагом) и пользовательские категории уровня аккаунта (одна дефолтная иконка на серой подложке). Задаётся на платеже; операция наследует снапшотом при материализации; ручная операция получает категорию напрямую.
_Avoid_: категория дохода/расхода (справочник единый и не привязан к направлению), тег, статья

**~~Форма оплаты / Payment Form~~** (выбыл, ревизия 2026-10-01 — карта #1005, тикет #1006):
Бывшее поле платежа «перевод/наличные» со снапшотом в операцию: удалено целиком из модели, БД (колонки снесены миграцией 000145) и контрактов — write-only, нигде не читалось пользователем, ценности не несло (решение владельца, ревизия решения №3 ADR 0047). _Avoid_ сохраняет силу: «способ оплаты» — канонический термин Billing (привязанная карта T-Kassa), не payments-слово; метод расчёта.

**Тик / Tick**:
Идемпотентный прогон материализации: правила + паузы + «сегодня» → операции. «Сегодня» — дата в часовом поясе собственника объекта (ADR 0048): граница суток едина для всего аккаунта. Запускается ежечасным фоновым воркером и внутри мутаций контекста; чистое чтение не тикает.
_Avoid_: крон, джоба

**Материализация / Materialization**:
Создание операций по вхождениям платежа: все наступившие (дата ≤ сегодня) и ровно одно следующее будущее. Вхождение не создаётся, если его период повторения уже несёт операцию этого платежа — календарный месяц у месячного правила, неделя у недельного, год у годового, день у дневного: правка дня платежа не воскресает оплаченные месяцы фантомными просрочками и не удваивает долг незакрытых (#815). Дальнейший график — проекция.
_Avoid_: генерация задним числом, доматериализация закрытого периода

**Проекция / Projection**:
Вычисляемый график будущих вхождений после материализованного следующего: без записей в БД и без статусов.
_Avoid_: виртуальные операции
