# Notifications

Контекст уведомлений: хранимая лента (карта #734, модель — решение #737), каналы доставки (email, Web Push), push-подписки и события подписки. Доставка по каналам идёт через очередь River и dispatch-пайплайн (#740, ADR 0059): издатели пишут ленту и ставят джобы через `Publisher` — grace (#741) и каталог (#748–#752). Чтение ленты и настройки — REST (#743): keyset-страница, счётчик непрочитанных, прочтение/удаление, страница уведомления с живыми действиями; матрица настроек — email per-account, push per-device (ADR 0058, решение #738, миграция 000134). Per-event-type × per-channel настройки (ADR 0030) сняты вместе с таблицей (миграция 000132): категория «Тариф» честно всегда включена.

## Language

### Feed

**Категория / Notification Category**:
Группа per-channel настроек и иконка. Шесть значений: Аренда (`rental`), Платежи и операции (`payments_operations`), Задачи (`tasks`), Совместный доступ (`shared_access`) — настраиваемые; Тариф (`tariff`), Системные (`system`) — служебные, всегда включены, вне экрана настроек. Enum `notification_category`.
_Avoid_: тип события, канал

**Тип события / Notification Event Type**:
Конкретное событие ленты; принадлежит категории (`EventType.FeedCategory`). Каталог — 20 типов: 15 из решения #737, grace-пара `subscription_grace_entered` / `subscription_grace_expiring` (#741), `payment_reminder` — «Напоминание о платеже» (карта #822, #824), `access_role_changed` (#830) и `payment_auto_paid` — «Автоплатёж исполнен» (#1169). Изданы к настоящему моменту: grace-пара (#741), `rental_completed` — «Аренда завершена» (#748, скан по поясу собственника; с #777 — граничная джоба в полночь зоны дня после planned_end, скан — подстраховка), платёжная пара `payment_due` / `payment_overdue` — «Оплатите платёж» / «Платёж просрочен» (#749, скан по поясу собственника; с #776 — граничные джобы, с #1168 — в настенные 10:00 (due) / 22:00 (overdue) зоны, скан — подстраховка с instant-гейтом), `payment_reminder` (карта #822, #824 — скан по поясу + граничная джоба в 10:00 «даты − N» (#1168), та же очередь, что у платёжной пары), `task_overdue` — «Задача просрочена» (#750, scheduled-джобы в момент границы — минута срока timed-задачи, полночь зоны дня после срока date-only (#777) — + скан-подстраховка), шестёрка доступа `property_invitation` / `invitation_accepted` / `access_revoked` / `access_paused` / `access_resumed` / `member_left` (#751, хуки переходов access), смена роли `access_role_changed` — «Роль изменена» (#830, хук ChangeMemberRole) и тарифная пара `subscription_payment_succeeded` — «Оплата прошла» / `subscription_plan_changed` — «Тариф изменён» (#752, хуки биллинга). Хранится в enum `notification_event_type`.
_Avoid_: категория

Мёртвые значения `notification_event_type` (`free_reminder`, `operation_due`, `operation_overdue`, `lease_expiring`, `lease_requires_action`, а с #741 и `subscription_grace` — значение прямого канала, снесённого #741) и `notification_target_type` (`free`, `operation`, `recurring_operation`, `lease`) остаются в PostgreSQL навсегда (прецедент #277) — домен и контракты о них не знают.

**Уведомление / Notification**:
Строка ленты одного получателя: снимок текста (заголовок, тело, лейбл контекста — имя объекта/тарифа или «Системные уведомления»), payload-ссылки, личные флаги (прочитано `read_at`, удалено `deleted_at`). Одно событие = по строке на каждого получателя (fan-out); переписанный шаблон не трогает хранимые строки. Таблица `notifications`; момент события — UTC instant (`created_at`), группировка «Сегодня/Вчера» — дело экрана (#744).
_Avoid_: пуш, письмо, сообщение

**Снимок сущности / EntityRef**:
Payload-ссылка с карточными строками: `id` (переход) + `name` (карточка живёт даже после переименования/удаления сущности) + необязательные строки карточки — `address` у объекта, `email` у приглашающего (решение владельца 19.09.2026, #745). Оба — снимки момента публикации; строки, которых в снимке нет, карточка просто не рисует. Словарь издателей — #748–#752 (адрес из `properties.address`, email из профиля актора на момент события).

**Лента / Notification Feed**:
Хранимый список уведомлений пользователя, читается newest-first keyset-пагинацией (канон #597). Настройки глушат только email/push — строка ленты пишется всегда.
_Avoid_: история, журнал

**Получатель / Recipient**:
Пользователь, которому адресована строка. Объектные события — владелец + все активные участники (включая «Просмотр»); доступ — адресат по событию; Тариф — владелец; Системные — все пользователи. Инициатор не получает уведомление о собственном действии (actor-skip); один пользователь — одна строка, дублирования на устройства/роли нет.

**Действие / Action**:
Кнопка перехода на экран сущности, никогда не мутация. Вычисляется при чтении страницы уведомления (`GET /notifications/{id}`, #743) по живому состоянию сущности и правам читателя; возможные действия за событием закрепляет каталог (`ActionsForEvent`). Состояние ушло — кнопок нет; сущность удалена — уведомление остаётся без действий; роль «Просмотр» получает уведомления без кнопок-мутаций.
_Avoid_: кнопка-действие (выполняющая мутацию из ленты)

**Дедуп-ключ / Dedup Key**:
Пара (получатель, `dedup_key`), где ключ = (тип события, сущность, фаза/дата); уникальный индекс делает инвариант прочным: повтор с тем же ключом строку не создаёт. Словарь издателей: grace (#741) — `subscription_grace_entered:<subscription_id>:<YYYY-MM-DD конца окна>` (без даты, когда окно без известного конца); скан аренды (#748) — `rental_completed:<rental_id>:<plannedEndDate YYYY-MM-DD>` — продление аренды меняет дату, значит ключ: повторное «Ожидает действия» уведомляет заново; скан платежей (#749) — `payment_due:<rule_id>:<YYYY-MM-DD операции>` и `payment_overdue:<rule_id>:<YYYY-MM-DD операции>` — (правило, дата операции) из решения #737: долг, не гашеный неделями, держит один ключ и одну строку; reminder-нога (#822/#824) — `payment_reminder:<rule_id>:<YYYY-MM-DD операции>` — та же пара (правило, дата операции): одно напоминание на вхождение даже при смене оффсета после срабатывания; auto-paid-нога (#1169) — `payment_auto_paid:<rule_id>:<YYYY-MM-DD операции>` — та же пара: одно «исполнен» на вхождение; издатель задач (#750) — `task_overdue:<task_id>` — один task_id из решения #737: одна задача — одна просрочка, кто бы ни сработал первым (джоба или скан); перенос срока правила сносит задачу и материализует новую — новый id, новый ключ; издатель доступа (#751) — переходы с одноразовой сущностью ключуются голым membership id (`property_invitation:<membership_id>`, `invitation_accepted:<membership_id>`, `access_revoked:<membership_id>`, `member_left:<membership_id>` — invitation снесён активацией, revoke/leave сносят саму membership), повторяемые переходы — membership id + мгновение перехода в unix-секундах (`access_paused:<membership_id>:<unix>`, `access_resumed:<membership_id>:<unix>`): цикл пауза → восстановление → пауза — каждый раз новый факт, а повторная публикация того же перехода вставляет пусто; смена роли (#830) — `access_role_changed:<membership_id>:<unix>` по `updated_at` строки: каждая смена уведомляет заново, повтор той же смены — пусто; издатель тарифа (#752) — платёж подписки и переход подписки из решения #737 (`subscription_payment_succeeded:<payment_id>` — платёж применяется один раз, дубликат доставки — no-op без публикации; `subscription_plan_changed:<transition_id>` — апгрейд по payment_applied-переходу и назначение даунгрейда по downgrade_scheduled-переходу, повторное назначение — новый переход и новая строка).

**Счётчик непрочитанных / Unread Counter**:
Число непрочитанных неудалённых строк пользователя. Снижается кликом по уведомлению, открытием страницы и «Прочитать все»; удаление непрочитанного снижает его; пуш и email на читаемость не влияют.

### Channels

**Channel / Канал доставки**:
Транспорт доставки уведомления. Значения: `email`, `push`. Отдельного хранения канал не имеет: с пайплайном доставки (#740, ADR 0059) канал — отдельная джоба очереди (`notifications_email`/`notifications_push`), enum `notification_channel` дропнут вместе с таблицей per-channel настроек (миграция 000132).
_Avoid_: тип доставки

**PushSubscription / Push-подписка**:
Подписка устройства/браузера на Web Push-уведомления. Содержит endpoint URL (push-сервис), ключи шифрования (`p256dh`, `auth`). Один пользователь = N устройств. Таблица `push_subscriptions`. Endpoint — естественный ключ и секрет (RFC 8030 §8.3). Мастер-состояние устройства — само существование строки (спека #1028, решение владельца 01.10): строка есть = включено, строки нет = выключено; отдельного флага нет (колонка `enabled` снесена миграцией 000147 как вырожденная), выключение — жёсткая отписка (идемпотентный `DELETE /push/subscriptions`, 204 и при отсутствии строки) вместе с категорийными флагами.
_Avoid_: устройство, девайс, флаг мастера

**PushSender / Отправитель пушей**:
Порт `application.PushSender`: шифрует payload (RFC 8291), подписывает VAPID JWT (RFC 8292), отправляет POST на endpoint. Маппит коды ответа push-сервиса в доменные ошибки: `ErrSubscriptionGone` (404/410), `ErrRateLimited` (429), `ErrPushPayloadTooLarge` (413).

**PushPayload / Payload пуша**:
JSON-тело, отправляемое в service worker: `title`, `body`, `tag` (для замещения/группировки), `url` (навигация по тапу), `eventType`. Ограничение 3993 байта (практический потолок RFC 8030 после aes128gcm overhead).

**VAPID / Voluntary Application Server Identification**:
RFC 8292. P-256 ключ pair для идентификации application server'а перед push-сервисом. Публичный ключ отдаётся фронту через `GET /push/vapid-public-key`; приватный ключ и subject (`mailto:`/`https:` URI) — серверный секрет. Ротация ломает все подписки — не ротировать без миграции.

### Delivery pipeline

**Пайплайн доставки / Delivery Pipeline** (#740, ADR 0059):
Путь уведомления от издателя до каналов: издатель после коммита своего бизнес-транзакции (канон grace_events, post-commit) вызывает `Publisher.Publish` → в одной транзакции: строка ленты на получателя (in-app доставлено) + джобы `deliver_email`/`deliver_push` (River `InsertTx`). Строка и джобы атомарны: джоба без строки и строка без доставки не существуют. Джобы несут только id — контент читается из закоммиченной строки при доставке. Строго после коммита пайплайн толкает в стрим `notification.created` + `notification.unread_count` (#742, ADR 0060) — best-effort, на доставку каналов не влияет.

**Часовая группа / ScanGroup** (#748–#750, #776–#777):
Ежечасный зональный обход notifications — общий панцирь трёх сканов-издателей: воркер `platform/scheduler` (общая обёртка `ZoneTickWorker`, свой advisory lock) раз в час запускает `application.ScanGroup` (`application/scan.go`), а группа — членов в порядке каталога: скан завершения аренды (#748), скан платежей (#749), скан задач (#750). «Сегодня» каждого пояса — по канону тиков ADR 0048 (p.2 — дата как UTC-полночь `DateAtUTCMidnight`, p.3 — один «сегодня» на пояс собственника); зоны перечитываются каждым проходом заново — у прохода состояния нет; память живут дедуп-ключи опубликованных строк и стоящие unique-джобы букинга. Отказы изолированы: сломанный член, зона или цель не останавливает остальных, собранная ошибка падает целиком. У прохода две роли (дополнение ADR 0048 p.3, решение владельца 21.09.2026): **бэкфилл букинга** — каждый проход бронирует граничные джобы границ из окна (now, now+48ч], повторный запрос возвращает стоящую джобу, — и **ретроспектива-подстраховка** — догоняет всё, что джобы пропустили (простой воркера, граница, ещё не попавшая в окно букинга); флад публикаций при первом проходе после простоя — ожидаемая ретроспектива, дедуп-ключи делают её однократной.
_Avoid_: крон по зоне (полуночный fan-out отклонён — ADR 0048), per-zone состояние тика

**Граничная джоба / Boundary Job** (#750, #776, #777; решение владельца 21.09.2026 — «все уведомления — чётко по времени», канон задач #750 → платежи #776 → аренда #777):
Unique-джоба River (ADR 0059), забронированная на точный момент дневного события — не на ближайший часовой проход (канон — дополнение ADR 0048 p.3): полночь зоны дня после `planned_end` (аренда #777), 10:00 даты операции / 22:00 следующего дня (due- и overdue-ноги платежей #776, #1168), 10:00 «даты − N» (reminder-нога, карта #822, #1168), 10:00 даты операции (auto-paid-нога, #1169), минута срока timed-задачи / полночь дня после срока date-only (задачи #750/#777). Настенное время через `AT TIME ZONE` пояса собственника (конвенция DST; с #1168 платёжные границы — 10:00/22:00, полночь как момент доставки ушла: будил). Очереди — по сущности (`notifications_rentals`, `notifications_payments` — все четыре платёжные ноги в одной, `notifications_tasks`), unique по args во всех нетерминальных состояниях — максимум одна джоба «в полёте»; args повторяют дедуп-ключ события (перечисление — у «Очереди»); бюджет попыток 5 (публикация — одна запись ленты). Пробуждение — момент доставки: джоба перечитывает живое событие (условия ноги на момент пробуждения), не доверяя брони, и уходит вежливым no-op, когда событие перестало быть живым — завершено, продлено, выполнено, оплачено, отменено, снесено, уведено в архив (полные условия ног — в статьях сканов); в норме публикует ровно в границу, часовой проход после неё вставляет пусто — идемпотентность несёт дедуп-ключ, а скан остаётся подстраховкой. Скелет и планировщики — `adapters/notificationsjob` (`boundaryWorker`, `PaymentBoundaryScheduler` и родня).
_Avoid_: крон, таймер в процессе, скан (скан — подстраховка, не носитель момента)

**Шов планирования / Scheduling Seam** (#775):
Пост-коммитная передача стоящих невыполненных задач из потоков создания/правки правила tasks в notifications: мутация после коммита своей транзакции отдаёт id задач через consumer-declared порт `tasksapp.MaterializedTaskNotifier`, адаптер `adapters/taskschedule.Seam` передаёт их издателю задач, который решает по каждой — жива и граница впереди: граничная джоба на момент границы (созданная между проходами срабатывает ровно в свой момент, без ожидания тика); рождённая просроченной: публикация немедленно; не жива: no-op. Канон grace-events: захват списка — внутри транзакции, вызов — строго после коммита, best-effort — отказ шва правило не валит. Шов есть только у задач: у платежей его нет сознательно (#776) — материализационный тик генерирует вхождения на годы вперёд, граничные джобы бронируются заранее часовым проходом, а правило, созданное в последний час перед границей, догоняет скан.
_Avoid_: хук события (шов передаёт id задач, а не событие), вызов в транзакции мутации

**Скан завершения аренды / Rental-Completed Scan** (#748, #777):
Издатель каталога `rental_completed` — не хук перехода, а часовой зональный скан (канон тиков ADR 0048 p.3): один «сегодня» на пояс собственника объекта, по всем зонам; цели — незавершённые аренды с плановым окончанием строго раньше «сегодня» на неархивном объекте (первый проход после полуночи пояса = «на следующий день после plannedEndDate», решение #737 тип №1; архив вне скана — канон тиков active/maintenance: мутации аренды архивного объекта отвергаются, кнопки были бы тупиковыми). Идемпотентность несёт дедуп-ключ, а не состояние прохода: повторный проход — пусто, продление (новая дата окончания) — новый ключ и повторное уведомление. Получатели — владелец + активные участники («Просмотр» включён); инициатора у системного события нет (actor-skip не срабатывает). Пейлоад — снимок объекта (id, имя, адрес) и id аренды; кнопки «Продлить»/«Завершить» вычисляются при чтении (#743), а диплинк пуша/письма/тоста строится из этих id. Отказы изолированы по зоне и по аренде — сломанная цель не останавливает проход. **Граничные джобы** (#777, решение владельца 21.09.2026: все уведомления — чётко по времени, канон платежей #776): часовой проход в окне (now, now+48ч] бронирует unique-джобы `notifications:rental_completed` (args = аренда + planned end — пара дедуп-ключа; отдельная очередь `notifications_rentals`), `ScheduledAt` — полночь зоны дня после planned_end (настенные 00:00, `AT TIME ZONE` пояса — конвенция DST платежей). Джоба на пробуждении перечитывает needs_attention как момент доставки: не завершена, planned end (= забронированной дате) строго раньше «сегодня» зоны, неархивный объект — завершённая, продлённая (дата уехала с забронированной: пара мимо, новая граница встаёт своим проходом), архивная — вежливый no-op. В норме джоба публикует ровно в полночь, проход скана после неё вставляет пусто — дедуп-ключ несёт идемпотентность.

**Скан платежей / Payments Scan** (#749, #776):
Издатель каталога `payment_due` / `payment_overdue` — вторая нога часовой группы (`ScanGroup` бежит вместе со сканами аренды и задач одним воркером). Цели — planned-операции (вхождения Payments; JOIN к правилу заодно отсекает ручные факты, осиротевшие операции снесённого правила и отменённые надгробия) на неархивном объекте: нога «Оплатите платёж» — операции с датой ровно «сегодня» пояса на правилах без автоплатежа (автоплатёжное вхождение тик гасит в тот же день — ADR 0049; если автосписание не состоялось, операция станет просроченной и скажет нога просрочки), нога «Платёж просрочен» — операции с датой строго раньше «сегодня», автоплатёжные включены (ретроспективных автогашений нет). **Граничные джобы** (#776, решение владельца 21.09.2026: все уведомления — чётко по времени, канон задач #750): часовой проход в окне (now, now+48ч] бронирует unique-джобы `notifications:payment_due` / `notifications:payment_overdue` (args = правило + дата операции; отдельная очередь `notifications_payments`), `ScheduledAt` — настенные часы пояса (#1168): 10:00 зоны даты операции для due-ноги, 22:00 зоны следующего дня для overdue-ноги; материализационный тик генерирует вхождения на годы вперёд, поэтому джоба встаётся заранее, повторный запрос возвращает стоящую джобу. Граница — настенное время (`(date ± …)::timestamp + time '10:00'/'22:00'` затем `AT TIME ZONE` пояса, #1168): 10:00/22:00 всегда легальны — DST-крайний случай полуночи исчезает из платёжных ног. Скан-ноги несут instant-гейт (#1168, прецедент — скан задач): предикат даты дополнен «граница <= now» — часовая подстраховка не публикует раньше границы (иначе первый проход после местной полуночи обгонял бы джобу на 9–21 часа), а опоздавшую догоняет в первый проход после неё; date-половина несёт семантику самогасания due/персистентности overdue. Джоба на пробуждении перечитывает живое (условия ноги на момент пробуждения: planned, не автоплатёж для due, дата против «сегодня» зоны, неархивный объект, живое правило) — оплаченное, отменённое, перекатившееся, осиротевшее — вежливый no-op. Часовой скан остаётся подстраховкой: ретроспектива после простоя и первая публикация правила/операции, созданных в последний час перед границей (шов планирования правил платежей — не #776). Пауза безопасна: будущих planned у правила на паузе тик не оставляет. Идемпотентность — дедуп-ключ (правило, дата операции): просрочка, не гашеная неделями, сканится ежедневно и остаётся одной строкой; в норме джоба публикует ровно в границу (10:00/22:00), проход скана после неё вставляет пусто. Тексты — копия решения #737 дословно; название в тексте — текущее название правила (ссылка ведёт на страницу правила), сумма и дата — операция. Сумма форматируется на сервере (целочисленно из копеек, NBSP-группы): тело — хранимый снимок, самодостаточный без UI, — легитимное серверное место форматирования денег рядом с фронтовым `formatMoneyKopecks`. Пейлоад — снимок объекта (id, имя, адрес), id правила и дата операции (`payment_date`) — живая проверка кнопки «Оплатить» (`PaymentOpen`) ищет planned-операцию этого правила с этой датой: гашена/отменена/правило снесено — кнопки нет (#743). Отказы изолированы по брони, зоне и операции; в одной зоне нога срока бежит перед ногой просрочки.

**Скан напоминаний / Payments Reminder Leg** (карта #822, #824):
Издатель каталога `payment_reminder` — третья нога платёжного скана внутри часовой группы, тот же двойной механизм, что у платёжной пары #776 (граничная джоба + скан-подстраховка). Цели — planned-вхождения правил с заданным напоминанием (`payments.reminder_offset_days`, 1/3/7, NULL = напоминаний нет) на неархивном объекте, чей **день напоминания** — дата операции минус оффсет, ровно «сегодня» пояса. Автоплатёжные правила включены: напоминание живёт независимо от auto_pay (решение владельца, #823 — аренда ставит его вместе с автоплатежом). **Граничные джобы**: часовой проход в окне (now, now+48ч] бронирует unique-джобы `notifications:payment_reminder` (args = правило + дата операции; очередь `notifications_payments`), `ScheduledAt` — настенные 10:00 «даты − N» зоны (#1168; конвенция DST #776). На пробуждении джоба перечитывает живое: planned, неархивный объект и **текущий** оффсет правила всё ещё кладёт день напоминания на «сегодня» — оффсет, сменённый после букинга, отправляет устаревшую джобу вежливым no-op (новая граница встаёт своим проходом), как и оплаченное/отменённое/осиротевшее/перекатившееся. **Семантика границ** (зафиксирована #824): пауза — внутри паузы вхождения не генерируются, напоминаний нет (ADR 0049 §2); окончание (правка end_date, завершение аренды) — снесённые future planned напоминаний не получают; «до оплаты меньше N» — если день напоминания вхождения уже прошёл к моменту установки, на ЭТО вхождение напоминание не придёт, первое придёт на следующее; симметрично при увеличении оффсета, когда новая граница «дата − N′» уехала в прошлое, — на это вхождение напоминание не придёт вовсе (старая джоба уходит no-op, скан видит только «день = сегодня»). Идемпотентность — дедуп-ключ (правило, дата операции): одно напоминание на вхождение даже при смене оффсета после срабатывания. Тексты — тайтл «Напоминание о платеже», тело — форма due-ноги (факт срока); пейлоад и получатели — как у платёжной пары (#737: владелец + активные участники, снимок объекта, id правила + дата операции), диплинк — страница правила.

**Издатель «Автоплатёж исполнен» / payment_auto_paid publisher**:
Издатель каталога `payment_auto_paid` — четвёртая нога платёжного скана внутри часовой группы, тот же двойной механизм, что у платёжной пары #776 (граничная джоба + скан-подстраховка; #1169, карта #1162). Цели — вхождения auto_pay-правил (ADR 0049) на неархивном объекте, **исполненные тиком в свой день**: штамп `operations.paid_source = 'auto_pay'` (миграция 000150) + `status='paid'`, `paid_date` = дата операции — тик гасит вхождение строго в его день. **Пер-платёжный флаг** (#1189): ногу гейтит `payments.notify_auto_paid` (словарь payments — «Уведомление об автоплатеже») во всех трёх механизмах — молчащее правило (дефолт новых, макет 3214-72739) не бронит джобу, не попадает в скан и отвечает no-op в разрешении; флаг, снятый после букинга, глушит стоящую джобу. **Решение владельца по гриллингу #1167**: событие — только об автосписании; ручная оплата того же вхождения («Оплатить сейчас», штамп `paid_source='manual'`) молчит — владелец сам знает; неудачное автосписание молчит в 10:00 — в 22:00 скажет нога просрочки; бэкфилла нет — живой день только (пропущенные при простое дни не ретроспективятся, просрочка персистентна и догонит). **Граничные джобы**: часовой проход в окне (now, now+48ч] бронирует unique-джобы `notifications:payment_auto_paid` (args = правило + дата операции; очередь `notifications_payments`), `ScheduledAt` — настенные 10:00 дня операции зоны (#1168). На пробуждении джоба перечитывает живое (разрешение в момент доставки): штамп тика своего дня, неархивный объект, флаг и дата = «сегодня» зоны; всё прочее — вежливый no-op. Скан-нога — подстраховка с instant-гейтом 10:00 (#1168). Идемпотентность — дедуп-ключ (правило, дата операции). Тексты — тайтл «Автоплатёж исполнен», тело «Платёж «X» по объекту «Y»: сумма, оплачен автоплатежём. Дата операции: …»; пейлоад и получатели — как у платёжной пары (#737), диплинк — страница правила; actor-skip не нужен (событие системное).

**Скан задач / Tasks Scan** (#750, #777):
Издатель каталога `task_overdue` — третья нога часовой группы, единственная с двумя механизмами (решение #737: «минутная точность — River scheduled jobs на момент срока + скан-подстраховка»; с #777 — решение владельца «все уведомления — чётко по времени» — джоба есть у обеих форм, канон платежей #776). **Scheduled-нога** (любая датированная задача): каждый часовой проход бэкфиллит unique-джобы `notifications:task_overdue` (args = task_id, уникальна во всех нетерминальных состояниях, повторный запрос возвращает стоящую джобу) для задач, чей момент границы — timed-задачи `(due_date + due_time)`, date-only задачи полночь дня после срока (`due_date + '24:00'`, настенные 00:00 — конвенция DST платежей), прочитанное в поясе владельца, — попадает в окно (now, now+48ч]; `ScheduledAt` джобы = сам момент границы, пробуждение — «в минуту срока»/«в полночь». Тот же букинг делает **шов планирования** (#775): при создании/правке правила tasks-контекст пост-коммит (канон grace-events — захват в транзакции, вызов после коммита, best-effort) передаёт стоящие невыполненные задачи правила, и notifications решает по каждой: жива и граница впереди — джоба на момент границы (созданная между проходами срабатывает ровно в свой момент, без ожидания следующего тика); граница уже прошла — публикация немедленно (рождённая просроченной — без ожидания скана, включительно — канон минуты); не жива — no-op (снесена, completed). Повторный букинг идемпотентен, часовой проход остаётся подстраховкой — ретроспектива после простоев, дедуп молчит в норме. Джоба на пробуждении перечитывает задачу (разрешение в момент доставки): снесена правкой правила, выполнена или ушла на архивный объект — вежливый no-op; живая — публикует. **Скан-нога** (подстраховка): тот же зональный обход, цели — активные датированные задачи на неархивном объекте или без объекта (ADR 0052): со временем — срок-мгновение уже прошло (в минуту срока, включительно — канон просрочки tasks), дата-без-времени — дата строго раньше «сегодня» пояса. Без срока — никогда; напоминание «сегодня» не делается (решение #737). **Две ноги — одна строка**: дедуп-ключ — голый task_id, кто бы ни сработал первым. Пейлоад — снимок объекта (id, имя, адрес; безобъектная — без объекта и без лейбла, макет), task_id и task_rule_id: экран задачи — экран её правила, переход («Выполнить» и диплинк пуша/письма/тоста) ведёт по правилу — объектная задача через `/properties/{pid}/tasks/{rule_id}/edit`, безобъектная через `/tasks/{rule_id}/edit` (ADR 0052). Получатели — владелец + активные участники; безобъектная — владелец. Отказы изолированы по брони, зоне и задаче.

**Хуки доступа / Access Transition Hooks** (#751, #829, #830):
Издатель шестёрки доступа (типы №5–№10) и смены роли (#830, `access_role_changed` — «Роль изменена», решение владельца 23.09: «изменение ваших прав или доступа» из матрицы настроек, часть каталога v1, не покрытая типом) — не скан, а хуки переходов access: события `InvitationActivated`, `MembershipGranted` (#829 — мгновенная посадка зарегистрированного), `MembershipSuspended`, `MembershipResumed`, `MembershipRevoked`, `MemberLeft`, `MembershipRoleChanged` (#830) покидают access-контекст через порт `AccessEventPublisher` (канон grace-events: события чистые — только id, флаги и мгновения; снимки имён резолвятся при публикации) и составной корень подписывает на них `AccessPublisher` над тем же пайплайном. Швы по владельцу транзакции: сервисы access публикуют строго после коммита; `SlotCoordinator` бежит внутри чужих транзакций (billing, properties) и публикует в транзакции — та же форма, что у заменённых им lifecycle-писем (issue #162), пул (64 соединения) переживает второе соединение публикации. **Семантика**: №6 «Приглашение принято» — пригласившему при любой активации; №5 «Приглашение в объект» — адресату при любой активной посадке: и при активации приглашения при регистрации, и при мгновенной посадке зарегистрированного (#829: активные исходы Invite/AddProperties и потока InviteByEmail — №6 на мгновенную посадку не существует, принятия не было; consequence — зарегистрированному приглашённому уходит и email/пуш по матрице каналов, дефолт «вкл») (копия «Теперь объект доступен вам совместно» была бы ложью при посадке без слота), при посадке без слота вместо №5 — системное №8; отозван/покинул — только при активной membership (приостановленная уже скрыта — канон #162); «Роль изменена» (#830) — участнику при смене его роли, актор = сменивший, копия «{Имя} изменил вашу роль в объекте «X» на «Редактирование»/«Просмотр»» (отображаемые имена ролей — канон чарта #692, per-context копия канона #748), дедуп `access_role_changed:<membership_id>:<unix>` по мгновению смены (`updated_at` строки) — каждая смена уведомляет заново (канон циклов пауза/восстановление #751), приостановленная membership молчит (объект уже скрыт — канон #162), действие `open_property_members`. **Без имени**: у системного перехода (пауза слотами, восстановление) актора нет — текст без имени («Ваш доступ к объекту „X“ приостановлен») по собственному образцу каталога (№10); с ручными паузами карты «Совместный доступ 2.0» актор появится — с-акт-вариант уже в коде. {Имя} — display-name канона access (имя, иначе «Пользователь» — карта #1105, аменд #1123: телефон больше не фолбэк), per-context копия (канон #748). **Прямые письма снесены**: access_revoked, access_suspended, access_restored, downgrade_summary, invitation_activated, member_left заменены строками ленты + каналами по матрице «Совместного доступа»; остались прямыми только invite-письмо незарегистрированному (получателя-юзера ещё нет) и «объект удалён». Тексты — решение #737 дословно.

**Хуки тарифа / Tariff Transition Hooks** (#752):
Издатель тарифной пары (типы №13–№14) — не скан, а хуки биллинга: события `PaymentSucceeded`, `PlanUpgraded` и `PlanDowngradeScheduled` покидают billing через порт `EventPublisher` (общий с grace-парой #741; канон grace-events — захват внутри транзакции, публикация строго после коммита, best-effort; carrier `tariffEvents` рядом с `graceEvents`) и составной корень подписывает `TariffPublisher` над тем же пайплайном. **Швы по владельцу факта**: №13 и апгрейд №14 захватываются в `applySucceededPayment` — общем шве применения успеха (webhook, reconciliation- и renewal-воркеры), где платёж, оба тарифа и послеприменительная валидность в руках; №14-даунгрейд — в момент назначения (`scheduleDeferredDowngrade`, после коммита планирования ChangeTariff). **Семантика ног №14**: апгрейд — тариф сменился по оплате вверх (классификация `ClassifyTariffChange` по записям тарифов, не по id), даунгрейд — по оплате вниз не уведомляет (нога №14 — момент назначения, платёж говорит №13), применение назначенного даунгрейда воркером в конце периода — молча (факт озвучен при назначении); продление — только №13. **Получатель** — владелец (актора у системных событий нет). **Снимки при публикации**: слаг тарифа резолвится из tariffs портом `TariffEventViewSource` (consumer-declared), отображаемое имя — словарь фронта («Про»/«Бизнес»/«Базовый», неизвестный слаг — как есть, per-context копия канона #748); отказ резолва роняет публикацию. **Тексты** — решение #737 дословно: №13 «Оплата тарифа «{тариф}» на {сумма} прошла успешно. Подписка активна до {дата}» (сумма — формат #749, дата — рендеринг grace-дедлайна, день-месяц), №14 — «Тариф „{тариф}“ активирован» (апгрейд, дата-до = валидность после оплаты) и «С {дата} тариф сменится на „{тариф}“» (назначение, дата = конец оплаченного периода). Лейбл строки — имя тарифа. **Payload тарифа** — слаг, период, сумма, дата до (решение #737): апгрейд несёт сумму применённого платежа и дату-до; у назначения даунгрейда ни суммы (платежа не было — строка суммы принадлежит применённому платежу №13 и ноге апгрейда), ни даты-до (цель ещё не активна) нет — карточка строку без снимка просто не рисует (канон #745). **Действия**: №13 без кнопок (решение #737), №14 — `open_tariffs` (глобальный экран, стоит всегда, #743); диплинки обоих — /profile/tariff.

**Очередь / Delivery Queue**:
River (Postgres-очередь, ADR 0059) в процессе API; очереди `notifications_email`, `notifications_push` (независимые потолки воркеров), `notifications_tasks` — граничные джобы задач (#750, #777), `notifications_payments` — граничные джобы платежей (#776) и `notifications_rentals` — граничные джобы аренды (#777) (все — фикс-потолки без env-ручек). Ретраи — дефолтная лестница River (`attempts^4 ± 10%`), бюджет 8 попыток на канал доставки (у task-, payment- и rental-джоб свой — 5: публикация — одна запись ленты); исчерпание → `discarded` (запросable, retention 7 дней). Дедуп джоб: unique по args (= id уведомления; у task-джобы — task_id, у payment-джоб — правило + дата операции, у rental-джобы — аренда + planned end) во всех нетерминальных состояниях — у одного уведомления/задачи/граничного события максимум одна джоба «в полёте». Доставка at-least-once: дубликат письма/пуша лучше потери.

**Доставка в момент доставки / Delivery-time resolution** (#740):
Джоба сама в момент доставки проверяет всё, что может устареть: контакт получателя (нет верифицированного email — leg пропускается), живой список push-подписок (мертвые 404/410 удаляются на месте) и матрицу настроек категория × канал — email-джоба спрашивает account-матрицу (`DeliverySettings`), push-джоба фильтрует подписки категорийным флагом (`Categories.Allows`; мастера-флага нет — подписки выключенного устройства просто нет в списке, спека #1028).

**Настройки / Settings** (#743, решение #738, ADR 0058; пуш-половина переписана спекой #1028 — решение владельца 01.10):
Матрица категория × канал в двух местах: **email — на аккаунте** (таблица `notification_email_preferences`, одна строка на пользователя, четыре настраиваемые категории; нет строки = включено; `GET/PUT /notification-preferences` — полная замена) и **push — на устройстве** (четыре категорийных флага прямо на push-подписке; `GET/PUT /push/subscriptions/preferences` по endpoint URL; `POST /push/subscriptions` несёт категории явно, omitted = все ВКЛ). Мастер-тумблер устройства — само существование строки: выключение = жёсткая отписка (идемпотентный `DELETE /push/subscriptions` — 204 и при отсутствии строки, 404 нет), повторное включение = новая подписка с чистого листа (все категории ВКЛ); `PUT preferences` — строгий 404 по чужому/неизвестному endpoint (это проверка правды, в нормальном флоу недостижим). Тариф и Системные всегда включены, в настройках не хранятся. Лента настройками не глушится — пишется всегда.
_Avoid_: opt-out таблица (ADR 0030), per-event-type настройки, флаг мастера

**Бюджет провайдера / Provider Budget**:
Глобальный email-лимит (`NOTIFICATIONS_EMAIL_PROVIDER_PER_MINUTE`, токен-бакет) списывается внутри email-джобы перед отправкой; исчерпание — `JobSnooze` (попытка не тратится). Потолок одновременных SMTP-вызовов — `MaxWorkers` очереди. Per-user бюджеты (5/час и пр., ADR 0013) остаются в точках HTTP-лимитов — в пайплайне их нет.

**Метрики доставки / Delivery Metrics**:
`notifications.email.dispatched{outcome=sent|skipped|rate_limited|failed|cancelled}` и `notifications.push.dispatched{outcome}` (канон webpush) + спаны/метрики River через `otelriver` → Uptrace. Алерты: устойчивый рост `rate_limited` — узкий бюджет провайдера; всплеск `discarded` в `river_job` — сломанный воркер.

### Push as best-effort side channel

Push delivery is best-effort: push failures (429, 5xx, no subscription) are logged but never block email delivery. Dead subscriptions (404/410, `ErrSubscriptionGone`) are deleted on the spot.

### Push delivery observability

`webpush.Metrics` exposes a single counter `notifications.push.dispatched` with an `outcome` attribute (`sent`/`gone`/`rate_limited`/`failed`). The cleanup rate of dead subscriptions — the volume of subscriptions the push delivery worker deletes because the push service returned 404/410 (`ErrSubscriptionGone`) — is observable as `notifications.push.dispatched{outcome=gone}` in Uptrace. The metric is recorded by the adapter before the domain error is returned, so every gone outcome is counted even if the DB delete fails. To monitor cleanup on prod, alert on a sustained non-zero `gone` rate (indicates subscription churn — devices uninstalled, ITP purges, OS token expiry).

### Declarative Web Push — decision (iOS)

**Decision: classic service-worker Web Push only for v1; Declarative Web Push (iOS/iPadOS 18.4+) deferred.** All notifications carry a visible notification (`showNotification` mandatory — iOS revokes the subscription on silent push), so the declarative format's main draw — silent/navigate-only messages without a `push` handler — adds nothing the v1 notifications need. The classic SW-push path (`public/sw.js` push-handler, research `docs/research/ios-pwa-push.md` §1.4) works on Android Chrome and iOS 16.4+ installed PWA alike. Declarative Web Push would primarily help if (a) we shipped silent/technical pushes, or (b) ITP purges of SW registrations started killing subscriptions at scale (the declarative format decouples the subscription from the SW). Neither applies to v1. Re-evaluate when a silent-push use case lands.

## Stream

**Стрим / Event Stream** (#742, ADR 0060):
Общий пользовательский SSE-стрим `GET /notifications/stream` — живой слой поверх ленты: тосты, бейдж непрочитанных; изменения сущностей (карта #714) — отдельный стрим `/realtime/stream` (ADR 0062). Авторизация — та же cookie-сессия (401 problem+json до старта стрима); транспорт однонаправленный, любые мутации — только через обычный API. Кадры best-effort: состояние клиент дочитывает своими запросами, лента остаётся системой записи. Тосты кадра `created` клиент глушит push-настройкой устройства (решение #737, #790): заглушённая категория тоста не получает, а лента и бейдж обновляются по тем же кадрам всегда — гейт на фронте, контракт кадров не меняется.
_Avoid_: пуш (это другой канал), WebSocket, «realtime-состояние» (стрим не несёт состояния)

**Хаб / Hub**:
`internal/platform/sse.Hub` — реестр открытых соединений в памяти процесса. Лимит 8 соединений на пользователя (вкладки/устройства, старейший вытесняется), буфер 32 кадра, переполнение = медленный потребитель: соединение закрывается, клиент переподключается и перечитывает. Публикация никогда не блокирует издателя. На остановке процесса хаб закрывается первым — graceful shutdown не ждёт долгоживущие стримы.

**Конверт / Envelope**:
JSON внутри кадра: `{v, occurredAt, payload}` — версия схемы, момент события (RFC3339 UTC), типизированная нагрузка из id и дисплейных полей. Имя события — стабильное грубое: `connected` (старт), `notification.created` (тост: id, категория, заголовок, тело, deeplink), `notification.unread_count` (бейдж). Новые имена добавляются без ломки старых клиентов (нет слушателя — кадр игнорируется); ломающее изменение payload — подъём `v`.

**Курсор / Last-Event-ID**:
Заголовок переподключения с монотонным id кадра (последовательность хаба). В v1 курсор логируется, replay не реализован: клиент на каждом открытии (включая переподключение) перечитывает живое через react-query. Ring-buffer replay — заготовленный v2.

### Stream observability

`sse.connections` (gauge) — открытые соединения прямо сейчас, нагрузочная граница транспорта; `sse.frames.dropped` — вытеснения медленных потребителей, устойчивый ненулевой темп = клиенты не успевают или соединения зависают. Метрики nil-safe: без OTel-провайдера (локально, тесты) инструмент — no-op.
