# property-attributes

Единый источник правды для каталога атрибутов недвижимости. Из этого каталога
генерируется код в Go, frontend TS и admin TS (см. раздел [Генератор](#генератор)
ниже).

## Файлы

- `catalog.json` — сам каталог (11 типов объектов, поля, группы). Верхних границ
  и кросс-правил нет — только минимумы (ADR 0069).
- `catalog.schema.json` — JSON Schema (draft 2020-12) для самопроверки каталога.
- `validate-source.mjs` — утилита: валидирует `catalog.json` против схемы через ajv.
- `generate.mjs` — генератор артефактов кода (Go + frontend TS + admin TS) из каталога.
- `gen/` — исходники генератора: `validate.mjs` (общая ajv-логика), `model.mjs`
  (канонические данные: порядок типов/полей/опций, правила), `emit-go.mjs`,
  `emit-frontend-ts.mjs`, `emit-admin-ts.mjs`, `gofmt.mjs`.
- `package.json` — npm-пакет с devDep `ajv` / `ajv-formats` и скриптами `validate`
  и `generate`.

## Почему это существует

До этого каталог атрибутов размножался вручную в трёх местах монорепо с
подвижными расхождениями:

1. Go — `apps/backend/internal/properties/domain/attributes.go`
2. Frontend — `apps/frontend/features/property-attributes/lib/{catalog,labels,validate,format}.ts`
3. Admin — `apps/admin/src/lib/propertyAttributes.ts`

Любое изменение требовало правок в трёх файлах на двух языках. Здесь каталог
живёт в одном нормализованном JSON, а код для трёх стеков будет генерироваться
из него (будущая задача — генератор артефактов).

## Как валидировать

```sh
cd tools/property-attributes
npm install
npm run validate
```

Ожидаемый вывод: `catalog.json: OK (11 типов, N полей)`.

## Генератор

Из каталога генерируются артефакты кода для трёх стеков. Генератор сначала
валидирует `catalog.json` против схемы (переиспользует ту же ajv-логику, что
`validate-source.mjs`), и при любой ошибке схемы отказывается что-либо писать.

```sh
cd tools/property-attributes
npm run generate      # или: node generate.mjs
```

### Что производит генератор

| Стек | Путь | Назначение |
| --- | --- | --- |
| Go | `apps/backend/internal/properties/domain/zz_catalog.gen.go` | Самодостаточный модуль пакета `domain`: `fieldDef`/`attrKind`, карты полей по типам, `fieldsForType`, `CatalogKeys`, `FilterByType`, `ValidateAttributes`, `validateField` |
| Frontend TS | `apps/frontend/features/property-attributes/lib/generated/{attr-keys,catalog,labels,validate}.ts` | Типы `AttrKey`/`AttrField`/`AttrGroup`, `catalog`, `groupLabels`, `fieldsForType`, `findField`, `fieldLabels`, `enumLabels`, `validateField`, `validateAttributes`, `filterByType` |
| Admin TS | `apps/admin/src/lib/generated/{types,attr-keys,catalog,labels,format}.ts` | Самодостаточные типы (`PropertyType`, `PropertyAttributes`, `AttrKey`), `catalog`, `groupLabels`, `fieldsForType`, `findField`, `isPropertyType`, `fieldLabels`, `enumLabels`, `formatAttributeValue`, `formatAttributesForCardGrouped` |

Все сгенерированные файлы начинаются со строки
`// Code generated by tools/property-attributes/generate.mjs from catalog.json. DO NOT EDIT.`

### Go-артефакт: единственная реализация

Сгенерированный Go-файл **полностью самодостаточен** и является **единственной
реализацией** символов каталога в пакете `domain` (шаг миграции 1.4b давно
удалил hand-written дубликаты из `attributes.go` — там остались только типы
`PropertyType`/`Attributes`/`ValidationResult`). Менять валидацию/каталог
вручную нельзя — правь `catalog.json` и регенерируй.

### Статус интеграции

**Интегрировано** (шаг 1.4b): приложения импортируют сгенерированные артефакты —
Go из `zz_catalog.gen.go`, frontend из `lib/generated/*` (тонкие реэкспорты
`lib/{catalog,labels,validate}` держат исторические пути импорта), admin из
`src/lib/generated/*`. Ручные дубликаты каталога удалены. Сборки и тесты всех
трёх стеков остаются зелёными; любое правое изменение каталога — только через
`catalog.json` + регенерацию.

### Идемпотентность

Повторный запуск `node generate.mjs` produces byte-идентичные файлы.

### Что осталось hand-written

Логика, не выводимая из `catalog.json`, намеренно не генерируется и остаётся в
ручных файлах:

- Сами типы `PropertyType`, `Attributes`/`PropertyAttributes`, константы
  `PropertyTypeApartment` и т.д. — они живут в `property.go` (Go) и
  `entities/property/model/types.ts` (frontend). Admin их дублирует
  самодостаточно (генерируется в `generated/types.ts`).
- API/domain-слой поверх атрибутов (`NewProperty`, `Validate` и т.д. в Go).
- Любая UI-логика рендеринга сверх format-функций (админка).

### gofmt

Если на машине доступен бинарник `gofmt` (Go toolchain), генератор прогоняет
Go-артефакт через него — выдача каноническая (выравнивание map-литералов, нет
лишних пустых строк). Если `gofmt` не найден, файл пишется неотформатированным и
печатается предупреждение; CI/Makefile может всегда догнать
`gofmt -w apps/backend/internal/properties/domain/zz_catalog.gen.go`.

## Как править

1. Измени `catalog.json`.
2. Запусти `npm run validate` — каталог должен пройти проверку схемы.
3. Запусти `npm run generate` — регенерируй артефакты (`zz_catalog.gen.go` +
   frontend/admin `generated/`); перегенерация byte-идентична при том же
   каталоге. Работающий код трогать руками нельзя.

## Структура catalog.json

```jsonc
{
  "version": 1,
  "types": {
    "apartment": {
      "label": "Квартира",
      "fields": {
        "rooms": { "kind": "enum", "label": "Комнаты", "options": { "studio": "Студия", ... }, "group": "about_object" },
        "area_total": { "kind": "number", "label": "Общая площадь", "unit": "м²", "min": 1, "decimals": 1, "group": "about_object" },
        "floor": { "kind": "integer", "label": "Этаж", "min": -3, "group": "about_object" },
        "spot_number": { "kind": "string", "label": "Номер места", "maxLen": 50, "group": null }
      }
    }
    // ...ещё 9 типов
  },
  "groups": { "about_object": {"label": "О квартире"}, ... }
}
```

Числовые поля несут только `min` — верхних границ нет (ADR 0069, решение
владельца 23.10.2026), как и кросс-правил согласованности полей.

Поле `options` у `enum` — это карта `ключ → русская подпись` (объединяет TS
`options[]` + `enumLabels`). Порядок ключей в JSON сохраняет UI-порядок полей
(объекты JSON хранят порядок вставки с ES2015).

### kinds

| kind | обязательные поля |
| --- | --- |
| `enum` | `kind, label, options, group` |
| `number` | `kind, label, unit, min, decimals, group` |
| `integer` | `kind, label, min, group` |
| `string` | `kind, label, maxLen, group` |

`group` может быть `null` (без группы, например у коммерции/паркинга).

## Верхних границ нет

У числовых полей (`number`/`integer`) нет `max` — значения произвольные выше
минимума (ADR 0069, решение владельца 23.10.2026). Прежние максимумы (площади
100 000, этаж/этажность 200, высота потолков 10, участок 1 000 000 соток,
уровень паркинга 100, год постройки «текущий + 5») и кросс-правила
согласованности («этаж ≤ этажность», «жилая/кухня ≤ общая») сняты целиком —
включая динамическую границу `year_built` (`maxYearBuilt()`/`yearBuiltMax`).

## Расхождения источников

При составлении `catalog.json` наборы полей для каждого из 11 типов сверялись
по двум источникам (Go `attributes.go` и TS `catalog.ts`). **Расхождений в
наборе полей между Go и TS не найдено** — все 11 типов имеют идентичные наборы
полей в обоих стеках.

Русские подписи взяты из frontend (`labels.ts`), подписи типов — из
`apps/frontend/features/properties/lib/property-types.ts`.

Примечания по деталям, которые различаются между стеками структурно (но не
семантически), и как они нормализованы:

- **год постройки и остальные максимумы**: сняты (ADR 0069) — исторически в
  Go и TS это было динамическое `now + 5` с маркером `yearBuiltMaxDynamic`
  в JSON.
- **cross-field правила**: сняты (ADR 0069) — исторически в TS `validate.ts`
  применялись безусловно ко всем типам (срабатывали только там, где есть
  соответствующие поля), в Go `crossFieldErrors` перечислял типы явно, а в
  `catalog.json` правила несли список типов по Go-источнику.
- **options как массив vs карта**: TS хранит `options: string[]` отдельно от
  `enumLabels` (карта подписей). JSON объединяет их в одну карту
  `ключ → подпись` — это канонично и удобнее для генератора.
