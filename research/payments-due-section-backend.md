# Research #1343: бекенд-подход секции «На оплату»

Дата: 2026-10-12. Методология: исследование по первоисточникам (код репозитория, GLOSSARY, ADR, уже принятая research-дока по уведомлениям, system-design-primer); каждое утверждение привязано к источнику. Кодовая база не изменялась. Тикет: [#1343](https://github.com/devnumbers/arenda-platform/issues/1343), реализация: [#1346](https://github.com/devnumbers/arenda-platform/issues/1346).

---

## Вопрос

Как построить серверную часть секции «На оплату»: правила с включённым напоминанием (`reminder_offset_days` 1/3/7, **без** auto_pay — решение владельца), у которых есть неоплаченная planned-операция с датой D в окне **D−N ≤ today ≤ D** (today — владельца объекта, ADR 0048). Просроченные (D < today) в секцию не попадают.

Выбрать: derivation на чтении vs материализация/индекс. Набросать контракт API (счётчик хаба + списковое чтение с бакетами «Сегодня / Завтра / Через 3 дня / Через 7 дней», сортировка «Сначала новые»). Оценить влияние на GET /payments, масштабирование и совпадение окна с уже стреляющими reminder-напоминаниями.

---

## Факты из кода

**Модель и канон вычислений на чтении:**
- Просрочка и «следующая дата оплаты» **не хранятся** — вычисляются на каждом чтении; «отдельная колонка в БД» в _Avoid_ словаря: `apps/backend/internal/payments/GLOSSARY.md` («Просрочка», «Следующая дата оплаты», «Завершённый платёж»).
- `NearestDateOfPayment` — единый seam ближайшей даты (тикет #991): хранённая next planned, иначе чистая проекция от `ProjectionCursor`; `apps/backend/internal/payments/application/nearest_date.go`.
- Глобальный фид правил уже деривирует всё на чтении одним SQL: lateral-агрегаты по `operations` (next planned, overdue count/oldest date), today владельца заезжает параметром параллельными CSV-списками owner→today: `apps/backend/db/queries/payments_global.sql` (`ListGlobalPaymentRules`, `SumGlobalPaymentCounters`, `CountGlobalPaymentRules`), адаптер `apps/backend/internal/payments/adapters/postgres/payment_global_store.go`, сервис `apps/backend/internal/payments/application/global_payment_service.go` (`ownerTodays`, `enrichItems`, keyset по `(created_at, id)`, total по скоупу).
- Красная точка просрочки в списке объектов — тот же приём, батчами по владельцу против его today: `apps/backend/internal/payments/adapters/postgres/overdue_reader.go`.
- Today владельца считается **в Go** и уходит в SQL параметром; `AT TIME ZONE` для доменной границы в SQL платежей запрещён (граничные джобы уведомлений — документированное исключение): ADR 0048 п.2.
- Чистое чтение не тикает: ADR 0048 п.1 (решение №1 карты #443), GLOSSARY «Тик»; тик — ежечасный воркер по зонам + внутри мутаций: `apps/backend/internal/payments/application/tick_service.go`.
- Материализация держит на правиле «все наступившие + ровно одно следующее будущее» вхождение: GLOSSARY «Материализация»; значит, stored planned-хвост на правило мал (просроченный долг + сегодня + одно будущее).

**Напоминания — существующая машина (notifications):**
- `payments.reminder_offset_days INT CHECK IN (1,3,7)` + частичный индекс `idx_payments_reminder_offset ... WHERE reminder_offset_days IS NOT NULL`: миграция `apps/backend/db/migrations/000138_payment_reminder_offset.up.sql`; валидация в домене — `apps/backend/internal/payments/domain/payment.go` (`ReminderOffsetDays`), `application/payment_service.go` (`IsValidReminderOffset`). Напоминание живёт независимо от auto_pay (#823); при создании автоплатёжного правила присланное напоминание форсится в NULL (#1186).
- Reminder-нога скана: planned-операции, у которых `(o.date − pay.reminder_offset_days) = today зоны`, `reminder_offset_days IS NOT NULL`, **auto-pay включён** (в отличие от секции!): `apps/backend/db/queries/notifications.sql` (`ListPaymentReminderTargets`, `ListPaymentScheduledReminderTargets`).
- Часовой прогон бронирует unique-джобы границ в окне `(now, now+48ч]` (`scheduledHorizon = 48h`): `apps/backend/internal/notifications/application/payments_publisher.go` (`RunZoneScans`, `scheduleBoundaries`), `tasks_publisher.go:21`; reminder-джоба просыпается в настенные 10:00 дня D−N в поясе владельца и на пробуждении перечитывает живое состояние (delivery-time re-check): `apps/backend/internal/notifications/adapters/notificationsjob/payment_boundary_scheduler.go`, `worker_payment_boundary.go`. Зональный скан — подстраховка с instant-гейтом (не публикует раньше 10:00). Канон машины и её сверка с практикой: `docs/research/notifications-scheduling-best-practices.md` (delayed job + sweeper + дедуп по (тип, правило, дата)), ADR 0059 (River), ADR 0048 п.3 (дополнение: букинг + ретроспектива), ADR 0040 (контраст UTC-якоря).
- Схема: `operations (payment_id, date) UNIQUE WHERE payment_id IS NOT NULL`, индексы `idx_operations_owner_date (owner_id, date)`, `idx_operations_property_date`: миграция `000115_payments_context.up.sql`; статусы planned/paid/cancelled, просрочка не хранится.

**Текущий контракт глобального фида:**
- `GET /payments`, `GET /payments/search`, `GET /payments/objects`, `PUT /payments/favorites/order`; строка несёт `today`, `nearestDate`, `overdueOperationCount/overdueDays/oldestOverdueOperationId`, `isFavorite/favoriteOrder`; счётчики хаба `favoriteCount`, `overdueOperationsCount` едут в ответе фида: `apps/backend/api/openapi/openapi.yaml` (пути ~2128–2260, схема `PaymentsGlobalResponse`/`PaymentGlobalItem`), `apps/backend/internal/payments/adapters/http/global_payment_handlers.go`.
- «На оплату» сейчас явно **вне среза**: GLOSSARY «Лента платежей» + `_Avoid_: «На оплату» (вне среза)`; это решение и ревизуется тикетом #1346 (словарную правку делает он).

**Совпадение окна секции с напоминаниями.** Операция входит в окно «На оплату» ровно в день напоминания D−N (reminder-нога публикует «Напоминание о платеже» в 10:00 этого дня) и покидает окно в день срока D (due-нога — «Оплатите платёж»; на следующий день операция становится просрочкой и уходит в существующую «Все просроченные»). Окно секции [D−N, D] — это в точности промежуток между двумя уже существующими граничными джобами. Джобы — механика доставки (at-least-once, отменяемые, re-check), а не источник истины для UI: истиной остаются таблицы `operations`/`payments`.

## Варианты

### A. Derivation на чтении (по образцу фида)

Один SQL: видимые неархивные правила с `reminder_offset_days IS NOT NULL AND auto_pay = false`, join planned-операций с предикатом `o.date >= today AND o.date - pay.reminder_offset_days <= today` (эквивалентно `today - N ≤ D ≤ today`), today владельца — параметром по образцу `ownerTodaysCSV`.

- **Плюсы:** нулевой дрейф — today меняется у каждого владельца ежедневно без единой записи, и derivation это ловит бесплатно; нет второй state-машины и её staleness-багов (неверно показанная денежная строка — худший класс дефектов для учётного продукта); нет бэкфилл-миграции; совпадает с каноном репо («вычисляется на каждом чтении», reads never tick, ADR 0049/0048, прототипное решение №2); стоимость чтения заведомо посильна — весь фид правил уже делает более тяжёлые lateral-агрегаты на каждый запрос, а planned-хвост на правило мал по построению материализации.
- **Минусы/риски:** стоимость растёт с таблицей `operations` (годы истории) — лечится частичным индексом по planned и общей архивацией истории (вне среза); при росте числа правил с напоминаниями запрос надо держать селективным (драйвер от `idx_payments_reminder_offset`).
- **Оценка по system-design-primer (read-heavy ленты):** паттерн «precompute/materialize» оправдан, когда чтение тяжёлое или fan-out большой; здесь чтение — селективный join по узкому окну в персональном скоупе актёра, а предвычисление потребовало бы ролловера на каждую полночь владельца — то есть второго тика, от per-owner состояния которого ADR 0048 осознанно отказался.

### B. Материализация (таблица `due_entries` / МV)

Таблица записей (rule, operation, bucket), обновляемая тиком/мутациями/ежедневной джобой; чтение — индексный скан.

- **Плюсы:** O(1)-чтение, тривиальная пагинация.
- **Минусы/риски:** инвариант придётся поддерживать на **всех** путях изменения правды: создание/правка/пауза/возобновление/оплата/отмена операции, смена `reminder_offset_days`, включение/выключение auto_pay, архив объекта, смена пояса владельца (ADR 0048 п.5 — сдвигает границы задним числом относительно секции), плюс ежедневный ролловер бакетов в полночь каждой зоны. Машин много, каждая — место для рассинхрона с таблицами; МV отвергается тем же (refresh дороже и так же страдает от today). На текущем масштабе (частные владельцы, десятки правил на актёра) выгода не окупается.

### C. Гибрид: derivation + честные индексы + счётчик в существующем агрегате

Derivation для строк (вариант A), а счётчик хаба — одной дополнительной агрегацией в уже бегущем `SumGlobalPaymentCounters` (тот же запрос уже суммирует просрочку и избранное по всему скоупу), без отдельной таблицы. Частичные индексы — по результату EXPLAIN в тикете реализации.

**Решение: C (derivation как основа, счётчик едет в существующий агрегат фида).** Обоснование: секция мала и персональна, окно секции структурно совпадает с окном reminder-ноги (истина — в таблицах, не в джобах), канон репо — вычислять на чтении и не хранить производные статусы; материализация на этом масштабе добавляет вторую машину правды ради экономии, которую не с чем сравнить — существующий фид уже деривирует тяжелее.

## Набросок контракта API

**1. Счётчик хаба** — расширить существующий `GET /payments` (`PaymentsGlobalResponse`): карточка «На оплату» живёт на главном экране рядом с «Все избранные (N)»/«Все просроченные (N)», которые уже едут в этом ответе и не сужаются поиском. Поля:

- `dueOperationsCount: int` — число операций в окне по всему видимому скоупу;
- `dueNearestDays: int` (или `dueNearestDate: date`) — оставшиеся дни до ближайшего D; фронт рендерит метку «Сегодня» (0) / «Завтра» (1) / «Через N дней» (2..7) по уже заезженному в строке `today` — сервер меток не строит (канон: серверные тексты не строим, cf. «История изменений платежа»).

Альтернатива (отдельный `GET /payments/due/count`) — только если главный экран перестанет читать фид; сейчас лишний эндпоинт.

**2. Списковое чтение** — `GET /payments/due?limit=&cursor=`. Актор-scoped cross-property read с предикатом видимости в SQL (правило глобальных лент, #521), архив срезан, отменённые операции не существуют, reads never tick. Строки — пары (правило, операция); origin='manual' в секции не бывает (напоминание живёт на правиле). DTO на строку:

`paymentId`, `operationId`, `propertyId`, `propertyName`, `type`, `title`, `amountKopecks` (BIGINT-копейки, ADR 0008), `category` (CategoryRef), `today` (today владельца, ADR 0048), `dueDate` (D), `daysLeft` (D − today), `reminderOffsetDays` (N).

Бакеты — группировка по `daysLeft`: `0` → «Сегодня», `1` → «Завтра», `2..3` → «Через 3 дня», `4..7` → «Через 7 дней»; порядок бакетов фиксированный, внутри бакета — «Сначала новые» (кандидат: keyset по `(daysLeft asc, dueDate desc, id desc)` — один курсор сквозь все бакеты; малый объём секции, возможно, позволит в v1 отдать всё одним чтением без курсора). Ответ: `{ items|buckets, nextCursor?, dueOperationsCount }`.

Правая граница окна: просроченные (D < today) не попадают; в день D строка ещё в бакете «Сегодня», в D+1 уходит в просрочку — клиентское обновление после оплаты/гашения закрывает карточку (оплата — на объектных эндпоинтах, секция read-only, как весь глобальный срез).

**3. Влияние на GET /payments:** структурного нет — новая секция читается отдельным запросом; единственная точка касания — добавка агрегата в `SumGlobalPaymentCounters` (и, если счётчик там, — в ответ фида). Реализация #1346 также обязана отревизировать словарь: убрать «На оплату» из `_Avoid_` статьи «Лента платежей» и завести статью секции (сейчас «вне среза» — решение ревизуется), возможно — амендмент ADR 0049.

## Индексы / производительность

- Драйвер join со стороны правил уже есть: `idx_payments_reminder_offset` (частичный, 000138). Со стороны операций работают `idx_operations_payment_date` (unique, lateral на правило) и `idx_operations_owner_date (owner_id, date)` (оконный диапазон).
- Кандидат для #1346 (только по EXPLAIN): частичный `operations(owner_id, date) WHERE status = 'planned'` — отсекает paid-историю и cancelled-надгробия из оконного скана; схема добавления — новая миграция, `make migrations-lint`.
- Reminder-нога `ListPaymentReminderTargets` считает `(o.date − offset) = today` — по computed-стороне неселективно, но часовой объём мал; секции это не наследует: её предикат надо писать саргируемым (`o.date >= today AND o.date <= today + max_offset` + проверка оффсета), не повторяя приём скана.
- Масштабирование: секция ограничена скоупом актёра и малым planned-хвостом; рост истории `operations` лечится частичным индексом и архивацией; reconsider материализации имеет смысл только при изменении профиля (агрегаторы/BI поверх всех операций) — не этого тикета.

## Открытые вопросы для #1346

1. Бакеты для промежуточных остатков (правило с N=7 в день D−5): предложено `2..3 → «Через 3 дня»`, `4..7 → «Через 7 дней»` — подтвердить маппинг и заголовки.
2. Трактовка «Сначала новые»: `dueDate desc` внутри бакета (дальние сроки сверху) или `created_at desc` правила (как в фиде); от этого зависит ключ keyset-курсора.
3. Пагинация: отдавать ли v1 все бакеты одним чтением (секция мала) или сразу keyset; курсор сквозной по бакетам или покомпонентный.
4. Арендные управляемые платежи: аренда ставит напоминание вместе с автоплатежом (#1198), а секция исключает auto_pay — управляемое правило, переведённое правкой в не-автоплатёж с напоминанием, попадёт в секцию; подтвердить, что это желаемое поведение.
5. Счётчик хаба: в ответе `GET /payments` (предложено) или отдельным эндпоинтом; сужается ли счётчик при поиске (канон — не сужается, как «Все просроченные»).
6. Realtime: персональные состояния фреймов не публикуют (D18) — секция обновляется перечитыванием; подтвердить для карточки хаба.
7. Словарь/ADR: ревизия статьи «Лента платежей» (снятие «На оплату» из _Avoid_), новая статья «На оплату», амендмент ADR 0049 — оформить в #1346.
8. Краевой случай смены пояса владельца внутри окна (ADR 0048 п.5): derivation подхватывает бесплатно, но клиентский кэш `today` может мигнуть — учесть в UI-тивете.
